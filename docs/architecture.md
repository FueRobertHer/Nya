## Storage and encryption

Everything is stored in Upstash Redis, in a key namespace per environment (`production:`, `preview:`, `dev:`; see `lib/storage.ts`). The values that hold financial data are encrypted (AES-256-GCM, `lib/crypto.ts`) before they are written: Plaid access tokens, SimpleFIN Access URLs and Lunch Flow API keys, balances, history, transactions, budgets, goals, category changes and renames, tags, notes and rules, manual accounts, the records of when shared accounts were shown (the sharing access log) and the caches. The structure around them is not: key and field names, and the few stores that hold no amounts (`classify()` in `lib/reencrypt.ts` lists every store and how it is kept). So a leak of the database or of a backup alone exposes no balances, transactions or access tokens, but it does expose dates and times, account, transaction and connection ids, the names of your linked banks (and whether Plaid included transactions when each connection was linked), the merchant names you have renamed, and for sharing, the names people gave each other, which accounts each shares at which level and until when, which other kinds (net worth, spending, holdings, budgets, goals) each shares at which level, with the random ids of the goals chosen, and for each connection the random id its records of showings are kept under and when they began, though not what they record (the same list as [operations.md](operations.md#taking-a-backup-by-hand)).

Encryption is layered. Data is encrypted with **data keys** that the app generates and keeps in Redis, each locked with one **master key** (`MASTER_KEY`, which lives only in your environment variables). `PLAID_ENCRYPTION_KEY` is the original key, `k0`, used for everything written before data keys existed and as a fallback if a data key is ever unavailable. Rotating the master key re-locks only the data keys, never the data. See [operations.md](operations.md#encryption-keys) for turning it on, moving old data across, and rotating. Each container also has a data key of its own ([below](#per-container-data-keys)): one made on this version gets it at birth, and one made before it from the migration pass; until then, a container's values are under the environment's keys, which every container can read.

The protection is against someone who obtains the database or a backup without the keys. It does not protect against someone with access to the Vercel environment, which holds both the master key and the database credentials.

Logs leave out what a request carried. A failed Plaid call throws an error that holds the request it was making (the Plaid secret in its headers, an access token in its body), and printing it copies both into the deployment's logs. The Plaid client is built so its errors never carry the request (`lib/plaid-scrub.ts`): the endpoint, the method and Plaid's answer stay, the headers, body and raw request go. Routes also log errors through `loggable()` (`lib/log-safe.ts`), which keeps the endpoint, Plaid's error code, reason and request id, the status and the stack, for anything that reaches a log some other way. Logs written before this change may hold the Plaid secret and access tokens: see [operations.md](operations.md).

Each institution's stored transaction and investment history is one compressed, encrypted blob, refused (never trimmed) past a size ceiling (`MAX_TXN_BLOB_CHARS`, 8,388,608 characters by default). Trimming would drop the oldest rows, which are exactly the ones no bank will serve again. `GET /api/storage-usage` measures, for one container (`lib/blob-sizes.ts`): every institution's stored transaction and investment blob, per institution and in total (`total_chars`), with the ceiling, blobs left behind by a disconnected institution, and the size a blocked institution was refused at; and every store on the storage seam that holds something (`stores`, and their total, `stores_chars`), each with its entries, its characters, and its largest value, the one nearest the ceiling, since each write is held to it on its own: a manual account's book of transactions (`lib/manual-txns.ts`), one import's records, a linked account's transactions imported from files (`imported-transactions`, `lib/history-import/store.ts`), one month of holdings history, and the rest. The largest value's id is named only for a store declared exportable: an API token's id is part of the token. The counters (a count per container or per id, such as each API token's requests) are bookkeeping and aren't listed. A refusal's log line names the container too. It doesn't measure the older stores kept as hashes (balance history, manual accounts, categories, renames, links, the account directory) or the caches, so neither total is the container's whole size. Nothing enforces a quota yet; one would read these numbers, and those stores' too.

### Per-container data keys

How each container's values get a data key of their own (#54, "Shape for multi-user"; the master plan's M1 gate and its privacy Gap 2), as built in `lib/crypto.ts`, `lib/key-archive.ts`, `lib/reencrypt.ts` and `lib/account-deletion.ts`. A container from before this release keeps its values under the environment's keys until the migration pass gives it a key and moves them, so until then the environment's keys stand for it as they always have: destroying a key can't make its copies unreadable, and a key-scoping bug would read its values. The operator's side (backups in two kinds of file, restoring, deleting, the migration pass, rotating, rolling back, and how long a deleted account's copies stay readable) is in [operations.md](operations.md#per-container-data-keys).

What it is for:

- **Deletion means deletion.** Deleting a container destroys its key. Once every kept backup of the keys has been rewritten without it (normally within minutes, as part of the deletion), nothing encrypted under that key can be decrypted from any copy Nya keeps, the nightly archives included.
- **Blast radius.** A value under container A's key fails to decrypt as container B's, even copied into B's keys. Isolation covers the values under a container's own key: values still under `k0` or an environment key read in any container until the migration pass moves them.
- **Isolation of loss.** Losing or damaging one container's key breaks that container's values and no other's, in the database and in the backups.
- **Transfer and rotation.** Handing a container to another owner changes the owners map and nothing else: the container keeps its id, and so its key. Rotating the master re-locks container keys exactly as it re-locks the environment's.

**Where the keys live: beside the environment's.** A container's key is one more entry of the key store, `crypto:keys`, in the same format: an id `k<n>-<8 hex>` that commits to the key, and a lock per master made with the same additional data. One field is added, `container`: the container the key was made for. The release before reads it as a field it doesn't know and keeps it (its rotation code copies the rest of a record as it is). Keeping container keys there is what makes rolling back safe (below). Under the container's own prefix the release before could not find them, `classify()` refuses a `crypto:` key inside a container, the key-family lists are frozen, and the key would travel in the data archive with the data, which is what deletion must avoid.

**Numbering.** A key's number comes from a counter of its own, `crypto:key-seq` (one `INCR`, started past the highest number in the store the first time), never from reading the whole store, which at a key per container would read megabytes on every sign-up, and never from a field of `crypto:keys`, where the release before refuses anything that isn't a key ("Unexpected entry") and with it every master rotation. Each id is checked against the id format before it is claimed. Past `k999999`, the most the release before's parser takes, no key is made: that container stays on the shared key and the status lists it. Two keys with the same number (the release before still numbers its own first key by reading the store) are harmless: an id commits to its key.

**The map.** `crypto:container-keys`, environment-wide, in the `crypto:` family that `classify()` already lists as holding no ciphertext: one field per container, `{"key": "<key id>", "since": "<when the key was made>", "moved": "<since when every value of it has been under that key>", "shared_in": "<when the newest nightly archive holding one of its values under a shared key was taken>", "key_in": "<when the newest archive the release before took after the key was made, which holds the key itself, was taken>"}`, or, once its key is destroyed, `{"destroyed": "<day>", "swept": "<day>"}`. It holds nothing secret. A write finds its container's key through it; a read needs only the key its value's header names. Unlike the key store it travels in the data archive, with the data it describes, so a restored container always says which key it expects.

**How `encrypt` knows the container: it is told.** `encrypt(ctx, plaintext)` and `decrypt(ctx, payload)`, the shape #54 set out. The `Ctx` is the container the value is stored in: the same `Ctx` that built its key with `kc()`, never the viewer's or the caller's. Sharing's projection passes the owner's (as it already does to read the owner's keys), the API on a token the token's container, the snapshot cron and the admin's view of connections each container's own, account deletion the deleted one's, and the one write a viewer's request makes in an owner's container (the record of a showing) the owner's. It is a required first parameter with no older form beside it, so a call that names no container doesn't compile, a branch merged later that still calls the old shape fails to build rather than writing under the environment's key, and there is no ambient container for a cron job or a shared read to get wrong. The seam (`lib/repo.ts`), `lib/stored-json.ts` and `lib/blob.ts` pass on the `Ctx` they already take or are given one (`readEncryptedJson(ctx, key, ...)`, `encodeJsonBlob(ctx, value)`), and so are the helpers that decrypt a blob without one (`decryptMap` and its like in `lib/history.ts`, `fetchInstitution` in `lib/networth.ts`, `checkOne` in `lib/item-usage.ts`). Every call-site change is that argument and nothing else.

**Checked where the container is resolved.** The container's key is opened (and kept for the minute its map entry is kept) where a request resolves its `Ctx`: `dataCtx`, `signedInCtx` and `deploymentCtx`, the API's token check once the secret matches, each container's run in the snapshot cron, and sharing's `theirCtx`. A key that can't be opened throws `ContainerKeyError` there, before any reader runs. So the readers that swallow errors (the caches, which only miss, and the catch-all blocks in `lib/history.ts` that drop a point they can't decrypt) only ever meet a key destroyed in the middle of a request; they stay lenient for that, and for values under other keys, as today, because what they feed is either recomputed strictly (the caches) or a chart that already says when points are missing. Account deletion doesn't check: it must go on when the key can't be opened, and then counts what it can't read as unavailable and the banks it can't reach as not disconnected, as it does today.

**What belongs to no container** stays under the environment's keys. The environment-wide stores (the list at `kEnv` in `lib/storage.ts`: the key store, the container registry, the owners map, sharing's connections and invites, the rate limiters, the sessions cutoff, the backups' last outcome, and the ECB's public reference rates, which belong to no one) hold nothing encrypted with `encrypt()`. The only ciphertext outside a container is the pre-container copies the data move left at the environment's root (`MOVED_KEYS` in `lib/move.ts`), which nothing reads and which are due to be deleted: they stay under `k0` or the environment's data key until then, and the migration pass leaves them alone.

**Writes.** A container the map names a key for writes under that key and never falls back: if the key can't be had (it is missing from the key store, this master can't open it, or its record names another container), the write throws `ContainerKeyError`, and so it does for a container whose map entry says its key was destroyed. So nothing is ever written beside values that can't be read, no write that doesn't read first (a map store's `set`) replaces one, and a request still in flight when its account is deleted can't leave a value under the shared key. A container the map names no key for (one made before this release, or by the release before while rolled back) writes under the environment's active key as today, with its fallback to `k0`, until the migration pass gives it a key. This withdraws, for containers with a key of their own, the promise in the header of `lib/crypto.ts` that a missing or broken master can make writes use the old key but never fail: a storage failure reading the map entry or the key on its first use in a process now fails that write.

**Reads.** `decrypt(ctx)` opens the key the value's header names, as today, and then checks it against the container:

- a value under a key whose record names this container, or under `k0` or an environment key (no `container`), reads as today;
- a value under the container's own key (the one its map entry names) that can't be opened, or whose record names another container, throws `ContainerKeyError`: the container's key is broken, not the value;
- a value under another container's key throws `KeyNotForContainerError`, an error of its own and not a `DecryptFailedError`, since nothing has been decrypted: to the seam it is unrecognised (409, never offered for removal), `unreadableForGood` in `lib/history.ts` doesn't take it for damage, and it is logged as a possible isolation bug, naming the two containers and the key.

Refusing values under `k0` or an environment key in a container that has moved (a strict mode) is a later step: only once rolling back to a release that writes them is no longer a plan, keyed per container off `moved` and an environment-wide floor the operator sets after the soak.

**Bound by the key, not by the `c` flag.** Each container's key is made for one container and used for no other, and both `encrypt` and `decrypt` check its record against the `Ctx`. No cryptographic binding fits the rollback constraint: the release before checks a wrapping's additional data, an id's commitment and a value's header exactly, so making any of them name the container breaks it. And none would stop anything more today: someone who can write to the database can already rewrite `owners`, a key's `container` field and the map, all plain text. What binding by the key stops is a key-scoping bug: code that reads one container's key while acting for another fails loudly instead of showing the wrong person's data. Since both sides of such a mix-up are a `Ctx`, the types can't catch one, so a test-time invariant in `test/fake-redis.ts` checks, across the whole suite, that every ciphertext written under `c:<id>:` names `k0`, an environment key or a key whose record names `<id>`. The later step is one change: authenticate the key records and the owners map with keys derived from the master, then bind values with the `c` flag behind a switch, with a context that never includes the environment prefix.

**Caching.** Opened keys are kept per process and per master as today, now with their `container`: concurrent first uses share one load, and a failure is never kept. A container's map entry is kept for up to a minute, as the active key is, and its key re-checked against the store when it is read again. So a write costs no extra round trip in the hot path, a read none beyond opening the key it names once per process, and a new key is picked up within a minute. The snapshot cron, which walks every container, opens each container's key once.

**Making a container's key: never on a write.** A missing map entry must never read as a new container, so `encrypt` never makes a key. The key is generated, numbered, wrapped and proven to open first, then claimed in one Lua step:

- **at the container's birth, in the step that registers it**: `CLAIM_OR_CREATE` (`lib/owners.ts`, an account's first sign-in) and `CREATE_FIRST` (`lib/containers.ts`) write the key's entry and the map entry together with the registry entry, so no request can reach a new container before it has its key, and a container born with its key is moved from the start (`moved` is its `since`). When the rotation or master checks below fail, the container is registered without a key, as before;
- **for a container from before this release, by the migration pass**, through `nya:container-key-create`, which answers the key already mapped if there is one (of two processes at once, one wins and the other uses its key, its own never stored) and refuses for a container not in the registry, so once a deletion has removed the registry entry no key can appear for it again.

Both refuse while a master rotation is prepared or pending or a rotation step holds the rotation lock, and for a deployment whose master isn't the current one: the rules `createActiveKey` follows, for the same reason (a key made then would have only one lock). Both claim the id only if it is free. A container left without a key writes under the environment's key until the pass makes it one, and the ops status lists it.

**When something is wrong.**

- A container whose key can't be opened answers `ContainerKeyError`, a `ContainerError`, so every route already answers it through `containerUnavailable()`: a 503, the API's `unavailable`. The person sees "Your data can't be read on this server just now"; the container, the key id and the reason go to the log only. Never empty, never written over, and never offered for removal: a missing key is a deployment problem (a key store restored without its keys, say), not damaged data. A storage failure while loading the key stays what it is, a 500.
- Before a token's secret has matched, the API's token check answers a container whose key can't be opened as it answers any token that doesn't work (`recordOf` catches it), so a broken key tells nobody a container exists.
- A map entry missing for a container whose values are under its key (the key's own entry, which names the container, still there) is damage, not a new container: reads still work, writes go to the environment's key, and the pass reports it and restores the entry from the key's record, never making another key.
- A key destroyed by a deletion leaves a tombstone (`crypto:destroyed`, a hash: the key id, its container and the day), kept for good, in the store and in every key archive. So the pass, the status and a restore tell a destroyed key from a missing one, and a restore of any archive, even one kept outside the retention window, leaves a deleted account out. Once the owners entry and the archives holding it are gone, a tombstone holds nothing about the person: a random container id, a key id and a day. With neither the key's entry nor a tombstone, the pass reports the values under a key the store doesn't hold, as it does today, and makes no key for that container.
- Errors and logs name containers, key ids and master fingerprints, never a key, a context or a value, as today.

**Master rotation, resumable.** With a key per container the rotation's loops are the size of the number of accounts, so they change, though not what they store. Prepare and finish read the key store a page at a time (`HSCAN`, 200 keys a page) and write a page of keys per request (100). Finish passes a key it has already finished (only the current master's lock, and no `next`), and removes the rotation record only once every key is in that state. Before this release an interrupted finish (a Redis error part way, or the automatic finish frozen when the request it ran beside ended) left its finished keys without `next`, so every retry refused and the rotation stayed pending for good; now the next attempt (the automatic finish runs every ten minutes per process) completes it. That matters more here, since no container key can be made while a rotation is pending. Prepare is still one pass that writes every key again: interrupted, it leaves no record and is run again whole. The ceiling is measured and stated in [operations.md](operations.md#per-container-data-keys). The release before reads every key as before.

**Rolling back.** The release before reads everything this one writes, so no switch holds the writes back: container keys are ordinary entries of the key store it reads, locked with the same master, and values stay unbound v2. While it runs, the isolation check is off (its `decrypt` takes no `Ctx`). What it sees, how this release notices afterwards from the backups it wrote, and what to do on rolling forward, is in [operations.md](operations.md#per-container-data-keys).

**The key archives** (`lib/key-archive.ts`) hold the key store apart from the nightly data archives, which leave it out (format 2, `lib/export.ts`): a header, one line per key (its record exactly as stored, and, for a key carried forward, when it was first missed and when a data archive last named it), one per tombstone and one per record kept beside the keys (`crypto:active`, `crypto:key-seq`, `crypto:master`, `crypto:rotation`), in code point order, so a file is a function of what it holds, and a footer with a count and a SHA-256 as the data archive's. A file's name ends with a digest of the tombstones it holds, so a run reads only the files that lack one. A rewrite is checked by building it again from the file before it. The nightly run (`lib/backup.ts`) writes them; a deletion and `POST /api/ops/container-keys` rewrite them; a restore (`lib/restore.ts`) reads one beside a data archive. Their lock and the marker a deletion leaves are `backups:keys-lock` and `backups:keys-pending`, beside the backups' own record.

**Changes this brings to the seam's header.** `lib/repo.ts` says a seam value is never bound to its container "so a container's data can still be copied byte for byte". With a key per container a byte-for-byte copy into another container no longer reads there, by design: moving data between containers means decrypting under one and encrypting under the other.

### Storage seam

New stores are built on the storage seam, `lib/repo.ts`, never on the Redis client. A store gets a few named operations instead of raw key access, so the code that uses it does not depend on Redis, and a Postgres or SQLite backend (which self-hosting would need) can later replace Redis one store at a time. It is Phase 1 of the Postgres migration plan, and changes nothing about how existing data is stored.

The seam keeps data inside containers only, by design: every store's data lives in the person's container and is deleted with it. There is no environment-wide store of anyone's data. A lookup that has to work before the container is known carries the container's opaque id itself (an API token will), so its record can live inside the container too.

The one exception is public data, which belongs to no one: `definePublicMapStore` declares an environment-wide map of plain JSON at `kEnv(name)`, checked by `isValid` on every read and before every write, never encrypted, never in anyone's download, and in the key inventory as plain (`classify()`), with `getMany` (strict, one HMGET), `getManyReport` (each field that can't be used named), `setMany` (one HSET, refused whole over the size ceiling) and `ids`. Its name must sit under a prefix of `REFETCHED_PREFIXES` (`lib/export.ts`), so backups leave it out (it can be fetched again) and a restore neither refuses nor writes it, and never deletes the running copy's. Only the ECB's reference rates use it, `fx:ecb` ([below](#exchange-rates)); declaring another is a reviewed change, as adding to `kEnv`'s list is.

A store is declared once, in a module under `lib/`, with:

- a **name**, its key family: each container's data is at `<prefix>:c:<container id>:<name>`. A name already claimed by a key family stored the old way, an environment-wide store or a backup exclusion is refused;
- **`what`**, a plural noun for messages ("Your saved rules could not be read");
- **`isValid`**, the current shape, checked on every read and before every write;
- **`exportable`**: whether its content will belong in the person's own data download;
- optionally **`upgrade`**, which turns what an earlier version stored into the current shape, and **`compress`**, which stores each value gzipped, for values that can grow large.

There are two shapes for data. `defineValueStore` holds one encrypted JSON value per container, replaced whole on every save, like goals and budgets (`get`, `getReport`, `set`, `update`, `remove`, `size`). `size` measures what a store holds without reading it (entries, characters, and the largest value), for storage usage. `defineMapStore` holds one encrypted JSON value per id in a Redis hash, like manual accounts (`get`, `getMany`, `getAll`, `getAllReport`, `getAllReportNamingSealed`, `getAllLenient`, `set`, `setMany`, `update`, `updateMany`, `replaceUnreadable`, `remove`, `count`, `has`, `size`). `measureContainer(ctx)` measures every key of a container, the older stores' and the seam's, without reading a value, for Your data and the admin's view of storage ([below](#your-data-and-storage-across-accounts)).

Budget rollover and income carryover (`lib/budget-months-store.ts`, #37) are two value stores, `budget-months` and `income-carryover`, kept beside the budget set rather than in it ([below](#budgets-by-month-and-rollover)). Both are in the data download.

The connection health stores (`lib/connection-records.ts`, #51) are map stores, one entry per connection under Plaid's `item_id`, each written from one module: Plaid's warnings that a connection will end, when each connection last answered, and the email bookkeeping of a break. All three are in the data download ([data-export.md](data-export.md#stores-built-on-the-storage-seam)): they are about the person's own connections, shown on their Connection health card, and the notices are the record of the emails Nya sent them.

The Plan's scenarios (`lib/plan-scenarios.ts`, [below](#plan-scenarios)) are a map store, one entry per scenario, holding what each changes from the Plan, never a figure.

The currency the Plan's typed figures are in (`lib/fire-plan.ts` `planCurrencyStore`, `fire-plan-currency`; the rules in `lib/fire/plan-currency.ts`) is a value store beside `fire-plan`, not a field of the plan: `FirePlan`'s shape is closed, so a field the release before doesn't know would make it read the whole plan as unrecognised, while it never reads this store. It holds `{ version: 1, currency, amounts }`, `amounts` being the plan's typed amounts (`typedAmounts`) as the save that wrote it left them, and holds for the plan only while they are equal (`recordedCurrency`). `GET /api/fire-plan` answers `currency` beside the plan: the recorded one when the record holds; else null, with `currency_problem` `stale` (a record of other amounts, its currency in `currency_was`), `unreadable` or `newer`; null and no problem is no record at all. `PUT` records the page's currency with the plan, the record first and then the plan, so a save that stops between the two leaves a stale record, never no record. The record is put back only when the seam refused the plan before writing it (`StoreRefusedError`, or a value there it can't read); any other failure may have come after the write landed, so the new record stays and then fits, or reads as stale. It refuses a currency other than the one recorded for the stored plan, or over a stale record, so a page that missed a change on another device loads and asks rather than change what the figures mean; a record that can't be used is left as it is, and the plan still saved. `POST` records the currency alone, for the plan as stored, when the typed amounts the page sends are the stored plan's; it replaces a record there (stale, unreadable, or another currency for the same amounts) only with `answered`, the person's own answer, and a newer version's never. So a save the release before makes after a rollback that changes an amount, a save that stopped part way, interleaved writes from two devices and a plan restored without its record each read as stale and are asked about, never as a wrong currency. The Plan's inputs then take that currency (`investedAssets`'s `own`, `trailingFlows`'s `currency`): with a home currency what is in others converts into it; without one only what is in it counts, the rest named, and a figure more than a tenth of whose transactions or accounts are in another currency isn't measured at all (`spendingGap`, `assetsGap` in `lib/fire/progress.ts`), so no FI number rests on a part of it. The year's tenth is weighed on each side apart (`TrailingFlows.volume`: money out against spending, money in against income, `CurrencyGap.sides` naming those over), and each figure needs only what it uses (`spendingOff`): the money out over leaves spending and savings unmeasured, the money in over only savings, so the FI number stands while savings, the savings rate and years to FI wait. The tenth is weighed by amount at the ECB's newest rates (`GET /api/currency`'s `ecb.rates`, read by `usePlanInputs` only then), used for nothing else, and by count where a currency in it has no rate or no rates are at hand (an empty `ecb.rates` is none), which `CurrencyGap`'s `unrated` and `ratesAtHand` tell apart. `Measured.unmeasured` carries such a figure apart from one with nothing to measure from, and `fiView` (`lib/fire/plan.ts`) and `planFigures` work out nothing from it: years to FI, Coast FI's `reached`, Barista FI's years, the balance at the target age, the walk and the projected start are null, never computed from zero. With nothing typed the plan has no currency of its own and follows its accounts', and the save that gives it its first amount records the currency (the accounts', when `shownReliably`, else the person's pick, asked first). With typed amounts and no record at all, the tab records the currency it is shown in when `shownReliably` (the accounts loaded from the server, never the dashboard's saved copy, and the transactions, without a problem; no counted account empty; a clear winner; most of the spending in it) and no save or answer is under way; it asks otherwise, and saves nothing on the Plan until it knows. The tab works this out from the plan the server last confirmed, never the one a save has yet to write, and `lib/whole-list-store.ts` holds a load asked for during a save until the save ends.

The allocation settings (`lib/allocation-settings.ts`) are a value store: the tax buckets, fund and account splits and target the person sets under Allocation on the Plan tab, saved whole through `/api/allocation-settings` after every field is checked (`lib/allocation/settings.ts` parseSettings). Reads check the shape only, closed, so a later release's settings read as unrecognised and are never saved over, and a release that changes a format or limit never makes earlier settings unreadable. They are in the data download. The classification and the allocation built from them are pure functions in `lib/allocation/`, run in the browser for today's allocation and on the server for each recorded day of holdings history.

The goal plans (`lib/goal-plans.ts`, #42) are a map store, one entry per goal id: each goal's allocation, monthly target, target date and archived state, beside the `goals` value, which keeps each goal's name, target and account as every release has, since the release before rewrites it with those four fields only. Each entry also holds those four fields as the save that wrote it left them in `goals` and, until that save finishes, the goal as it read before it, so a read tells a finished save from one that stopped between its two writes, and both from a change the release before made after a rollback; a save writes the entry of every goal it lists, then `goals`, then settles the entries (clears what it no longer needs of how they read before, deletes those no goal needs) with compare-and-set writes, each only while the entry is still what that save wrote or read, so no point in between reads wrong and two saves at once never take each other's writes for their own ([operations.md](operations.md#goals-plans-and-rolling-back)). What follows from them (what each goal counts of its account's balance, never more than it holds; its pace; when it will be reached) is worked out on every read by pure functions (`lib/goal-allocation.ts`, `lib/goal-projection.ts`, `lib/goal-view.ts`, worded by `lib/goal-text.ts`), in the browser for the Goals card and on the server for the API, and never stored. The months behind a pace are read from stored data only (`lib/goal-flows.ts`): through the Activity tab's assembly where Nya has the account's transactions, and from its measured balances, never an estimate, where it doesn't. A save is checked against the balances the server last measured (`lib/goal-save.ts`).

The weekly summary (`lib/weekly-summary/store.ts`, [below](#the-weekly-summary)) is two value stores and two counters. `weekly-summary` is the setting: on or off, the day and the time zone, closed, and in the data download. `weekly-summary-state` is its bookkeeping: the key its links to turn it off are signed with, the last week a summary went for (and one that got no answer), and the goals the last one found at their target; encrypted, backed up (so a restored copy doesn't send a week again), and left out of the download, the key being credential material. `weekly-summary-sends` counts Send me one now in a day, and `weekly-summary-unsubscribes` the links that worked in an hour. Reads are strict: a setting that can't be read is never taken for off, and a record that can't be read stops that person's summary rather than risk a week twice.

The currency settings (`lib/fx/settings.ts`, [below](#exchange-rates)) are a value store, `currency-settings`: the home currency the person chose, every change of it with its day, and their own rates. Closed, so a later release's settings read as unrecognised and are never saved over, and in the data download.

A third shape is for the service's own bookkeeping: `defineCounterStore` keeps a count per container in a fixed window that starts with its first count and ends on its own, for a rate limit such as the five downloads of your data an hour (`download-count` in `lib/rate-limit.ts`). `take` counts one and `read` reports the window, each one Lua script, so counts racing each other are each counted once and a count is never left without its expiry. A counter is a plain integer, never encrypted and never exported; a stored count that is not one fails as unreadable, so a limit built on it stays shut instead of opening. `defineCounterMapStore` is the same per id within a container, for a limit per API token (`api-requests` in `lib/api-token-store.ts`): one hash, each field an id's count and the end of its window (`<count>:<end>`, in seconds by the caller's clock), counted by one Lua script (`take(ctx, id)`), with the hash kept two windows past its last count so it outlives every window in it and goes on its own; `remove` forgets ids. A field that is not a count fails as unreadable, naming its id, and its hash is given an expiry if it has none, so it can't stay for good.

Writes to different ids of a map store never touch each other. Writes to the same id, like saves of a value store, are last-write-wins: reading an entry and then saving it loses a change saved in between. When something else can change the same entry at the same time (a webhook, a rule, a second device), use `update(ctx, id, fn)`. It reads the entry, computes the new value with `fn`, and writes only if the entry has not changed meanwhile (a compare-and-set in Lua); if it has, it waits a moment and runs `fn` again on what is there now, up to five times, then gives up with `UpdateConflictError`. It compares by SHA-1, so a large value is not sent back with its replacement. For a change that must land on several entries together or not at all (moving a manual transaction from one account's book to another's), `updateMany(ctx, ids, fn)` does the same for up to 16 entries at once: one Lua script compares every entry read and writes all of them or none, so no reader ever sees part of the change. A value store is for data one person edits at a time; where the app also changes one on its own (your categories, which grow from what transactions say while you may be renaming one), its `update(ctx, fn)` is the same compare-and-set for the whole value.

```ts
// lib/rules.ts
export const rulesStore = defineMapStore<Rule>('rules', {
  what: 'rules',
  isValid: isRule,
  exportable: true,
});

// lib/stores.ts
import './rules';
```

The rules for a new store:

- **Use the seam.** New code never imports `redis()`, `rawRedis()` or `@upstash/redis`, nor the raw-key helpers of `lib/stored-json.ts`, and never adds a key family to `lib/key-families.ts` or builds a new key by hand, even under a prefix or template the code already uses. If the seam lacks an operation, add a named, tested method to `lib/repo.ts` (with its Lua script, if it must be atomic), never a way to reach an arbitrary key. `test/storage-boundary.test.ts` enforces this. Its LEGACY list names the files that reached Redis before the seam; that list, the old key families and the key names the code builds (each with the files that build it) only ever shrink.
- **Declare the store, and import its module in `lib/stores.ts`.** That catalogue is how everything that walks every store sees all of them: the key inventory (`classify()` in `lib/reencrypt.ts`, which the re-encryption pass relies on) and the person's data download (`lib/user-export.ts`), where each store declared `exportable` is a section of its own, read with the seam's reports: an entry it can't use is named in the file (`problems`), never a reason to stop the download. A declared store is in the key inventory by construction, with no list to update. `test/repo.test.ts` fails if a declaring module is missing from the catalogue or two stores share a name. Give it an entry in `lib/inventory.ts` as well, in plain words, so Your data lists it ([below](#your-data-and-storage-across-accounts)); `test/inventory.test.ts` fails until it has one. The catalogue lists only stores built on the seam; the download reads the older stores itself until they move.
- **Label strictness.** Reads are strict. Never saved reads as empty. A value the seam cannot use is one of two kinds. **Unreadable**: its bytes are damaged (not ciphertext, or ciphertext that fails to authenticate under a data key). **Unrecognised**: as far as this code can tell it is intact, but it does not understand it: not JSON, a shape `isValid` rejects even after `upgrade`, or a format a later version may write (another version tag or flag, or a value bound to a context), so a rollback never offers such values for removal. Strict reads throw `StoredDataUnreadableError` for either: `UnreadableEntriesError` for a map store, naming the ids of each kind, and `UnreadableValueError` for a value store. **Only unreadable entries may ever be offered for removal**, and only once the person confirms: an unrecognised one is intact data and a bug to fix with `upgrade`. A deployment that cannot read the data (no `MASTER_KEY`, the wrong one, a key missing from the key store, a failed decrypt under `k0`, decompression failing, Redis unreachable) throws that error as it is, never reported as either kind or read as empty. A failed decrypt under `k0` is always treated so: `PLAID_ENCRYPTION_KEY` does not commit to its key, so after it is replaced every older value fails exactly as damage would, even beside newer values that read fine. `getAllReport` returns the readable entries, the unreadable ids and the unrecognised ids, so a route can show what it read, offer to remove the unreadable, and report the rest; a value store's `getReport` says the same of its one value. A store kept outside the seam whose reader reports what it can't read the same way (balance history and manual accounts, for the data download) tells the kinds apart with `openStored`, so every report draws the line where the seam does. A reader of one that answers rather than stops (the read-only API's manual accounts, a connection's record of its accounts in `rememberedAccountsReport`, each linked account's newest balance in `latestMeasuredBalances`) names a value sealed under a key this deployment can't use (a failed decrypt under `k0`, a data key the key store lacks: `sealedAway` in `lib/crypto.ts`) as `unavailable`, apart from what is damaged, and never passes over it for an older value. A map store's `getAllReportNamingSealed` does the same for the seam's entries, for such a reader: the accounts SimpleFIN and Lunch Flow keep up to date and their connections (`connectorBanksReport`), so one entry sealed away is named in the read-only API's `missing_accounts` as `unavailable` and the rest is answered, where `getAllReport` throws it. What says nothing about any one value (a master key that can't open the data keys, the key store out of reach) throws from each of them, as a deployment problem, so none of them calls a value damaged for it. Once the person confirms, `replaceUnreadable(ctx, id, value)` puts a value in place of one damaged entry in a single compare-and-set: it writes only while the entry's bytes are still the damaged ones it read (compared by Redis's own hash of them, since damaged bytes need not be text the client reads back exactly), so it can never replace an entry that reads, or an unrecognised one. `getAllLenient` is the one lenient read: it leaves out what it cannot use, and is only for conveniences that nothing writes, deletes or records on; say so where it is called. A value store refuses to save over a value it cannot read, and a map store has no "replace everything".
- **Answer its errors.** In a route, as `app/api/budgets/route.ts` does: `ContainerError` with `containerUnavailable()` (503); `StoredDataUnreadableError` with 409 and `{ error: err.message, unreadable: true }`, plus the id lists of an `UnreadableEntriesError`; `StoreRefusedError` (`UpdateConflictError`, `StoredValueTooLargeError`) with its `status` (409, 413) and the message; anything else with a plain 500.
- **Keep every stored shape readable.** Values are rewritten only when saved, and a restored backup brings old ones back, so `isValid` must accept every shape a deployed version wrote, after `upgrade`. Add a field as optional, or give the store an `upgrade` that fills it in. `upgrade` sees every stored value, current ones too, returns the current shape, leaves what it does not recognise for `isValid` to reject, and never throws. Writes always store the current shape.
- **Use opaque ids.** A map store's ids are Redis field names, stored and backed up in plaintext. Use random ids, a provider's own ids, or a hash of a random secret such as an API token. Never content (names, merchants, dates, amounts), and never a plain hash of content, which anyone with a copy of the database can reverse by hashing guesses. An id that must be derived from content needs a keyed HMAC whose key is not in the database. The seam accepts only letters, digits and `_.:-`.
- **Decide `exportable`.** True for what the person entered or what describes their money; false for secrets (token hashes, connector credentials) and the service's own bookkeeping. Separately, a store holding a credential that a restore must never bring back (API tokens, which a restore could otherwise revive after they were revoked) is declared `backup: false`, and its name listed in `EXCLUDED_PREFIXES` (`lib/export.ts`): declaring checks the two agree, so a store is never left out of backups by accident, nor kept in them by one. An exportable store is in the person's data download with nothing else to do: a section named after the store, holding its value (a value store) or its entries as `{ id, value }` (a map store), with what can't be read named under `problems` ([data-export.md](data-export.md#problems)). A name a part of that file already uses (`notes`, `accounts`) would fail every download, and `test/user-export.test.ts` fails first.

Every write is checked against the request-size ceiling of `lib/blob.ts` (`MAX_TXN_BLOB_CHARS`) and refused whole and loudly, with `StoredValueTooLargeError` (413): nothing is ever trimmed to fit. `compress` keeps large values well under it, and can be switched on or off later, since reads take either form.

Seam values are encrypted like everything else, but not bound to a crypto context (the `c` flag in `lib/crypto.ts`). The re-encryption pass cannot move a bound value, so it could never report complete, and retiring a leaked key depends on that. The header of `lib/repo.ts` says what binding would take later.

The existing stores still call Redis directly and move behind the seam one at a time. As each moves, it comes off the LEGACY list and out of `lib/key-families.ts`, and is given its Postgres destination. The seam's contract tests run the same assertions against the test double and, where `redis-server` is installed, against a real Redis.

## Caching

Balance and transaction responses are cached in Redis, encrypted with the same keys (`lib/cache.ts`), so the dashboard doesn't wait on live Plaid calls every load. The cache lasts 15 minutes; with Plaid webhooks configured it lasts up to six hours and is dropped the moment Plaid reports new data. The Refresh button bypasses it. The transactions cache holds only what came from Plaid (with categories, renames and exclusions carried across a re-link applied): transactions entered by hand, what the person said about each transaction (an exclusion, tags, a note) and their rules are read on every request and applied after it ([below](#tags-notes-and-rules)), so entering, editing, excluding or tagging a transaction, or saving a rule, never drops the cache or waits on Plaid, and a record that can't be read is marked on its row rather than stopping the cache. Every row carries its account's name and type, so the cash forecast counts only checking and savings; a cached part from before rows carried them is a miss. Beside the year of rows, the cached part also holds the few older rows recurring detection may need to see a yearly charge twice, and each answer sends those that qualify once exclusions are applied (`recurring_history`, [features.md](features.md#what-counts-as-recurring)); the cash forecast built on them is worked out in the browser and never cached or stored.

## Net-worth history

The daily net-worth series behind the Home chart (`lib/history.ts`) is stored the same way, encrypted and keyed by UTC date. It has two layers, and real points always win over estimated ones for the same date.

**Real snapshots** are recorded on every clean live fetch, plus daily by a Vercel Cron (`vercel.json`, `/api/snapshot`, authenticated with `CRON_SECRET`), so the chart stays gapless even on days you don't open the app. Per-account balances are snapshotted alongside the total, which feeds the tap-to-expand account charts.

- The cron runs each active container on its own (`lib/snapshot-job.ts`) and answers 200 with one result per container, even when some failed. It answers 500 when nothing was snapshotted: the container registry cannot be read (after one retry), holds no container, or no container was recorded (every one failed, came back unclean, was deferred, or is not active). Nothing linked is not a failure.
- A second entry two hours later (`/api/snapshot/catchup`) is the catch-up: containers already recorded that day are skipped, and the rest (failed, unclean, not started in time, or with nothing linked) are run again.
- Each container's outcomes are kept per date and served, newest first, by `GET /api/snapshot-runs`. They describe this environment's cron, so exports leave them out and a restore keeps them.
- No snapshot is recorded on a day when any institution failed or an account is unconfirmed missing (held for an answer, [below](#accounts-that-end-and-notes-on-the-timeline)). Accounts that did answer are still recorded to a separate per-account layer so their own charts stay real.

**Estimated backfill** reconstructs up to a year of history on first use (and after linking a new institution) from transaction data (`/api/backfill`), at three levels of fidelity:

- cash and credit accounts are walked backward from today's balances, un-applying each day's transactions;
- investment accounts have their external flows (deposits, withdrawals, dividends, fees) un-applied the same way, but market movement isn't a transaction and can't be recovered, so price changes within the window are not modelled;
- loans and manual accounts are held flat, since amortization isn't in the transaction stream and a typed balance has no stream at all (transactions entered by hand on a manual account need not add up to its balance, so they are never walked), and so is a bank account or card on a connection with no Transactions (one linked as a brokerage or retirement account whose accounts Plaid doesn't provide transactions for, see [features.md](features.md#connecting-accounts)).

The chart draws the whole estimated region dashed and labels it estimated. Some details:

- A connection with no Transactions never holds the run up, and is asked for transactions only if it holds a bank (depository) account or a card (`lib/item-products.ts`): its investment accounts are walked from their own flows, and a bank account or card on it that Plaid doesn't provide transactions for is held flat with no series of its own, its unknown past treated as a dormant account's is (the total stops at today unless another account's transactions reach back).
- Every estimate starts from every institution's balance today, so a balance Plaid doesn't give stops the run with nothing saved, never an estimate built without that institution, and the run isn't recorded as complete. What the answer says depends on who can fix it, by the same mapping as the connection's health ([features.md](features.md#when-an-institution-cant-be-reached)): no answer at all, or Plaid or the bank failing for now, is a 503 saying which ("Plaid couldn't be reached for Chase's balances"), and a later load tries again; a connection that needs reconnecting or removing first is skipped, as when its transactions can't be read (`skipped`, "institutions not ready"), until you do; and Plaid refusing Nya's own keys, settings or stored token is the server's own failure, a 500 logged with Plaid's code.
- An institution whose investments product isn't available falls back to flat for those accounts without affecting the rest of the run. One whose data is merely still being extracted also falls back, but the run isn't recorded as complete, so the next load rebuilds it once the flows have arrived rather than freezing the gap in place.
- An investment account whose flows out-run its balance (a $60k rollover into an account worth less than that today) is floored at zero from that day backward rather than dropped, so a large arrival reads as the step it was.
- Because a brokerage often reports further back than a bank, an investment account's own series is walked past the oldest cash transaction even though the net-worth total stops there.
- New links request 730 days of transactions; older Items may only have about 90 days until relinked.
- Hidden accounts are subtracted when the history is read, not when it is written, which is why hiding is retroactive and unhiding is exact. See [features.md](features.md#hiding-accounts). Accounts that ended are subtracted the same way, from their end day on ([below](#accounts-that-end-and-notes-on-the-timeline)).
- **An account's balances are kept unsigned**, beside totals signed when they were recorded, and every reader that takes an account back out of a total or splits one (hiding, an end, the split by currency behind converted history, forgetting a hidden account, the estimate's flat term) signs them with one type: the hidden or lifecycle entry's, or the account's own. So a manual account never changes between money held and money owed (`isOwedType`): `saveAccountEdit` in `lib/manual-account-writes.ts` refuses it (`OWED_FLIP`, 409) for the Update form and the API alike, and the form offers to close the account instead, for a new one of the other kind, which keeps every earlier point as it was recorded. Recording the sign each point was measured with, or a type per day, was weighed and left: the release before would read neither, so an account changed under them would be read with the opposite sign again after a rollback, and a forget there would write that into the totals for good. The form offers hiding beside closing: an account hidden is taken out of every day by its hidden entry's type, the one its days were recorded with, which suits one entered as the wrong type from the start.
- **Re-signing an account's past** (`lib/sign-repair.ts`) puts right the two ways an account still comes to be read as the other kind: SimpleFIN's and Lunch Flow's change of what a tracked account is (`retypeAccounts`, whose recorded values follow the kind: `nyaBalance`), and a manual account flipped under a release before the refusal. **Proven by the totals:** on a day with a total, sign every value in its breakdown by its account's type now; the sum falls short of the total by a gap, and every set of the day's accounts with a known type (Plaid's too, since a bank's own change of an account's kind explains a day as well as a person's) whose values, counted the other way, close it exactly is an explanation (`explanations`, half and half, at most `MAX_WEIGHED`, 24, accounts holding a balance; past it the candidates alone are weighed, every other account taken as counted as now, and past 24 candidates nothing is proven). Only the candidates (manual and tracked accounts) are labelled: one in every explanation was counted the other way that day (`flip`), one in none as now (`ok`), and one in some but not all can't be told (`ambiguous`: two flipped together whose values add up to a third's, equal values, or a held and an owed balance that cancel out, which totals can never tell apart); with none, an account whose type isn't known, more than 24 candidates, or anything unreadable, the day proves nothing, and says why (`Why` in `lib/sign-repair-store.ts`: `no-total`, `ambiguous`, `untyped`, `too-many`, `unexplained`, `unreadable`). A value of 0 needs nothing. Estimated days alike, against the estimated total, the walked map and that day's flat record. **Inferred from neighbours:** a day without a total (a partial day, one walked past the estimate) or one nothing proves takes the label of the nearest proven days on both sides when they agree, on the assumption that the account didn't change and change back between them; between a `flip` and an `ok` it is a `boundary`; with a proven day on one side only it is `undetermined` beside an `ok` (left as it is and reported, never taken as `ok`) and can't be told beside a `flip`. A retype's own moment counts as a proven `flip` before every entry of its day: the kind was the old one until then. **One mechanism:** a job in the `sign-repairs` store (by account id; bookkeeping, not in the download, in backups) plans each layer and day to turn over with the account's value there, and turns each over in one compare-and-set (`negateAccountOn`, the fold's `HISTORY_FOLD` with no total, a progress field of its own per step under the job's tag in `history:forgetting:`) only while the account's own value there is still the planned one: a fold of another account or a re-encryption, rewriting the map, leaves it to be turned over still, and a value turned over already or written since with another value is left. A day with a total is also decided again at that step, from the map and total as they are (`readSignDay`), and left when it now reads as counted as now (`ok`, or a gap of 0): a manual account's balance is the same number in either sign, so an estimate rebuilt meanwhile under its kind now holds the planned value in the right sign. So a job cut off part way is finished by running it again, never turning a day over twice; a run that stops (out of time, or cut off by an error) takes what it went through out of the saved plan, so the next starts there and never walks it again. It is run again by the request that started it, the next change of the account, the nightly snapshot (`finishSignJobs` within `SIGN_BUDGET_MS`, 5 seconds, which comes off the snapshot's `START_BUDGET_MS` as `PRUNE_BUDGET_MS` does; a failure there counts a night, as does a night out of time before a single day was gone through (`Stalled`, counted only for a run given at least half the budget), and after three the job is left to the operator's dry run), the download (within 90 seconds, counting no night), or the operator. Before a saved plan runs the account's kind is read again: no longer on the side it was planned for (changed back under the release before, say), the job is dropped with words and nothing more is turned over. Every total stays as recorded, and the account's hidden and lifecycle entries take its type now. A finished job leaves a `settle` record in its place: once `SETTLE_AFTER_MS` (10 minutes) has passed, the next run decides the day it finished, the day its job began (`began`), and the day before each, again by their totals and turns over one proven `flip`, which a recording that read the old kind before the change and landed after the job had turned the day over leaves (a day without a total is left so), then removes the record; a new job of the account replaces it, and it refuses nothing. A job holds the links lock at most `JOB_BUDGET_MS` (90 seconds, under `LINKS_LOCK_REQUEST_SECONDS`) in one go, stopping between the maps it reads or the days it turns over, so a hold fits the lock's lease inside any route. A forget of the account (`forgetEarlierAccount`), the API's undo of an account it made, and the folds beneath them (`foldHiddenAccount`, `forgetAccountBalances`) are refused while a job (`pendingJob`, a settle record aside) is pending, in words that point to the operator once the nightly job has stopped trying it; no job begins on an account being forgotten. **A retype** writes its job before the kind changes, makes the change its first step under the links lock, and plans under the new kind: `flip` days, proven or inferred, are turned over and `ok` ones kept (an older retype is put right so); on its own day a value nothing proves is turned over when it is the account's balance under the old kind and not under the new (recorded just before); every other day is left as it is, and the answer says how many, and why. A change read as within one side is written only while the kind stored is still on that side, and one that crosses now goes to the re-sign. Every change in a request is tried; `retype_note` says which changed, which didn't (the lock held, a job of it still pending, a failure, or already the kind asked), which are still being turned over, and the days left by reason, and the caches and the backfill flag go for what changed. **A repair** (`POST /api/ops/sign-repair`, [operations.md](operations.md#repairing-balance-signs)) turns `flip` days over, proven or inferred, and refuses, naming the days and writing nothing, when an `ambiguous` day, a `boundary` or a run of `flip` days reaching an end nothing marks says the days can't be told exactly; `undetermined` days are left and reported, with their reasons. It plans from the layers as they are, the legacy flat estimate record split by day only once a plan is accepted. **Not here:** an account's earlier ids (links) are not re-signed: each is subtracted by the kind its link recorded, and the split by currency reads them by the account's type now, as before. No reader and no stored shape changes, so the release before reads every re-signed day alike; it ignores the store, so a job pending under a rollback leaves the account read as it always was there.
- Transactions imported into a linked account from its bank's files take the estimate back past the backfill's earliest point, for bank accounts and cards, and only across days a file or the bank covers ([below](#the-walk-through-imported-rows)). They write estimated points before that earliest point only, never a recorded one. Those dated in the backfill's own window, it walks itself, beside the bank's rows.

### Accounts that end, and notes on the timeline

An account's end (#50, [features.md](features.md#accounts-that-end)) is a state with a day, never a deletion, kept in the `account-lifecycle` map store (`lib/lifecycle.ts`), one entry per account id: closed or left on a day with an optional note, untracked from a day, or active with the answer to a question ("Still open"); the account's kind and name, so it can be signed and named after its institution is gone, and its currency where the write knew it, so it can be priced after that; its connection; when it was set; `assumed` for a closure Nya assumed; `seen`, the balance a closed or left account showed when its end was set or confirmed (with the day its transactions were last read for the question about it, at most once a day); and `missed`, the windows it was missing and assumed closed before it came back, which every later change keeps, each with the id of its note. The notes are the `timeline-notes` map store (`lib/timeline-notes.ts`): Nya's under `lifecycle.<account id>`, one per account and moved with it, and `missed.<random id>`, one per missing window, the id kept on the window, since a day can't be part of a field name (`adoptMissedNotes` moves a note this branch first wrote under `missed.<account id>.<first day>`, once, beside the vanished-account guard); the person's under random ids; up to 500 of 200 characters. Both are encrypted, closed in shape (a field this version doesn't know makes an entry unrecognised), exportable, and measured by storage usage.

- **Applied on read, like hiding.** `getHistory(ctx, hidden, ended)` subtracts each ended account from every point on or after its end day, from its own balance in the per-account layers, signed by its kind, in the real and estimated layers alike; a day where it has a balance it can't sign (its kind unknown) is left out, never guessed, and an account both hidden and ended is subtracted once. The live total leaves an ended account out (`applyLifecycle`), from as soon as its end is set: an end may be today in the person's time zone, a day ahead of UTC (`lastEndDay`), while today's charted point, a UTC day before such an end, still counts it, as the day reads once recorded. Nothing is written to any history layer, so moving an end recomputes the later points and reopening restores them exactly; `test/lifecycle.test.ts` holds the real layer byte-identical.
- **The cliff stays.** Across a stretch with nothing recorded, the chart draws a straight line between the points either side (`bridgeInteriorEstimates`); a stretch that holds an end day steps on that day instead, with an estimated point on the day before it and one on the day itself where nothing else is (display only, never written), so the drop falls on its own day and its note marks it there. Only an end that moved the total breaks the line (`movingBreaks`: the account held a balance at the stretch's start); one at zero is bridged as any other day.
- **Days known short.** When an assumed closure is lifted because the account came back, the days saved while it was assumed are short of it. The real layer keeps them as written; the entry keeps them as a missing window (`missed`), `getHistory` leaves their points out on read (`shortDays`), so they are bridged like days with nothing recorded, and a note on the timeline says why.
- **Links.** An end set on any id an account has had applies to all of them through the links that apply (`effectiveLifecycle`), so it survives a re-link: the current id's own entry wins, then the newest. Reopening clears every id's entry.
- **Everywhere it counts**: the dashboard's payload (and with it the forecast, allocation, the FI figures and the Plan's inputs), transactions from the end day on (`lib/transactions.ts` displayRows and `lib/activity.ts`, so spending, budgets and group budgets, and the API's sums leave them out and keep the rows before), allocation over time, sharing (shown as ended from its day, `lib/sharing.ts`), the read-only API (`lifecycle` on each account, `lib/api-read.ts`), reports, and the data download.
- **Readers that keep the rows.** `keepEnded` on `assembleBankRows` and `finishActivity` keeps an ended account's rows from its end day on, for two readers. A report (`lib/report/read.ts`) leaves them out itself, by the same rule and the same view of the ends (`assembleBankRows` returns the `lifecycle` it read, through the links the hidden set was read by), and so can say what it left out: each account whose end the period has something to say of, with how many of its rows are in Nya and not counted, and as gaps an assumed closure, an untracked account (still the person's) and a missing window (`lib/report/build.ts`, ENDED ACCOUNTS); its totals stay the Activity tab's, which `test/lifecycle-reports.test.ts` holds to the Activity tab's own route and the API. A category's uses, before it can be deleted (`lib/category-usage.ts`), count what is stored, as they count a hidden account's: such a row is still filed under the category, and is back if the account is reopened.
- **Strict.** Every reader that counts reads the store strictly: an entry that can't be read fails the read, 409 with its id, rather than count an account the person closed. On the dashboard that 409 carries `repair`, and the Accounts tab offers to remove only damaged entries once confirmed (`POST /api/account-lifecycle` `{ "action": "repair", "confirm": true }`); unrecognised ones are only named. Notes are read with a report: the ones that can't be read are named and the rest shown.
- **Detection, with vanished and last known.** `lib/vanished.ts` notices an account missing from a healthy answer (`unconfirmed_missing`, which keeps the snapshot gate shut). `lib/lifecycle-questions.ts` holds it at its last known balance for display only (marked `stale` and `held`, never recorded, as `lib/last-known.ts` recovers a failed institution) and asks. Unanswered after the vanished guard's three days, the outcome is recorded as an assumed closure, from the day after it was last measured, in the lifecycle store only, and the gate reopens; the account reappearing lifts it. Only an end, or a "Still open" about it going missing given within `STILL_OPEN_HOLD_DAYS` (two weeks), settles it short of that: an answer to another question never lets a missing account be accepted with no end recorded. A "Still open" that has lapsed is asked again, with a grace window of its own. A balance at zero for four weeks with no transaction since asks too, and holds nothing, since a zero moves no total whichever way it is answered; so does a closed or left account its bank still returns once its balance moves from `seen` or a transaction posts after it (`askAboutReportedEnds`, a copy of the row in `ended_reported`, counted in nothing). The module headers say why.
- **Writes** go through `app/api/account-lifecycle`, one account per request, under the links lock, clearing both cached payloads, and write the account's auto note best effort. Ending the last open account of a Plaid connection answers `remove_connection`, and the dashboard asks whether to remove it. Reopening an account its bank no longer returns (no live list names it, its connection is still stored) records "Still open" instead of deleting the end (`reopenMissing`), so it is held and asked about rather than left nowhere. Forgetting an earlier account (`lib/links.ts`) takes its entry and Nya's notes on it, and is refused while its balances after its end are what keeps it out of past totals.

### Holdings history

Plaid serves an account's current holdings and two years of investment transactions, but never past holdings, and the transactions carry no prices. So what each investment account held over time, which allocation over time is built on (`lib/allocation/series.ts`, `POST /api/allocation-history`, which joins each recorded day to the balances measured beside it, `lib/history.ts` readMeasuredBalances) and returns will be, exists only from the day Nya starts saving it, and a day it misses can never be filled in. `lib/holdings-history.ts` saves it.

- **What is recorded**: each position of each investment account, with its security (Plaid's security id, ticker, name, type and cash-equivalent flag), quantity, the institution's price and the day that price was current (when the institution says), value, cost basis and currency. An investment account the holdings answer lists with no positions is recorded with none, which is not a claim that it held nothing: money an institution does not list as a position (cash, often) has none, and the balance recorded beside it says what the account was worth. That list is the holdings answer's own, never the balance call's, so an empty day always means the answer spoke for the account. Only an account the holdings answer lists as an investment account, and the balance call doesn't give another type, has positions recorded, so an account of another type never has any: forgetting one doesn't read holdings records (see Forgetting below).
- **Only a whole answer**: a recorded day is never corrected, so an answer that breaks Plaid's schema is never recorded as a whole one. With no list of holdings, nothing is recorded for that institution; a holding naming no account could be any account's, so nothing is either; an account with a holding naming no security is left out of that day, and the institution's other accounts are recorded.
- **When**: on every clean fetch, through the same `recordFetch` as the net-worth snapshot, so by the nightly cron and by every live load. Only an institution whose holdings call answered in that same fetch is recorded: never one whose fetch failed, and never balances recovered from an earlier snapshot. An institution short an account still records the accounts it returned, as their balances are. Hidden accounts are recorded like every other; hiding is applied when it is read.
- **Days**: keyed by UTC day, like the net-worth layer, and each account's latest observation of a day wins, whichever write lands last.
- **Never in the snapshot's way**: it runs beside the net-worth write and never throws. A failed write is logged and counted (`holdings_failed`, on the day's outcome in the cron's report and in `GET /api/snapshot-runs`), never part of whether the day was recorded. A day recorded with `holdings_failed` is not finished: the catch-up run, two hours later, runs it again for its positions (the fetch costs nothing extra, since Plaid bills holdings per Item per month), and a worse outcome that time leaves the day's record as it was.
- **Stored** through the storage seam: one compressed, encrypted value per month (`holdings:history`) under a random id, since a month is content and a map store's ids are plaintext, and a small index (`holdings:history:index`) of which id holds which month and the first and last day (and the moments behind them) each account was recorded on. Within a month each security is described once, as last seen that month, and positions name it by number rather than by Plaid's 37-character id, which keeps a month small: a realistic portfolio (4 accounts, 60 positions, every day of a 31-day month) stores about 48,000 characters, about 0.6% of the 8 MiB ceiling, and 1,000 positions about 1,330,000 (16%). A month that would cross the ceiling, at about 6,000 positions held every day, is refused whole and loudly, never trimmed, and the seam warns in the log past 60% of it. `GET /api/storage-usage` reports the months together and the largest of them against the ceiling (`stores`, as `holdings:history`). The stored shape is closed: a field this version does not know, at any level, makes the value unrecognised, so a version rolled back to never rewrites a month without what a later one added. The price is paid on a rollback: rolled back past a release that added a field, this version stops recording into the months that release wrote (and range reads of them answer 409) until that release is back, and if the field is in the index, it stops recording altogether and every investment account's forget with it. So a new field ships in two releases, first one that reads it and then one that writes it, and a rollback always lands on a release that can read what was written.
- **The index is bookkeeping**: every month names itself, so the index can always be derived from the months. If it is missing while months remain (deleted by hand, say), the next recording derives it before it claims anything, so no month is stored twice and every recorded day stays readable (unless a month this version does not recognise is among them: that could be any month, so nothing is claimed around it). Until then nothing says which month is which, so every read answers 409 with `index_missing`, never an empty history (or names the month it doesn't recognise), and the line under the chart says the history can't be read, never that nothing was recorded, and offers the repair. If its bytes are damaged, recording stops, since it is read strictly; the line under the chart says so and offers a repair. Once the person confirms (`POST /api/holdings-history` with `{ "action": "repair", "confirm": true }`), the repair puts an index derived from the months in place of the damaged bytes in one compare-and-set (`MapStore.replaceUnreadable`), which writes only over the damaged bytes it has just read: never over an index that reads, and never over or around a record this version does not recognise. A missing index is derived the same way. A damaged month is left where it is and counted.
- **Without a master key**: `MASTER_KEY` is recommended, not required ([deployment.md](deployment.md#3-environment-variables)), and without it every value is under `k0`, which does not commit to its key. So the seam can't tell damaged bytes there from a replaced `PLAID_ENCRYPTION_KEY`, and a value under `k0` that fails to decrypt is treated as the deployment's problem, never the data's (`lib/repo.ts`). For holdings history that turns a damaged month or index into a server error, not a 409: reads fail, the line under the chart says nothing at all (no notice, no repair), recording stops with only the log and `holdings_failed` to say so, and an investment account's forget fails. With `MASTER_KEY` set, new values are under data keys, which do commit, and damage is told apart and handled as above ([operations.md](operations.md#turning-on-the-master-key)).
- **What didn't come**: the live payload marks an investment account whose positions this load's holdings call didn't answer for (`holdings_unanswered` on the account, `lib/networth.ts` markUnanswered: the call failed this time, or its answer left the account out; never for a connection that offers no positions at all), so the allocation counts its balance as unclassified rather than as an account that lists none. Over time, a day with a balance measured for an account but no answer recorded for its holdings is read the same way.
- **Read** strictly, by `GET /api/holdings-history?from=&to=&account_id=&include_hidden=1`: each recorded day's positions, each with its security's description, at most 92 days at a time. Account links are followed as the balance chart follows them, so a re-linked account's positions continue under its current id, and hidden accounts are left out unless asked. The index is read once per request, so the days and when recording began agree; the same read gives each account's first and last recorded day under its current id, so allocation over time can name an account missing from a day, and say since when. An answer is bounded by its own size, 4,000,000 bytes measured on the answer (inside the platform's 4.5 MB), however long the securities' names; a range over it is refused, never cut short. `summary=1` reads only the index, for the line under an investment account's chart: "Holdings recorded since" a date while recording is current, "from" and "to" once it has stopped, on the viewer's own days (from the moments the index keeps; a UTC day where none is known, labelled as one), and never "daily", since a day can be missed. Anything stored that can't be read answers 409, never an empty history, with `repairable` when it is the index alone, damaged or missing beside the months (`index_missing`).
- **Forgetting** an earlier account walks the store's own entries, so it reaches a month the index does not name, and removes the account's positions from each month that holds them (and any security only it held), one month at a time, so a forget that stops part way is finished by running it again. A damaged entry, the index's included, holds nothing anyone can read: it is left as it is and reported. An entry this version does not recognise stops the forget before anything is changed, but only for an account that could be in it (one a month or the index records, or any account while the index can't be used: damaged, unrecognised, or missing beside a month that can't be read, since it could note any). An account known not to be an investment account never had positions, so its forget does not read holdings records at all, and nothing in them, not even a record no one can read, holds it back. The account-links route answers the seam's refusals in the seam's words (409 for unreadable records or a month that kept changing, 413 for one too large to save). Deleting an account deletes both stores with the rest of its container, and exports, restores and the re-encryption pass carry them like every other key. The months are in the person's own download of their data (`holdings:history`, see [data-export.md](data-export.md#holdingshistory)); the index, which only says where each month is and dates the months hold, is not.

## Exchange rates

A person can choose a home currency, and their totals are then shown in it, converted at the European Central Bank's euro reference rates or at rates of their own ([features.md](features.md#a-home-currency)). Balances convert by currency (`lib/fx/net-worth.ts`): Home's total, its change and its chart, a mixed institution's total and connection health's share of net worth, and the API's `base` and `to_base` fields. Totals of transactions convert through one seam, `totalsIn` (`lib/fx/totals.ts`): each row in another currency becomes a copy at its own day's rate, rounded once, saying what it was, a row with no rate stays as it is so the spending rules leave it out and name it as they always have, and nothing else on a row changes, so transfers, exclusions, splits and groups count as before; every reader lists the rows as they are and sums the copies. The Activity tab, Insights, the Budgets tab (into the budgets' own currency), the Plan (into its own), reports, the API's `base`, the weekly summary and shares read through it, and the forecast, the calendar and recurring totals convert at the newest rates. The page gets its rates with its transactions (`/api/transactions` `fx`, read after the cache: `lib/fx/read.ts readFlowFx`, for the rows' currencies and the person's accounts'), so the browser converts exactly as the server does. What a person typed (budgets, the Plan's figures, the forecast's warning) is never relabelled: those keep their currency and the rest converts into it. `test/currency-callers.test.ts` lists each reader that still picks a currency itself, by function, with its reason.

**Only the person chooses.** Nya never writes a home currency on its own, on any path (`lib/fx/settings.ts`): until the person picks one, nothing converts and every figure is what it was before. A default worked out from the accounts would move every total whenever a bank failed to answer, an account was hidden or accounts were linked in another order. Someone whose accounts and transactions are in more than one currency is offered the choice on Home, suggesting the currency their budgets are read in; only their confirmation writes it.

**The rates.** `/api/fx/fetch`, a cron of its own (16:30 UTC: after the ECB's 16:00 CET in winter and in summer, and apart from the snapshots and the backup), downloads the ECB's whole history file, `eurofxref-hist.zip`, reads it with the shared bounded zip reader (`lib/zip.ts`, which checks each entry's sizes and CRC-32) and a strict parser (`lib/fx/ecb-parse.ts`: anything unexpected refuses the whole file), and writes it into one public store, `fx:ecb` (`lib/fx/ecb-store.ts`): per currency and year the rates as published, never rounded; per year the days the ECB published, the calendar that tells "published without this currency" from "didn't publish"; the newest publication whole; and the last run. Every currency the ECB publishes is kept, never only those someone holds, which would say something about the people on this copy. Each year is one atomic HSET, written only when it is missing or can still change (the current year, and the year before during January), and only when its days are a superset of the stored year's; the newest publication never moves back, and a file older than what is stored is refused. A field that can't be used (damaged, or not the shape its id holds) reads as no rate on its days, said as rates Nya doesn't have and named in the notes, never as rates the ECB didn't publish; the next run writes it again. A calendar or the newest publication goes with its year's write, and after tonight's writes the run checks the past years against the file, one read of a year's series at a time, from a different year each night, until the writes' deadline: a year whose stored series are missing, can't be used or differ from the file's is written again whole, and the record names what was mended (`mended`). Upstash doesn't time a request out on its own and Vercel ends the function at its limit with nothing after, so every call is raced against what is left of the run (48 seconds, in the route's 60): the reads of what is stored, the download (20 seconds at most, and aborted), each year's write, with the writes stopping between years at their deadline. A call over its time is an ordinary failure naming the step, recorded (`fetch`) and answered (500, so the cron's log shows it); the record has six seconds kept for it and is raced too, so even one that never lands is logged and answered in time. Readers never fetch: they only read the store. Rates are stale when the last fetch that worked was over 30 hours ago or the newest publication is over 5 days old, and every converted figure then says so.

**On read, never stored.** Conversion happens on every read, after the caches (`/api/net-worth` adds `base` as it adds connection health), so a change of home currency or of a rate needs no cache cleared, and nothing converted is ever written: the snapshot records the unconverted sum as before, and the cache keeps the history's split by currency, unconverted (`history_split`, a regrouping of stored numbers, never sent). The arithmetic (`lib/fx/rates.ts`, `lib/fx/decimal.ts`) is exact: rates stay the decimal strings the ECB published, an amount is read as the decimal it is, and products and quotients are exact fractions of `BigInt`s, rounded once, half away from zero, to the target currency's minor unit (8 places for an unofficial code such as BTC), so the browser, the server and the tests agree on every half cent. A cross rate is worked out through the euro each time, never stored or rounded.

**A day without a rate.** An amount on a day takes the newest publication on or before it (a weekend or a TARGET holiday the last working day's; the ECB's longest gap is 5 days, so never more than 4 days back), and its currency must be in that publication: a currency the ECB stopped publishing is never carried forward. A day after the newest publication takes it. A day in a year's first week reads the year before too. A currency with no rate is left out and named, never guessed, and a day in a year Nya hasn't fetched is said as rates Nya doesn't have yet.

**Balances by currency.** A total of balances adds each currency's signed balances, then converts each subtotal once (`balancesIn` in `lib/fx/net-worth.ts`): the hero, the API's `base.net_worth`, each day of the chart, an institution's mixed total. An account's own `to_base` converts it alone, so the parts of a total can be a cent per currency away from it. A day of history converts from its split by currency (`getHistoryWithSplit` in `lib/history.ts`): what each account in another currency than the main one put into the point, by the rule hiding takes one out by, from the per-account maps behind it, and the main currency the rest. Which accounts those are is known from the accounts listed, those that ended (their lifecycle entry keeps the currency) and the account directory (which keeps each account's currency from this release on), by every id each has had, through the links (`lib/fx/known-accounts.ts`); an account nothing records a currency for is counted in the main one, as before, and the chart's note says so. A point whose split can't be told is not drawn; one whose main currency has no rate that day is not drawn as a fall. Home's change over recent days is read from the converted chart, so rate moves are in it, and says how much: the earlier day's parts at the later day's rates, less at their own, when more than rounding.

**Own rates.** "1 BTC = 61,000 USD", from a day or for every day, kept in the person's encrypted settings, one per currency, wins over the ECB's on the days it applies, through the ECB's rate for its quote that day: one hop only, so rates can't loop.

**Rollback.** The release before reads none of it: not `currency-settings`, not `fx:ecb`, and not `history_split` in a cached payload (an extra field it ignores). The account directory's `currency` is an optional field it keeps reading and drops when it rewrites an entry. A Plaid account with only an unofficial currency code (a cryptocurrency) says that currency from this release on, in the remembered accounts and the lifecycle entries too, which the release before reads as any other currency: its net worth then shows the mix it always had, and its API's `totals` keeps the entry for that code.

## Import pipeline

Files a bank exports come in through one pipeline (`lib/import/`), so that every other way in (importing into a linked account, [below](#importing-into-a-linked-account); a SimpleFIN connector; another app's export) adds a stage or a parser rather than a second import path:

```
parse  ->  RawRecord[]  ->  normalize  ->  match  ->  commit
```

- **Parse**: one parser per source (`ofx.ts`, `csv.ts`, `qif.ts`), each producing `RawRecord`s (`record.ts`): `source`, `source_id` where the source has its own id (OFX's FITID), `date`, `posted_date`, `amount` in Plaid's sign (positive is money out, whatever the source's), `description`, and `raw`, the record as the source had it; optionally `currency`, `category`, `note`, `transaction_code` (Plaid's code, where the source says what a transaction was outright: OFX's TRNTYPE ATM is `atm`) and the `line` it starts on. A record a parser can't read is a problem with its line and reason, never dropped silently, and where a parser had to repair a file's structure (an OFX aggregate left without its end tag), the preview says so. `read.ts` runs the right parser and says what it needs answered first (which statement, which columns, the order of the dates, which the file's own dates settle whenever they can); `text.ts` reads a file's bytes as text (UTF-8, UTF-16, Windows-1252) and tells its format from what it holds.
- **Normalize** (`normalize.ts`): each record as a manual transaction's fields, checked by the rules a typed one meets (`lib/manual-txn-input.ts`), or a problem; its text cleaned; and the content key (day, currency, amount in minor units, description lower-cased to letters and digits): a source without ids keeps it as the row's `source_id`, and one with ids keeps it hashed short as the row's `source_key`.
- **Match** (`match.ts`): each row new, already stored, repeated within the file, or a conflict. In that order: by id exactly (the same FITID on exactly the version that was imported, or on a row that says the same), by content key against any stored row not taken (each matching one row at most, so two identical coffees stay two, and a renumbered FITID is found by what the row says), and only then by id within a tolerance (the same amount, dated within five days: a pending charge that posted later), so a FITID a bank reused can't take a stored row from the row that really is it. A row whose FITID is on a stored row that is another transaction is a conflict the person decides (import as new, replace, skip), with a suggestion only when nothing but the id is alike. Exact, never fuzzy.
- **Commit** (`commit.ts`), the only stage that touches storage: the raw records into the `imports` store and their summary into `import-summaries`, then the new rows into the account's book (`lib/manual-txns.ts`) in one compare-and-set, with the conflicts' choices applied, matched again against the book as it is at that moment, and refused whole past the size ceiling or while a conflict has no answer. Undo, the list of imports, the offer of a statement's balance and forgetting a deleted account's imports are here too. Undo takes out the rows an import added, except those a later import relied on (found already there, replaced, or skipped as its own version), which it hands to the earliest such import, and puts back the rows it replaced as they were.

Parse, normalize and match are pure and safe in the browser. The import sheet (`components/ImportSheet.tsx`) runs them on the file to ask its questions and show how its first rows read; the route (`app/api/import`) runs them again on the file it receives, so what is previewed and imported is the server's reading. Nothing is staged between the preview and the import: the file is sent twice, and the import matches against the account afresh.

The stores, on the storage seam (`lib/import/store.ts`): `imports`, one compressed entry per import under a random id (the raw records with what became of each, the format, the account, when, how it was read, and the counts), read whole only to undo an import and for the download; `import-summaries`, one small entry per import under the same id, written and removed with it, which the list of imports reads, so opening the sheet never decompresses a file's records; `import-settings`, per manual account, how its last file was read and its OFX statement's account (masked); and `import-requests` and `import-reads`, the hourly counts of import requests and of reads of the list. The entries and the settings are in the person's [download](data-export.md#imports).

Plugging in:

- **Another format or connector** is a parser producing `RawRecord`s and a `SourceKind`. If its ids identify a transaction exactly (SimpleFIN's, another app's export with ids), its source goes in `ID_SOURCES` (`normalize.ts`), and matching uses them; without ids it falls back to the content key. A connector (SimpleFIN's, [below](#connectors)) uses parse and normalize, and commits by its ids alone: a fetched window has no preview and no conflicts to settle.
- **Importing into a linked account** keeps parse, normalize and the exact match against the account's own earlier imports, and adds a match against the bank's rows, a review, a commit of its own and a walk of the estimated history ([below](#importing-into-a-linked-account)).

Limits: a file of 3 MB and 10,000 transactions, sized for Vercel's 4.5 MB limit on a function's request body with the form around it (the route refuses a declared or actual body over 3 MB and 64 KB before reading it as a form); the account book's own ceiling (`MAX_TXN_BLOB_CHARS`); 1,000 characters a field; 32 levels of nesting in an OFX file, so a hostile one can't exhaust the stack; and 200 columns in a CSV file and 50 statements or accounts in an OFX or QIF file, refused before anything is built from them, so no answer (a question's column names and first rows are cut short too, and a preview lists at most 200 problems and 200 conflicts) comes near Vercel's 4.5 MB limit on a response, and the sheet never builds a list that would freeze a phone.

An import into a manual account never writes the history layer (`lib/history.ts`). It adds transactions; a statement's balance is set only when the person ticks the offer, and only from a statement dated today or yesterday, as the account's **Update** form sets one; the estimated history holds manual accounts flat.

### Importing into a linked account

Importing years of a linked (Plaid) account's history from its bank's files (#52; `lib/history-import/`, the route `app/api/history-import`, the sheet `components/HistoryImportSheet.tsx`) reads the file as a manual account's import does, matches it exactly against the account's own earlier imports (`lib/import/match.ts`), and adds what a file overlapping the bank's synced rows needs. How it looks to the person is in [features.md](features.md#importing-history-into-a-linked-account).

- **Where the rows live.** Not in the bank's transaction store (`txns:<connection>`): that is Plaid's, rewritten by every sync, refused whole past the ceiling, and deleted on disconnect, so rows kept there would be lost, or fail every sync of a large institution. Each account's imported rows are a book of their own on the storage seam, `imported-transactions`, one compressed value per Plaid account id, in the shape of a manual account's book, kept past a disconnect as balance history is. Readers follow account links (`lib/link-core.ts`), so an account's rows are the books of every id it has had; forgetting the earlier account deletes its book (`forgetImportedHistory`, from `forgetEarlierAccount` in `lib/links.ts`). Each row carries `source` (`import:ofx`, `import:csv`, `import:qif`), `source_id` (the FITID, or the content key), an OFX row's `source_key`, `import_id`, and what the review decided: `same_as`, the bank's row it is, by `bankKey` (the posting day, the amount in thousandths and the bank's own descriptor normalized, which survive a re-link where Plaid's ids don't), `same_as_row`, the earlier import's row it is, by id, or `distinct_from`, the bank rows the person said it is not (pairs never made again, the bank rows left free). A book holds some 90,000 rows; four years of a busy account (about 7,000) is under a tenth of the ceiling, so no overflow is needed. Ids are `imported-txn:` and a random id, which the pruning of categories and exclusions (`lib/overrides.ts`, `lib/txn-annotations.ts`) passes over: what is said about an imported row goes with the row (undo, forget), not with a bank's sync.
- **The other stores.** `history-imports`, one compressed entry per import (`history-import:` and a random id): the file's records with `raw` always, each with what became of it, the row it became and, for a duplicate, its `twin` (the bank's row or an earlier import's) with the proposal answered, the format, the account, the period it covers (`covers`, with `whole` when the person said the lines that couldn't be read aren't transactions), the bank's earliest row when it was reviewed (`bank_from`), how it was read and the counts (`already`: rows kept as an earlier import's); read whole only to undo an import and for the download. `history-import-summaries`, the same without the records, which the list of imports and the walk read. `imported-twins`, one compressed entry per connection, by its Plaid Item id: which of its bank rows stood for which imported row (each imported row's id to the bank row's transaction id, one to one), kept by the sync (below), and deleted with its connection. `carried-imported-twins`, one entry per earlier account, by its account id: a disconnected connection's pairs, each imported row's id to the content key its bank row had, for a re-link (below). `imported-history-walk`, the walk's bookkeeping (below). How a file was read is kept per account in `import-settings`, and requests count against `import-requests` and `import-reads`, shared with manual accounts' imports.
- **Matching** (`match.ts`, pure). A file row and a transaction the account already counts (a posted bank row under any id it has had, or a counted row an earlier import kept: `knownOf` in `plan.ts`) are a pair when the amount is exactly the same, the currency is the same (or the bank's row has none) and their days are at most `MATCH_DAYS` (5) apart. The description, a Dice similarity over its words, only breaks ties and moves the confidence: high within a day, or within three days and alike; medium within three days, or alike; low otherwise. Pairing (`pairUp`) is one to one, per amount: a maximum matching (the most pairs), then the fewest days apart in all, then the most alike, found by a dynamic program over pairings that never cross in date order, a run at a time (rows more than `MATCH_DAYS` apart can't pair), with a greedy fallback (still the most pairs) past `DP_LIMIT` cells. Where the plan says which pairs cross an edge, it pairs those inside both sides' days first, and those across an edge only among the rows and twins left over, so a pair across an edge never displaces one inside, and a same-day pair is always inside. A pending bank row never pairs. A pair across an edge (`crossesEdge`: the row before the bank's earliest posted row, or the other row outside the period its file covers) is the same only through a posting lag, which the dates of rows of one amount can't tell from none: the plan makes it low and says why (`edge`), and never makes it for an OFX file against a row dated by posting; a read never makes it at all.
- **The plan** (`plan.ts`, pure): the exact matches against earlier imports first; then proposals against what the account counts, each once: every posted bank row (named by the earlier import's row that already stands on it, where one does, so two files never both claim it) and every counted row of an earlier import (`already` when answered the same, kept as `same_as_row`), with a row a bank row was kept as standing for at another amount offered at its own amount too, so another file's copy of it is found already there, answered `same` by default for high and medium confidence, and not at all for low. Its `review` string, every row's content, outcome and proposal and the period covered, is hashed into the digest the client sends back with its answers (`reviewDigest`).
- **The commit** (`commit.ts`): the entry and its summary, then the rows in one `updateMany` compare-and-set over the account's books, which plans again from the bank's rows and the books as they are at that moment and refuses unless the digest is the reviewed one (`ReviewChangedError`, 409) and every proposal has an answer (`UnansweredError`, 409); past the ceiling it is refused whole (413). A refused commit takes its entry back out. Nothing is staged between the review and the import: the file is sent twice.
- **Which rows count** (`settle`, `match.ts`), worked out on every read: first the pairs kept once made (`twins`, below), each a bank row by its id, while that posted row is there, whatever its amount, day or words say now, as a duplicate's twin or as the row superseding it; then a duplicate STANDS for its twin only while the twin is there (a posted bank row with its key, one to one, earlier imports first; an earlier import's row that is kept); every other row, and a duplicate whose twin is gone, counts unless a free posted bank row pairs with it by the same matching, an import at a time in the order they were made, never across an edge and never as a pair the person said is not one: then that bank row supersedes it. A superseded or standing row stays in its book, uncounted, so the bank removing its row, a re-link whose window starts later, or an undo brings it back exactly. For what is shown (`pending`), a pending bank row stands in for a row like it until it posts; the walk takes posted rows only. `countedRows` (`read.ts`) is the one place that says which rows count, for the read layer, the walk, the backfill, sharing and the list of imports (`rows_now`, `duplicates_now`, `superseded_now`, `returned_now`), each with the account's connection's kept pairs, read strictly beside its bank rows (a connection's that can't be read keeps its accounts' imported rows out, with a note, as when its bank rows can't be); the review and its commit read them in the account's context, and the download applies the same `settle` to the rows in the file, with its `imported-twins` part (an entry listed under problems pairs nothing there, and the file says so).
- **Kept once made** (`twins.ts`). Plaid keeps a transaction's id when it modifies it, so a pair worked out again from a new amount (a duplicate's key holds the amount too) would let the imported row count beside the bank's. A pair the rule made holds by the rule while its bank row says what it said, and only the sync changes the bank's rows (`lib/transactions.ts`), so the sync that changes one keeps it: when it removes a posted row, or changes what matching reads of one (its account, day, amount, currency, words or pending state: `changedRows`), `keepImportedTwins` works out `settle` on the rows as they were, before it saves them, with the pairs already kept, and keeps every bank row that stood for an imported row at the Item's accounts, by its id, so a row it modifies is kept as it stood. It reads only those accounts' books, under every id they have had (`readImported`'s `bookIds`, by `getMany`), the summaries of the imports their rows came from and the Item's own pairs; a sync that only adds rows, or changes only what matching doesn't read, reads none of them. It drops a pair whose bank row the new rows don't hold (the bank removed it: the imported row is back as before) and one whose imported row none of those books holds once every one of them was read (an undo, a forget; it pairs nothing meanwhile). It keeps nothing when what decides the rule's pairs at the Item's accounts can't be read (the links, the Item's accounts, an end of one of them, a summary of one of their imports; what can't be read elsewhere doesn't stop it), and never fails the sync: a failure leaves the pairs as they were, logged. Reads never write it. A pair made before this was kept is worked out from the amounts until a sync changes its bank row; one the bank changed before then is lost to it. **A pending row that posts** is the same transaction under a new id (Plaid's `pending_transaction_id` names the pending one), dated by its posting, often after the last day of the imported row's file (an edge the rule never pairs across), and maybe at another amount (a tip): so a sync that brings such a posted row, or removes the pending one it names (`replacedPending`), also works `settle` out with `pending: true` on the rows as they were, and keeps each imported row the replaced pending row stood in for (`pendingStood`) as a pair under the posted row's id, which then takes its place at step 0 whatever its day or amount, as the pending row's approval moves to it (`carryApprovalsToPosted`). Only that sync can: once the pending row is gone, nothing says what it stood in for, so one that posted before this release counts beside the bank's. SimpleFIN keeps no pending rows and its accounts take no history import, so this is Plaid's alone. **Across a re-link** the pairs go by content, as categories and what was said about transactions do: `disconnectItem` records each kept pair's bank row by its content key (`retireImportedTwins`: the account, the day, the amount in cents, the bank's descriptor) under that row's account in `carried-imported-twins`, then deletes the Item's entry; once the earlier account is linked to the re-added one, every sync of the re-added Item pairs each such imported row with its posted row that has exactly that key under the current id (as the row was before the sync, else as the sync brings it), one to one, unless either is paired already, and drops each carried pair it then keeps (`carriedPairs`). One whose row hasn't come waits; one the bank changed again meanwhile is never paired by anything looser. Every sync reads that store once (one small hash, almost always empty), and the links only when it holds something; forgetting the earlier account deletes its entry. A bank row standing for an imported row at another amount carries that amount (`imported_amount`, from `importedForActivity`'s `changed`), which the Activity tab says; a split carried from the imported row shows the difference as its remainder (`lib/split-rows.ts`), and `lib/txn-lookup.ts` answers the bank row's amount for the imported id, which an edit of the split adds up to.
- **Reading.** `importedForActivity` (`read.ts`) is part of the banks' part of the read layer (`assembleBankRows` in `lib/activity.ts`), matched once the syncs are done, against the rows they wrote (`stored`, asked for with `withStored`), so a bank row a sync just brought supersedes in that very answer, and no connection's rows are decoded twice. The person's categories and merchant names apply to imported rows as to the bank's, and their exclusions, tags, notes and rules in `finishActivity` (`lib/txn-layers.ts`, as for any row: a note kept beside the row, as a bank row's, over the file's own); a bank row standing for imported rows (`represents`, earlier imports first) takes a category chosen for one there (`categoriesFromImports`), and names them (`stands_for`), so `applyLayers` lays what else was said about them (an exclusion or an include, tags, a note) under what is said on the bank row itself, and `expandSplitsAndGroups` gives it their split and their places in groups ([Splits and groups](#splits-and-groups)). The last `LOOKBACK_DAYS` as rows, older ones back to `RECURRING_LOOKBACK_DAYS` as recurring detection's history; for a report, every one from its period's first day on (`since`, as the bank's part reads its rows), and the days each account's imports cover (`importedCoverage`), so a period the files reach isn't called short (`lib/report/build.ts` IMPORTED), each account through the day before its end, when it ended (`throughOf`), and with those that ended that its connection no longer reports (`coveredAccountsOf`); the rule is `lib/history-import/coverage.ts`, which the Activity tab's month notes and the cash flow chart (for a connection whose transactions don't come in, `lib/history-import/without-files.ts`), the months budget rollover counts and a goal's pace (`lib/goal-flows.ts`: an account's rows begin as far back as its files reach in one run to the bank's own, or, with no bank rows at its connection, where the run of its files that reaches the end of the last month averaged begins, the account being paced by its recorded balance without one) follow too. Totals (`countsInTotals`), budgets, recurring bills, the Plan and the API and MCP server read that. Sharing reads `importedForShare`, which shows no tag, note or rule, and the download `importedTransactionsIn` (`lib/user-export.ts`), which gives a bank row what was said about the imported rows it stands for, as the app does, and lays the same layers on the imported rows themselves (`layeredImportedRows`, for the CSV and an OFX statement). An account whose imported rows can't be used (a book, or its connection's accounts, that can't be read) gets a note, never a short list. An account that ended (`lib/lifecycle.ts`) has its rows from its end day on left out as the bank's are, through every id it has had (`endedFrom`, the same `endDays` the bank's part filters by), unless the reader keeps them (`keepEnded`: a report, which counts them as not counted, and a category's uses); the download and an OFX statement keep them. `liveLinkedAccounts` lists, beside the accounts the loads remember, each that ended on a connection still stored that they no longer do (a bank stops returning a closed account), named and typed from its lifecycle entry, so its rows before its end still count; an end that can't be read (or that a later release wrote) is named instead (`endsUnread`), and a book no live account claims that is filed under one of that account's ids is then `unresolved`, as with a connection's accounts that can't be read, so the drawing waits rather than draw without it, and the import route answers 409 rather than call the account unlinked. Importing into an account that ended is allowed: the review warns how many of the rows it adds are dated from its end. The lifecycle's questions read only the bank's own rows and measured balances (`readStoredTxns`, `readMeasuredBalances`), so an imported row never raises or answers one. A connection whose first pull is done and whose history is still on the way (Plaid's `INITIAL_UPDATE_COMPLETE`) is marked `history_pending` in its store until Plaid says the history is complete; the review and the list say so.
- **Undo** (`undoHistoryImport`): the import's rows out of every book of the account, but those a later import relied on (found already there), which are handed to that import; the categories and exclusions on them forgotten; the entry and summary removed; the walk drawn again (and the backfill first, when a row's day is after the chart's earliest estimated point). Forgetting the earlier account hands rows a later import into another account relied on to that import the same way (`forgetImportedHistory`).

#### The walk through imported rows

The estimated history is extended back through imported rows (`walk.ts`, pure, and `extend.ts`) after the backfill (`app/api/backfill`), never instead of it:

- **The backfill first.** The backfill walks the counted imported rows of the cash accounts it walks, dated in its own window, in each account's currency, and only through the run of covered days that reaches today (`importedFlowsForBackfill`, with the drawing's own covered ranges: never across a day nothing covers, so a file a hole cuts off is walked nowhere, and is a gap), so its earliest point holds them: a card whose bank gives Plaid 90 days beside a bank that gives a year is no longer held flat across imported rows. A change to which of them count with a day after that point (an import, an undo) or any link, unlink or forget (`importedRowsChanged`, `linksChanged`) clears the done flag so it runs again before the drawing, and bumps `rows`; a backfill during which `rows` changed doesn't call itself done.
- The **anchor** is the chart's earliest point (`readEarliestPoint` in `lib/history.ts`), leaving out what an earlier drawing drew. Only depository and credit accounts are walked, through their flows up to the anchor: the bank's posted rows and the counted imported rows in the account's currency. Each is walked back from its balance at the anchor (a bank account's balance the day before is the day's plus the day's flow; a card's owed amount is the day's less it), and every other account is held at its balance on the anchor day.
- **Covered ranges**: the connection's own period (its earliest posted row to today) and each import's `covers` (its statement's period, its first to last day, or wider where the person said so), but for an import with lines that couldn't be read and no `whole`, or with rows in another currency than the account's: those are `excluded`, with why. An account is walked back from the anchor only through an unbroken run of covered days that holds the anchor and reaches on to today (or only holds it, for a recorded anchor, whose balances were measured that day), and not when the estimate held it flat at the anchor though it moved since (`held-flat`); the first uncovered day stops it, and every import beyond is a gap (the imported range and the uncovered days that cut it off), which the chart names rather than drawing across. At most thirty years (`MAX_EXTENSION_DAYS`).
- **Strict.** A drawing that can't read what it needs (a book, its bank's rows, an import's summary, the links, a connection's accounts, or the end of an account that is live only through it) throws `DrawUnreadableError` having drawn nothing: what was drawn stays, the record stays marked, and `problem` names the accounts for the chart's note.
- **What it writes** (`replaceEstimatedBefore`, `lib/history.ts`): the estimated layer only (`history:net-worth:est`, `history:accounts:est`, and `history:accounts:est:flatd`, the balances held flat on each date, which hidden subtraction reads), only for days before the anchor, and never a day with a recorded point (the recorded days are read strictly first). Doomed totals are deleted before their maps, and maps are written before their totals, the order hidden subtraction is safe against. The real layer (`history:net-worth`, `history:accounts`, `history:accounts:partial`, `snapshot:taken`) is never written, and the tests hold it byte for byte the same across imports, undos and walks.
- **Ends.** The drawing walks an account whatever its end, and what it writes is per account, so `getHistory` subtracts an account that ended from its end day on (`lib/lifecycle.ts`) as it does a measured point. The note (`importedHistoryView`) and the API's `from_imports` (`importedStretch`) take the ends as the chart does: net worth's stretch stops at an account's end, an account that ended before the oldest day drawn of it, or an import not drawn that starts from its end, isn't named, and one that ended before its bank's own rows begin is said to follow imported rows only. One account's own history keeps every day.
- **Its state** (`imported-history-walk`): a `generation` that every change bumps (an import, an undo, a link, an unlink, a forget, a backfill) and the generation last drawn (`built`), `rows` (the changes that asked the backfill to run again), the anchor, the oldest day drawn, the days drawn (`drawn`, so the next drawing clears exactly them, which is what makes an undo exact), each account's reach, where its bank's own rows begin (`bank_from`, so the note and the API's `from_imports` say which stretch follows the bank's rows and which the imported ones), gaps, imports not used and why one isn't walked, and `problem`. A drawing overtaken by a change records itself stale. The backfill gives up the days it rewrites before writing them (`yieldToBackfill`) and draws again after; the import and undo draw at once when the backfill has run. While a drawing is due the net-worth route answers `backfill_stale`, so the client runs the backfill, which draws it; and it sends the view the chart's note is made from (`imported_history`, `lib/history-import/view.ts`).

### Another app's export

Switching from Monarch, YNAB, Lunch Money, Actual Budget or ZeroSum (M2; `lib/import/apps/`, `lib/migration/`, the route `app/api/migration`, the sheet `components/MigrationSheet.tsx`) is a parser and a planner on the same pipeline, not a third import path. How it looks to the person is in [features.md](features.md#switching-from-another-app).

- **Reading** (`lib/import/apps/`, pure but for the file's bytes). One module per app (`monarch.ts`, `ynab.ts`, `lunchmoney.ts`, `actual.ts`, `zerosum.ts`) knows its columns (by aliases of each role: date, account, payee, amount or outflow and inflow, category and group, notes, tags, currency, flag, a split's parent and id) and reads the table `lib/import/csv.ts` makes of the file (with `max_rows`, since one export holds every account) into `AppTxn`s: the account, the day, the amount in Plaid's sign, the payee, the app's category with its group and kind (income, transfer, or none: `AppCategory`), a transfer to another of the person's accounts (`transfer`), an opening balance (`starting`), the note, the tags, and a split's parts. None of the apps publishes a specification, so each module cites its sources (help pages, Actual's own source, published files) and what they leave unconfirmed. `detect.ts` tells the app from the header (each app's own columns, the most specific first) and proposes the columns for the mapping step, the fallback for a header no module recognises; `read.ts` (`readAppFile`) runs it and says what it needs answered first (which app and columns, the order of the dates), as `lib/import/read.ts` does, and settles the decimal mark, the date order and (for Lunch Money) the sign. `splits.ts` rebuilds split transactions from the marks each app writes (YNAB's memo "Split (1/3)", Actual's "(SPLIT INTO n)" row and "(SPLIT i OF n)" parts, Lunch Money's Parent ID), summing in millionths and checking each rule a split in Nya meets, else keeping the lines as rows with the reason (`SplitReport`). `zip.ts` reads a zip's central directory and inflates one entry with `node:zlib` (stored or deflated only, at most 64 entries and 6 MB an entry, encrypted and ZIP64 refused), and `file.ts` picks the transactions file in it (YNAB's Register, ZeroSum's `transactions.csv`) and says how to export a CSV for Actual's SQLite export (`db.sqlite`), which isn't read: that would need an SQLite reader, a new dependency.
- **Planning** (`lib/migration/plan.ts`, pure). Each of the file's accounts goes where the person says (`AccountChoice`: a new manual account, one they have, a linked one, or nowhere), and until every one is answered the import waits. Each Nya account's rows become `RawRecord`s (source `csv`, so `import:csv` content keys) and go through that account's own import unchanged: `planImport` (`lib/import/commit.ts`) for a manual account, `planHistoryImport` (`lib/history-import/plan.ts`) for a linked one, whose review against the bank's rows is the person's to answer, with the account's pairs kept once made (`twins`, from `readAccountContext`), as the history import's route passes them, so a bank row the bank changed since still stands for the earlier file's row, and the app's copy of that transaction is found as it. A linked account's answers are keyed by the line a row starts on in the file (`MigrationAnswers`), which no other answer can move, and translated to the history plan's row indexes (`byIndex`). Categories are mapped by `lib/migration/categories.ts` (pure): by name or text key to the person's, YNAB's and ZeroSum's money to budget to their income category, else a new category with the app's kind in a group of the app's group name, within `MAX_CATEGORIES`, `MAX_GROUPS` and `NAME_MAX`, and `applyCategoryPlan` makes them with `addGroup` and `addCategory` themselves. A transfer the app marks is filed under the seeded `transfer out` and `transfer in` text keys, an opening balance under `Starting balances` (a transfer category), so `isTransfer` keeps both out of every total. The limits of every store a row touches are checked here, so the review says what blocks it: `MAX_IMPORT_ROWS` an account, `MAX_MANUAL_ACCOUNTS`, `MAX_TAGS` (names cut at `TAG_NAME_MAX`, `MAX_TAGS_PER_TRANSACTION` on one), `MAX_ANNOTATIONS`, `MAX_SPLITS` (each split's parts through `checkParts` in the account's currency). `planDigest` hashes the read, the answers, the mapping, the tags and each account's rows, a manual account's outcomes and a linked account's review (never the answers to its proposals, which the import carries, as the history import's own review leaves them out) into the fingerprint the import must send back; what a block needs counted (what is said beside rows) is counted for either answer, so an answer never moves the fingerprint.
- **What a linked account takes** (`planMigration`'s first pass, before anything is mapped): nothing its bank's own balance and rows already are. The app's opening balances and balance adjustments (`AppTxn.starting`, Monarch's Balance Adjustments too) never come in, so none is walked as money that moved (`importedFlowsForBackfill`, `drawImportedHistory`). Where the account's own transactions already reach (`reached`: the bank's from `bank_from` on, and each earlier import's period), Lunch Money's groups (`grouped`) are left out, a split's lines that weren't rebuilt (`split_of`, from `splits.ts linesOf`) come in as the whole the file gives (Lunch Money's parent row, Actual's own row and total, a complete YNAB run), one row with no parts, or are left out without it, and a rebuilt split Nya can't hold (`holdable`) comes in whole; before that, nothing has them, and they come in as a manual account takes them (a group at its net, a split as its lines). An export that marks no split (`group_key`: Monarch's Original Statement, ZeroSum's and older Actual's payee) has its rows of one account, day and key taken together (`combineUnmarked`) when they add up exactly to one of the account's transactions (`knownOf`, as the account's import plans, and the bank's pending rows) that no row of the file is by itself (each row is first paired with the closest such transaction, each once), and aren't each one, as a split with their categories where it can be held; matched to a pending row, the combined row is retired by it once it posts. Each target's `left_out`, `whole` and `combined` say so in the review. A linked account's rows must be in its bank's currency (a block otherwise), and a new account is in the one most of its rows are in. Whether its bank's rows take the app's category, tags, note and split is the person's (`MigrationAnswers.carry`), and they take only what will show and never what moves a row the person approved (`carry_to`, by each row with a proposal; `moves`, the rows that would give their bank's row anything there; and `carried`, how many go each way, an approved row counted apart when it has tags or a note to give, so the box is offered only while it moves something): a row that is one an earlier file brought, which no bank row stands for (`standsFor` leaves out a row standing for it, so nothing would show what is said on it), carries nothing and that row keeps what it has; one whose bank row holds an approval in the review queue (where `approvalFor` finds one: the row's own id, the pending one's it replaced, or a row imported from a file that it stands for) carries its tags and note, never its category or split. A row it adds whose only look-alike is a pending bank row (`onto_pending`, paired with it as `settle` pairs a pending row that stands in, the closest, one to one, never across an edge) is the same: the posted row takes its place and what is said about it, so it carries by the same rules (the pending row's own approval read too), and otherwise comes in at its total, its parts dropped and its tags not written. All of it is in the fingerprint (which rows a pending row will take the place of always, where each carries while the carry is on), so a pending row or an approval made after the review asks for it again.
- **What it reads** (`lib/migration/targets.ts`): the categories as the app's first load makes them (`ensureTaxonomy`, the one write a review may make), the tags strictly when the file brings some (unreadable is a block, so the person can import without them), the manual and live linked accounts, the links strictly (unreadable: no linked account offered), each chosen manual account's book and each chosen linked account's context (`readAccountContext`, strict: one whose bank rows, earlier imports or kept pairs can't be read is unavailable, with why), for each of those the posted bank row each kept row stands for and the bank rows that hold an approval (`reach`: `readApprovalsForDisplay` over every bank row's id, posted or pending, the pending ids the posted ones replaced, from the context's `pending_from`, and the kept rows' ids, an approval that can't be read counting as one), and, leniently, the ends of the chosen linked accounts, for the review's words (`ends`).
- **The commit** (`lib/migration/commit.ts`, the only part that writes), all of it or none: the entry in `app-imports` first, naming every id it will make (manual accounts, categories, groups, tags and each account's import, whose own entry names its rows; all minted then: `lib/import/commit.ts` and `lib/history-import/commit.ts` take ids from their caller for this, `ids` and `ids_minted`, refusing ids that don't name every row); then the new manual accounts, within the room counted again (`MigrationRoomError`); the categories in one compare-and-set that works the mapping out again and refuses unless it is the one reviewed (`CategoriesChangedError`); the tags in one; each account's import through its own commit, which matches against the account as it is then and, for a linked one, refuses a review that changed (`ReviewChangedError`); then what the rows carry, in batches: tags (and, on a row the bank already has, the app's note) in `transaction-annotations`, split parts in `transaction-splits`, and on such a row the app's category as an override (`setOverrides`, `lib/overrides.ts`), which `categoriesFromImports` gives the bank's row standing for it, each on such a row only as its `carry_to` says. Any failure undoes what was done, as Undo would, before answering. The route answers an import whose id is already stored with what it made (`already`), before comparing the fingerprint, so a request sent twice is made once.
- **Undo** (`undoMigration`): refused while the entry is `importing` and younger than any request may run (`STILL_IMPORTING_MS`, `MigrationBusyError`); then each account's import undone through `undoImport` or `undoHistoryImport`, a linked account's with every id it has had (`sameAccountIds` over the links read strictly, as its own Undo passes them, so a later import made under its new id after a re-link keeps the rows it relied on; links that can't be read refuse it, `MigrationLinksUnreadableError`), one the person already undid on its account skipped; and what it made removed where nothing uses it now: a manual account it made with an empty book, still stamped with the import's start (the person hasn't changed it) and tracked by no goal (`deleteManualAccount`, `lib/manual-account-delete.ts`, the manual accounts route's delete, moved there so both share it), the tags no annotation, carried annotation or rule holds (deleted as one deletion, one sweep), the categories `categoryUsages` finds unused (every store read once for them all), and a group left empty with no budget now or in a past month (`groupsWithBudgets` over `budget-months`); then the entry. `migrationUndoPlan` adds up each account's `undoPlan` or `historyUndoPlan` for the confirmation. The entry's shape is closed: one a later release wrote more into is unrecognised, so never undone without what it added.
- **Stores.** `app-imports` (`lib/migration/store.ts`), one entry per import under `app-import:` and a random id: the app, the export's variant, the file's name and size, the entry read from a zip, its status, each account's import (`imports`), what it made (`made`) and the counts, exportable. Everything else it writes is in the stores the other imports and the app already write (the manual accounts, `manual:accounts`; `manual-transactions`; `imports` and `import-summaries`; `imported-transactions`; `history-imports` and `history-import-summaries`; `categories`; `tags`; `transaction-annotations`; `transaction-splits`; and the category overrides, `txn-category-overrides`), all of them in the download already, which `test/migration-routes.test.ts` checks. No balance history is written, as no import writes it; a linked account's estimated history is drawn again through its new rows (`importedRowsChanged`, `drawImportedHistory`).
- **The read-only API needs no change.** The rows are manual and imported rows to every reader, read through `lib/activity.ts` as any import's, so `/api/v1` and the MCP server list and total them, with their categories, tags, notes and splits, as they do a file's; the record of the import is the app's own, like `imports` and `history-imports`, which the API doesn't list either.
- **Left out.** YNAB's and Lunch Money's APIs: either would take the person's personal access token (full access to their budget there, to write as well as read), and nothing could be tested against either without real credentials, while the exports carry the same data. Actual's SQLite export, above.

Limits: the file as the other imports' (3 MB), at most `MAX_APP_ROWS` (30,000) transactions and `MAX_SOURCE_ACCOUNTS` (100) accounts, each list in the review cut short (`LISTED_*`), and the hourly counts of `import-requests` and `import-reads` shared with the other imports.

## Connectors

Bring your own sync ([features.md](features.md#bring-your-own-sync)) is built on a connector interface (`lib/connectors/types.ts`), so SimpleFIN, the first, is one module (`simplefin.ts`), and the Lunch Flow Personal API, the second, is one more (`lunchflow.ts`), on the same stores, daily fetch, budget, health, routes and screens.

**What a connector supplies** (`ConnectorDef`) is four calls and a few numbers:

- `checkInput` and `exchange`: whether what the person pastes can be a token at all (checked before anything is counted or sent, after the connect route has refused anything longer than `maxInputChars`), and that token exchanged for the credential Nya keeps: SimpleFIN's one-time Setup Token claimed for its Access URL, or a Lunch Flow API key checked once with Lunch Flow and kept as it is. `hostOf` reads the host a stored credential reaches.
- `fetch`: with that credential, a window of days (with the remote ids of the tracked accounts, `accounts`, for a connector that asks account by account) or balances only, every account the credential can see (`RemoteAccount`: the connector's own id, name, institution, currency, the balance from the holder's side with the time the institution gave it, or none (`balance_at` null, shown as of the fetch that brought it) when the connector gives none, and the transactions posted in the window as the import pipeline's `RawRecord`s, in Plaid's sign, with the connector's id as `source_id`), and the problems it reported, in its own words (`RemoteProblem`), each with whose side it is on and the accounts it concerns when that can be told. A request that brings nothing usable throws a `ConnectorFailure` of one of a few kinds (`refused`, `payment`, `limited`, `rejected`, `down`, `answer`, `blocked`, `credentials`), with whose side it is on and a message that is safe to show and to log.
- `windowDays` and `overlapDays`: the longest window it serves (90 for SimpleFIN, 731 for Lunch Flow, which documents none: two years in one answer) and how far each window overlaps the one before (5, and 45 for Lunch Flow, whose held card purchases can post weeks after the day they are dated by). `providerDailyLimit` is the service's own limit per credential (24 for SimpleFIN; none documented for Lunch Flow).

Its words are in `CONNECTOR_WORDS` (`types.ts`, so client code needs no connector module): what the person calls it, what they paste, what connecting again takes, and whose day a balance's date is (the institution's, or, for Lunch Flow, the day Nya received it: `connectorBalanceDay`). A new connector is a module implementing `ConnectorDef`, a line in `lib/connectors/registry.ts`, its kind in `CONNECTOR_KINDS` with its words, and that kind as its rows' `source` where sources are listed (`SourceKind` and `ID_SOURCES` in `lib/import/`, the rules' `SOURCE_KINDS`, the API's schema). Everything else is shared and knows nothing of the protocol: the stores (`store.ts`), the daily fetch and its request budget (`sync.ts`), connecting, choosing accounts and letting them go (`manage.ts`), how the accounts join net worth and the history gate (`institutions.ts`), their connection health and its words (`health.ts`), what the screens are sent (`view.ts`), the routes (`app/api/connectors`) and the screens (`components/Connectors.tsx`). No code under `lib/connectors` or `app/api/connectors` imports the Plaid client, and a test holds it to that.

**The network** (`http.ts`, `net-guard.ts`). A connector's URLs come from the person (SimpleFIN's Setup Token is a URL they paste, and the Access URL names whatever host the server chose), so every request goes through one guarded HTTPS request, against server-side request forgery. Lunch Flow's address is fixed (`LUNCHFLOW_API`, `https://lunchflow.app/api/v1`), and nothing the person pastes names a host, but its requests are held to the same rules:

- https only, on any port;
- no credentials in the URL itself: they are sent as an Authorization header (SimpleFIN's) or in a key header the connector names (Lunch Flow's `x-api-key`, which can't be a header the request sets itself, nor hold a line break), and only to the URL's own origin, or to the few the connector names as the same service's (`trustedOrigins`: Lunch Flow's site at its `www` name), never to another host a redirect names;
- every address the host resolves to must be public, checked after DNS resolution and pinned for the connection (through the request's own `lookup`), so a name that resolves differently a moment later can't slip a private address in. For IPv4, nothing private, loopback, link-local (the cloud metadata services among them), shared, documentation, benchmarking, multicast or reserved. For IPv6, only global unicast (`2000::/3`) outside its documentation, protocol (Teredo) and 6to4 ranges, plus an IPv4-mapped or NAT64 address judged by the IPv4 one it carries; an address with a zone is refused. For IPv6 that is an allow-list, so a range assigned later is refused until it is known;
- at most three redirects, each held to every rule above;
- one deadline for the whole exchange, redirects included (15 seconds to claim a token or check a key, 20 to fetch, which Lunch Flow's requests for one fetch share), so an answer that comes a byte at a time is cut off like one that never comes;
- a bounded answer (4 KB for a claim, 10 MB for SimpleFIN's accounts, 5 MB for each of Lunch Flow's answers): one declared or found to be larger is dropped, never read whole;
- no compression asked for, and none undone: a compressed answer arrives as the bytes it came in, held to the same bound, so a small one can't inflate past it.

Its errors name the host, never the URL, its path, a header or the request's options, and never wrap the error underneath, so they are safe to pass to `loggable()` and to show.

**The SimpleFIN protocol** (`simplefin.ts`). A Setup Token is the base64 of a claim URL; a POST to it answers the Access URL (`https://user:password@host/path`), once: a second claim is refused. Reading is `GET <Access URL>/accounts`, the credentials sent as Basic authorization, with `start-date` and `end-date` in Unix seconds (transactions posted on or after the first and before the second) or `balances-only=1`, and never `pending=1`. The answer is an Account Set: `errors`, messages for the person, shown as they came, and `accounts`, each with `org`, `id`, `name`, `currency`, `balance`, `available-balance`, `balance-date` and `transactions` (`id`, `posted`, `amount`, `description`, and optionally `payee`, `memo`, `transacted_at`, `pending`). Amounts are from the holder's side (money in is positive), so each is negated once into Plaid's sign; balances are from the holder's side too (money owed is negative) and are kept as reported, turned into Nya's positive amount owed only once the person says an account is a card or a loan. The accounts are read at the Access URL's own path with `/accounts` after it, set on a copy of its address, so a path that starts with `//` stays a path on the same host. A transaction's day is the UTC day of its `posted` time: right for SimpleFIN Bridge's noon UTC stamps, and a day early for a server that stamps local midnight east of UTC, whose zone the protocol doesn't give (Nya doesn't guess it from the hour, which is a real posting time in the Americas). An `errors` message is tied to the accounts of the institution it names as words of their own ("Ally" is not named in "Rally Credit Union"); one that names none could concern any of them. A server that also sends `errlist`, entries with an account id, is read by id.

**The Lunch Flow Personal API** (`lunchflow.ts`). Its documentation couldn't be read in full when this was built, so some of it was read from Lunch Flow's own clients and other apps' that read it; the module's header names each source, and what it takes on a safe reading. The key goes in `x-api-key`; checking it is one `GET /accounts`, where 401 or 403 is a key Lunch Flow doesn't take, and nothing is spent, so a check that got no answer can be tried again. No one answer holds every account, so a fetch asks account by account: `GET /accounts` (`{ accounts, total }`, each with `id`, a number, `name`, `institution_name`, `provider`, a `currency` that is often missing, and `status`, `ACTIVE`, `DISCONNECTED` or `ERROR`); then, for the tracked accounts (`FetchRequest.accounts`) first, each one's `GET /accounts/:id/balance` (`{ balance: { amount, currency } }`, the amount a number or a string), which also gives its currency, and its `GET /accounts/:id/transactions` with `from` and `to` (`{ transactions, total }`, each with `id`, null on a pending one, `accountId`, `amount`, money out negative, `currency`, `date`, a calendar day, `merchant`, `description` and `isPending`); then the balance of each account not tracked that Nya doesn't offer yet. One it offers already (`FetchRequest.offered`, from the connection's `available`) is only listed (`RemoteAnswer.listed`), and `availableIn` keeps its stored offer, currency and all, under its new names. A listing to choose from (balances only) asks every balance. At most four are in flight within the fetch's one deadline, and the fetch counts as one of the day's requests. `from` and `to` are inclusive days, and every posted row an answer holds is kept back to `FetchRequest.since` (the history's limit), dated before the window or not: a row is dated by its own day and a held card purchase comes once it posts, so it can turn up weeks late, and rows are matched by id, so one sent again or outside the window is never counted twice. The windows overlap by 45 days for the same reason. An answer's `total` isn't read (no client reads it, and one sample has 2927 beside 11 rows). `include_pending` is never sent, and a row marked pending or with no id is left out and counted. Lunch Flow gives a bank no id, so accounts are grouped into banks by `provider` and `institution_name`. A balance comes with no time (`balance_at` null), so its card says the day Nya received it, its age never holds its bank (`OLD_BALANCE_HOURS`), and a link at Lunch Flow that broke is told by the accounts' `status` instead, one problem per bank with an account tracked (a link that stops updating while still `ACTIVE` can't be told). A request about a tracked account that brings nothing usable (no answer, a 5xx such as the 503 `GCRateLimited` a provider's limit behind Lunch Flow gives, an answer that can't be read, a 404 that isn't "Account not found", or Nya's own time running out before it asked, on Nya's side) is a problem for that account only, of kind `retry` (`RemoteProblem.kind`): it holds the bank, and connection health words it as a wait (`issue: 'down'`), never as something to fix at the connector, which stays the word of a problem with no kind. "Account not found" leaves the account missing from the answer. A refused key (401, 403), 402, 429, any other 4xx, or an address Nya won't use stops the fetch, and one where no tracked account came through throws its first failure. Only the tracked accounts' problems are kept, theirs first, at most 20: past that, one names no account, so a cut list never reads as whole. Text Lunch Flow sends is cleaned and capped, with the key taken out, before it is kept. Holdings (`/accounts/:id/holdings`, for some providers' accounts only) aren't read.

**The stores**, on the storage seam, all in the person's container (`store.ts`):

| Store | What it holds | Download |
| --- | --- | --- |
| `connector-secrets` | Per connection, the credential (SimpleFIN's Access URL, or the Lunch Flow API key). Encrypted like every seam value, never sent to the browser, never in a log or an error, deleted on a disconnect, and never in a backup (`backup: false`, below). | Left out (`exportable: false`): a credential, not data. |
| `connector-connections` | Per connection (`conn_` and a random id): the connector, the host, what its latest request came to (the connector's words among it), when an answer last came, the tracked accounts' remote and Nya ids, the names of the accounts it offers that aren't tracked (never their balances), and how far back history has been fetched. | In. |
| `connector-accounts` | Per tracked account, under its own id: the connection, the connector's id for it, its name and institution, what the person said it is, its currency, and the balance as reported, with the time the institution gave it (none from Lunch Flow). | In. |
| `connector-ended` | Per account let go (stopped or disconnected), under its id: the connection and host it came through, the connector's id for it, its name, institution and kind, when it was tracked and let go, and whether it was kept as a manual account or removed. Written before anything goes, so reports can say what a period may be missing; the person can forget one (`forgetEnded`, `/api/connectors/ended`, on the Reports page). | In. |
| `connector-requests` | A counter per container: the requests made in the current day's window. Out of backups too. | Left out: bookkeeping. |
| `connector-claims` | A counter per container: the tokens claimed and keys checked this hour. Out of backups too. | Left out: bookkeeping. |

**Out of backups.** A store declared `backup: false` on the seam is left out of every backup, and `lib/export.ts` must list its name in `EXCLUDED_PREFIXES` (declaring checks both ways). An Access URL works on its own, as a Lunch Flow key does, unlike a Plaid access token, which is no use without the deployment's Plaid secret: in a backup it would read a person's bank for as long as the backup is kept, and a restore would bring back one the person had disconnected, and the daily fetch would read that bank again. So a restore ends every connection's access: each connection then has no credential, says so, and the person connects again (with a new Setup Token, or a Lunch Flow key, which may be the same one), which carries the same accounts, history and transactions on. The two counters are left out with it, since a window restored part way would only shut requests.

**Kept like manual accounts.** A tracked account's id is a manual account's kind (`manual_` and a random UUID), its transactions are a book in `manual-transactions` (`lib/manual-txns.ts`), each row with its connector as its `source` (`simplefin` or `lunchflow`) and the connector's id as its `source_id`, and its institution in the net-worth payload is `manual` with `connector` beside it. So nothing Plaid-shaped reaches for it: it is never written to the account directory, never joins an account link (`lib/links.ts` leaves manual ids out), and Plaid's health, warnings and emails skip it. The readers that treat manual accounts and these alike read both through `lib/kept-accounts.ts`: Activity's transactions, sharing, and the balances the estimated history holds flat. Net worth reads them apart, each bank a card with health and a gate of its own, and the Plan and the allocation take them from the net-worth payload. Keeping it as a manual account on a disconnect is the same id carried on, so its history, transactions, hidden state, goals and shares stay with it. A tracked account's id is chosen inside the one compare-and-set on its connection's entry, so two devices tracking it at once agree on one id.

**Matching** goes through the import pipeline's normalize stage ([above](#import-pipeline): the rules a typed transaction meets, its text cleaned) and into the account's book in one compare-and-set per 16 accounts, matched by the connector's id alone (`simplefin` and `lunchflow` are in `ID_SOURCES`): an id the book has is the same transaction, brought up to date when the bank changed its date, amount or description, keeping the person's category; an id it hasn't is new. There is no tolerant match and no preview: a connector's id identifies a transaction exactly. Only the category of a connector's row is the person's to change; its note, like its date, amount, payee and account, is refused.

**Read-only readers** (the API and MCP server, `lib/api-read.ts`, and reports, `lib/report/read.ts`) read the connector's banks leniently (`connectorBanksReport`): an account entry that can't be read is named (`missing_accounts` with its connector as `source`, `simplefin` or `lunchflow`, or a report's gap) and the rest answered, and a connection entry that can't be read leaves its banks saying how they are doing isn't known, never gone. The API serves each account with its connector as `source` and its balance from `nyaBalance` (so an unanswered card leaves net worth `complete: false`), as of its `balance_at` (or, from Lunch Flow, which gives none, of the fetch that brought it), with its bank's health in the API's connection shape; each bank is a transaction source. A report lists each bank as an institution "through SimpleFIN" or "through Lunch Flow", dated by its latest answer while its card is current and by its last clean sync otherwise, importing only before the history that has come, and reads `connector-ended`, written by `releaseAccounts` before anything goes, to say an account let go in the period was removed (as a removed Plaid connection is) or kept by hand from that day (`disconnected`).

**Transfers between connector accounts** are worked out when the rows are read (`lib/manual-txns.ts` connectorTransfers), never stored: an exact opposite pair (the same amount out of a checking or savings account and into another connector account, one currency, within four days), neither categorized by the person, is shown as a bank shows the same pair, in Plaid's words, by the type of the account the money goes into (`PairKind`): into a card as Plaid's card payment (`loan payments`, detail `credit card payment`), into a loan as a loan payment (`loan payments`), and otherwise as `transfer out` and `transfer in`, by its side, with no `transaction_code` (a US bank gives none). The words file each side into the person's categories as a bank's are (seeded, into the Transfers group), and a total leaves out a row whose category's group is of the transfer kind (`lib/spending.ts` isTransfer): renamed, a pair's category still leaves it out; moved into a group of another kind, it counts as that kind, a bank's rows and these alike, and its row stops saying how to count it. The finer rules read the words, never the group: a card's or a loan's payment from cash is a bill recurring detection finds and the cash forecast counts, as a bank's is (`lib/recurring.ts`), and a loan's is a loan payment in the Plan's spending (`lib/fire/inputs.ts`). `paired` marks its Activity row as worked out from the amounts, and a category the person gives either side undoes the pair, on the server and at once on the page (`components/transaction-edits.ts` recategorizedRow). Money leaving a card is never a side: a purchase matched with an unrelated deposit is how a false pair would look. Paired across hidden accounts too, so a side shown never counts alone. The rest come without a category; the Activity tab's month totals and the Plan's spending say how many they count (`uncategorizedFromConnector`).

**Balances and the history gate** (`institutions.ts`). The accounts are read from what the last fetch stored, so a dashboard load asks the connector nothing. A balance is a measurement, the institution's own with its time, recorded through `recordFetch` like a Plaid balance on a clean answer, in the day's total and its breakdown (which must name every account the total holds, for hidden-account subtraction), and shown with the institution's own date; one that comes with no time (Lunch Flow's) is as of the fetch that brought it, and its card says so (`connectorBalanceDay`). A bank's card is held out (`error` set, which closes the snapshot gate, and its balances marked `stale`, which keeps them out of the per-account layer too) whenever its latest word isn't a whole, current answer: the request failed, the connector reported a problem that concerns it or names no institution, a tracked account was missing, no answer has held a balance yet or none has been asked for since the person connected again, a card or a loan reports a positive balance the person hasn't said how to read, the institution's own balance is more than 72 hours old (`OLD_BALANCE_HOURS`, which a balance with no time of its own never trips), or no answer has come for 36 hours. Either holds the card, judged now; the connector's last answer only says whose it is: a balance that was current then and has aged past 72 hours since, with no answer for 36 hours to bring a newer, is the missing answer's fault, on Nya's side, never the connector's link to the bank, which is named when the balance was that old already at the answer, or when the answer is fresh. Its last balances are shown as last known, never written as measured and never recovered from the history layer. A connection's accounts that can't be read hold the gate as one unreadable institution, never an empty list; with none tracked, nothing about connections is read at all.

**Signs** (`nyaBalance`). Balances are kept as reported. The protocol's rule is the holder's side, owed negative (Lunch Flow's balances are read the same way, as the apps that read it take a card's and a loan's), so a card's or a loan's negative balance is the positive amount owed in Nya's sign, and with that rule a type chosen wrongly misnames an account without changing its contribution. The protocol doesn't pin a liability's sign, though, so an account the person calls a card or a loan with a positive balance has no balance at all (`needsSign`) until the person says, once per account (`ConnectorAccount.sign`, through `PUT /api/connectors/accounts` with `sign`): `as_reported` (money held) or `owed_positive` (the server reports what is owed as positive, so its sign is turned). It holds its bank meanwhile, with an issue of its own on the person's side.

**The daily fetch** (`sync.ts`) runs inside each container's snapshot (`lib/snapshot-job.ts`), started beside Plaid's fetch, with a deadline of its own (60 seconds) shorter than Plaid's worst case. It settles twice: `recent` once each connection's recent window is stored, which is all the day's total waits for, and `done` once older history has been asked for too, which runs beside the recording and the email notices' preparation, and which the run waits for before it ends. A container makes at most 8 requests in a day's window, counted on the seam before each is sent (a count that can't be read stops requests until the window ends, never opens them; a Lunch Flow fetch, its account by account requests together, is one): the recent window, and while older history is still coming, up to two older windows, never taking the count past 5, so the person's Refresh always has 3. The recent window starts `overlapDays` before the last day fetched and at most `windowDays - 1` days back (it runs to now, with no end date, so it spans under `windowDays` days); a gap longer than that starts the walk back again from the recent window, so no stretch is skipped. Only a whole answer (every tracked account in it, no problem about them) moves the fetched history on, recent or older. History walks back a window at a time until two whole answers in a row bring nothing older than what is there, or two years (730 days, `HISTORY_DAYS`, what Plaid is asked for at link) are fetched; an answer that isn't whole marks the window failed, to ask again the next night. No window starts before that limit, and a recent window that reaches it (Lunch Flow's first, two years long) leaves the history complete at once, with nothing older to ask for. While it walks, Activity reports the connection's banks as importing (`readManualTxnsForDisplay` `incomplete`). The catch-up run skips the recent window only when the last answer is under 12 hours old and whole and current for every tracked account (`answeredWhole`), so a held bank is always asked again. Connecting again forgets the old access's last request, so the accounts wait for the new one rather than showing its refusal; tracking more accounts forgets it too (a listing to choose from names no account, so its problems would read as any bank's), and until the fetch that follows answers (none when the day's requests are spent) the accounts wait for it. An account another connection already tracks for certain (the same remote id from the same connector on the same host, one space of ids) is refused (`trackedElsewhere`), since tracked twice it would be counted twice; names are never compared within one space of ids. Through another connector or on another host (Lunch Flow's API and its own SimpleFIN server answer on one host, with ids of their own), the same institution, account name and balance is only a likely match, shown beside the offer and left to the person. Letting accounts go and keeping them is refused (409, nothing changed) while a card or a loan among them waits for its sign: the disconnect and stop requests take the answer (`sign`) first, and refuse such a keep before saving anything else they bring (`keepRefusal`, counting the kinds and answers in the same request); a refusal only a later step can find says that the changes before it were saved. A share of an account that is only held (no countable balance just now) is paused as a hidden account's is: kept by an edit that doesn't name it, ended by one that names it `none`, unchangeable meanwhile, and listed in the sharing settings as waiting so it can be ended (`lib/sharing.ts` waitingAccounts, `lib/kept-accounts.ts` heldAccounts). Each account's `ok_at` is the time of the balance from the latest answer that reported no problem about it: connection health's last good sync. Pending transactions are never asked for, and any an answer holds are counted and left out: the protocol doesn't tie a pending transaction to the posted one that replaces it.
## Categories

A transaction's category is one of the person's own (#38): a set of categories, each with a random id, in groups, kept in one value store (`categories`, `lib/category-store.ts`; its shape is in [data-export.md](data-export.md#categories)). The pure part, safe in the browser, is `lib/categories.ts`.

**Resolution.** One function, `resolveCategory`, files any transaction from what is known about it (`CategoryFacts`: the words on the row, whether the person chose them, and Plaid's primary and detailed personal finance category). Most specific first:

1. **The person's own**: a category chosen for the transaction (`txn-category-overrides`), or for the one it continues across a re-link (`txn-category-carry`), or written on a row they entered or imported (`manual-transactions`). It is matched by its words, a `text` key. One chosen for a bank's transaction goes with it, by the rules the annotations' prune keeps (`pruneOrphanOverrides` in `lib/overrides.ts`): after a sync saves the bank's removal of it (only the removed ones' read, and the stores only when one has one), at a disconnect (once carried) and at a forget.
2. **The layers'**, by id, following a merge (`rule_category`, set by `lib/txn-layers.ts`; see [below](#tags-notes-and-rules)): below a choice made on one transaction, above what the bank says. Of the layers', first the category an approved transaction was approved under ([below](#review-queue-and-merchant-defaults)), then the first matching rule's (#36), then the merchant's default. One whose category is gone files nothing.
3. **The provider's**: Plaid's detailed category, then its primary one, each a `plaid` key. Seeded, only primaries are mapped, so a detailed one falls through to its primary until a category is given it.
4. **The words the row carries**, for a bank row stored before Plaid's values were kept.
5. **Uncategorized**: the category the set names (`other` when seeded), for a row that says nothing. A row that says something no category has a key for (only past the 500 categories a set holds) is left unfiled instead: it shows its own words and counts by them, as before categories had kinds.

A key is on exactly one category, so the answer never depends on the order of the list. The name always comes from the category, and the result says whether the row said anything at all (the API's `category` is `null` when it didn't, as before). The kind of the category's group (`expense`, `income`, `transfer`) is what decides a transfer in `lib/spending.ts`; the finer rules (recurring detection's everyday categories, the Plan's loan payments, cash and refunds) read the words the row carries (`categoryKey`), never a name.

**Where it runs.** `finishActivity` (`lib/activity.ts`) files every row the Activity tab, the read-only API, reports and recurring detection see, after the cache (only the app's own reads grow the stored set; the API and reports file without writing): the cache keeps each bank row's facts, not a filing, so a rename or a merge shows on the next read without dropping it. Each row keeps its words in `category` (what the release before reads, and what the finer rules key on) and gains `category_id`, `category_name` (`null` when the row said nothing) and `category_kind`. The data download files its transactions, a manual account's rows in its CSV among them, by the same function (`lib/user-export.ts`), each side of a pair of SimpleFIN rows in the pair's words, worked out from the file's rows as the app does (`lib/manual-txns.ts` withPairWords). Totals by category (`lib/totals.ts`) are by the category a row is filed under, named by it, never by an id; a report's marks for taxes (`lib/report/build.ts`) are a category's words, found among the categories by them on each report, so they follow a rename and a merge.

**Text keys are how older stores point here.** Overrides, carried categories and manual and imported rows store a category as words, as they always have, and each set of words is a `text` key of one category. A rename changes no key, so it renames everywhere at once; a merge moves the merged category's keys to the one it went into, so everything that pointed at it points there, with nothing rewritten. Choosing a category stores its first `text` key, which the release before reads as before. Budgets are kept by id (`budget-set`, `lib/budget-store.ts`), with the old name-keyed `budgets` rewritten as a copy on each save; `lib/budget-set.ts` has the rule a group's budget is reconciled with its categories' by. The migration and what a rollback sees are in [operations.md](operations.md#category-ids-the-migration-and-rolling-back).

**Starter sets.** `lib/category-templates.ts` holds the three starter sets ([features.md](features.md#starter-sets)) and the pure plan, `planTemplate`: each seeded category found by the key it was made with (its first key, Plaid's primary category, or the uncategorized one; a merge appends the merged category's keys, so a kept category is placed as what it is, and one the person made is placed by none), placed in the set's group (one of the person's by its name, else added) under the set's name, and archived only when `categoryUsage` (`lib/category-usage.ts`, read strictly) says nothing uses it and it holds no key the set keeps shown. A group it empties goes only when it is a set's (by name and kind), has no budget of its own and has none in the record of budgets by month (`groupsWithBudgets` over `budget-months`, read strictly), since the next note of the budget set drops the record of a group that is gone. The end state is checked whole (names unique in any case, the stored shape, the limits), so two categories can trade names, and the set's own categories are added with `addCategory`, keys and all. No key moves, so every row stays filed where it was, and budgets, kept by id, follow. `app/api/categories/templates` previews a plan, applies it in one compare-and-set that works it out again on the stored set and refuses one other than the one previewed (a digest of its changes; the 409 says `changed`, and the page previews again), and undoes it from what the apply answered (`undoOf`: each change as it was and as it was made, so one made since is kept), making a removed group again under its own id and removing the categories it added only through `deleteCategory`. A usage read is every stored row, so it is made once for all the categories a set would archive, or an undo would remove (`categoryUsages`).

**Seeding and growing.** The app's first read makes the set from the default groups, Plaid's primaries and every category already written on the person's data; afterwards, a key no category has (Plaid starts using a new category, a file brings its own) is given one, to the category with the same words or a new one where its kind belongs (`growTaxonomy`). Both are a compare-and-set on the stored set (the value store's `update`), so two reads at once agree on the ids. The read-only API and the download never write: they grow a copy in memory, with provisional ids (`new:` and a random id) that are shown as `null`. A set that can't be read is never seeded over: the edits refuse, and the Activity tab shows each transaction under the category it came with, with a note.

## Tags, notes and rules

Tags (#40) and rules (#36) are applied on read, in the one place every reader shares, and never written into a stored row: so a rule saved changes every past and future match at once, turning one off puts every row back exactly as it was, and the app, the read-only API and its MCP server, reports, recurring detection, the cash forecast and the Plan all see the same rows.

**Where they are kept.** Four stores on the storage seam, all encrypted:

- `tags` (`lib/tags.ts`), one value: the tags, each a random id, a name (unique in any case) and a color. Rows and rules hold ids, so a rename is everywhere at once.
- `rules` (`lib/rules.ts`), one value: the rules, each a random id, `enabled`, `priority`, its conditions (all must match) and its actions. Its shape is closed: a condition, action or field this release doesn't know makes the whole set unrecognised, never half applied, since a rule read without a condition a later release added would match more than it should. While the rules can't be read none is applied, the Activity tab, reports and the API say so, and nothing is saved over them.
- `transaction-annotations` (`lib/txn-annotations.ts`), one record per transaction, by its id, a bank's, a manual one's or one imported into a linked account (`imported-txn:`) alike: `excluded`, `tags` (put on), `untagged` (taken off: a rule or a carried tag doesn't put it back) and the `note` of a row that stays as its source gave it (a bank's, a SimpleFIN one's, one imported into a linked account, whose file's memo shows until the person writes one); a row entered by hand or imported into a manual account has its own (`lib/manual-txns.ts`), so a row never has two. Undoing an import, or forgetting the account it was imported into, takes its rows' records with them. Fields a later release adds ride along and every edit keeps them, as the release before this one keeps tags and notes. Pruned with the transaction after a sync saves the bank's removal of it, a disconnect or a forget, as exclusions always were.
- `carried-annotations`, one record per earlier account: what was said about its posted rows, by content key, for a re-link (`lib/txn-annotations.ts`).

**The read path.** `lib/activity.ts` assembles the banks' part (cached) and then `finishActivity` (on every request):

1. The banks' part, as before, with the person's category for a row, a carried category or exclusion, and their name for its merchant applied, and, never sent, what the later steps need: the row's account (`account_ref`), the bank's name under a rename (`renamed_from`) and what the row carries from an earlier account besides an exclusion (`carried`: an include, tags, a note), and on a bank row standing for rows imported into its account (#52), their ids, earlier imports first (`stands_for`; a pending one takes nothing said about them until it posts), so what was said about them is read with every record on each request rather than cached. A payload cached before rows carried these is a miss (`layer_facts`).
2. `finishActivity` merges the manual rows and reads what was said about each row, the tags and the rules (each a display read: what can't be read is a note, never a stop).
3. The categories are loaded (and, by the app, grown) first, since rules read them (`lib/category-store.ts` filingSet).
4. The rules are compiled once (`compileRules`: enabled ones, in order, each condition a test; one naming a category that is gone is left out, as broken), and the links read only when a rule names an account, which follows them as every reader does: the links that apply (`effectiveLinks`), never one whose earlier account is live again, or two live accounts would be folded into one. Links or live accounts that can't be read leave a rule on an account to that account's own rows, with a note; categories that can't be read leave out every rule that names one, with a note (both affect totals, so reports carry them as gaps). The tags' own note goes only to what shows tags (the app and the API), not to reports.
5. `applyLayers` (`lib/txn-layers.ts`) gives each row, from the row as it is before any rule (`subjectOf`: its names, amount, account, institution, the category it is under, its source), what the rules that match say, each field from the first rule that sets it, tags from every one, and lays over it what was carried, then what the person said about the imported rows it stands for, then what they said on the row itself. A choice made on one row always wins: their category (`lib/categories.ts` ownCategory, which a rule's never replaces), their name for its merchant (a vendor rename of a bank's, a name given an imported row in the app, `ManualTxn.named`, or the name typed on a row entered by hand, which no rule renames; a SimpleFIN row's payee stays the bank's, so only a rule renames it), a tag taken off, an exclusion set or cleared. A rule's hide marks the row excluded, as an exclusion does, so every total leaves it out by the one rule in `lib/spending.ts`, with `excluded_by_rule` to say whose. A rule's category never goes on one side of a pair Nya works out between two SimpleFIN accounts (`paired`, `lib/manual-txns.ts`): its category is the pair's, so a total never counts half a transfer. A note on a SimpleFIN row is the person's, kept in its record as a bank row's is, since the row stays as the bank gave it, and so is one on a row imported into a linked account, which stays as its file gave it. A row imported into a linked account is otherwise ruled as a bank's: its source is `import`, as a manual account's imported rows are (the account condition tells them apart), its account rides along as a bank row's does (`account_ref`), a rule names it unless the person renamed its merchant, and files it only when it has no category of its own (the file's words, or one chosen). Then the review queue's layer (`lib/review-layer.ts`, [below](#review-queue-and-merchant-defaults)): a merchant's default under the rule's category, and what the person approved over both. A rule's category is marked `category_by_rule`, and a rule's name keeps the name before it beside it (`name_before_rules`), both sent: the edit form of a manual row starts from its own and sends a name or a category only when the person changed it (`components/ManualTxnSheet.tsx`), so a save never writes a rule's into the row, and a rule made from a row starts from the name rules match.
6. Every row is filed (`fileRows`), a rule's category in the slot `resolveCategory` keeps for it, and the facts above are dropped.

What can't be read along the way is a note. Of the notes, those that mean transactions are missing (an institution's, rows imported into a linked account that can't be shown, a manual account's) are also given apart (`unread_notes`, which `/api/transactions` sends beside `notes`): the Plan weighs its figures by those only (`lib/fire/inputs.ts` unreadNotesOf), never by one that says how a rule, a category, a split or a group applies. The notes on what no figure reads (tags that can't be read, and the review queue's settings) are sent apart too (`aside_notes`): the list says them after the rest, and the cash flow chart, which puts the list's notes first among what may be missing, never does.

The download (`lib/user-export.ts`, through `lib/export-layers.ts`) applies the same `applyLayers` to every stored row from the file's own parts, so its `nya_category`, `nya_name`, `tags` and `excluded` are the app's (a manual account's institution as the app shows it, `Manual` when it has none, which a rule's institution condition reads), the rows imported into linked accounts' among them (`layerImportedRow`), and a bank row standing for some laid on again with them once the file knows which (`buildUserExport`). A transactions CSV or an OFX statement made while a part they are made from can't be read (what was said about rows, what was carried, the rules, the tags) is called incomplete and says what that leaves out.

The rows before the year that recurring detection reads (`OlderTxn`) carry the merchant behind a payment processor, so a name rule matches them as it matches the year's. Which of them the banks' part keeps with its cache is chosen by name before rules apply (rules apply after the cache), and narrowed after them: a rule that gives one merchant's changing descriptors one name can leave out an older row whose descriptor matches none of this year's, which a yearly charge may need. Sharing reads the stored rows directly and applies nothing: a tag, a note or what a rule does is never shown to someone else.

**The order between them.** Field by field, the person's own last: excluded is the row's own record, else unknown when that can't be read (counted, marked null), else what was said about the imported rows a bank row stands for (any excluded excludes it; else one that can't be read leaves it unknown; else one put back puts it back), else what was carried, else a rule's hide; tags are the rules', then the carried ones on top (what was taken off removed, what was put on added), then the imported rows', then the row's own; a bank row's note is its own (an empty one clears it), else one written on the imported rows it stands for (the earliest import's), else carried.

**Deleting a tag** can't leave half a state: one compare-and-set takes the tag out of the list and notes its id under `deleting`, and from then on nothing shows it, since only tags that exist are ever shown; then its id is swept off every record, carried record and rule, each in its own compare-and-set; then the note goes. A sweep cut off part way is finished by the next change to the tags, sweeping only noted ids, so a tag made meanwhile on another device is never taken for a deleted one (`lib/tag-delete.ts`). Rules that can't be read keep the note until they can be swept. A rule saved, or a tag put on a transaction, while the tag was being deleted can land after the sweep: the save then sweeps the ids of tags that no longer exist itself (`app/api/rules`, `app/api/transaction-annotations`), so the two end with nothing holding it whichever lands first; meanwhile no screen or answer shows it (`withLiveTags`), and an edit of the rule leaves it out rather than refuse.

**Cost.** Rules run on every read, over every row the reader reads: compiled once per request, with each row's names normalized once. A hundred rules over five thousand transactions take about 60 ms (`test/rules.test.ts` holds it under 300 ms, warmed up); 250 rules of ten conditions over twenty thousand rows, about 450 ms. The preview of a rule (`app/api/rules/preview`) reads every stored row of every date, from storage, never syncing.

## Budgets by month and rollover

Budget rollover and income carryover (#37) live beside the budget set, never in it. `budget-set` keeps its closed shape, written exactly as the release before writes it, so a rollback reads every budget as before ([operations.md](operations.md#budget-rollover-and-rolling-back)). Two value stores on the seam (`lib/budget-months-store.ts`) hold what rollover adds, keyed inside by the same category and group ids:

- **`budget-months`**: for each budget, the amount the record last saw in the budget set (`seen`), the amounts it had in past months (`amounts`: each entry an amount for the months before a month, back to the entry before), and the months it rolled over (`rollover`: periods from the month it was turned on, or reset, to the month it was turned off), with the month the record began (`since`). Its shape is closed, as the budget set's is, so a later release's record reads as unrecognised here and is never saved over.
- **`income-carryover`**: whether income carryover is on, and the month its pool counts from.

**Amounts by month.** A budget's amount now is the budget set's. Whenever the app reads a month of budgets, or saves them, it notes the budget set in the record (`noteBudgets` in `lib/rollover.ts`, a compare-and-set): a budget whose amount differs from what the record last saw has the amount it had kept for the months before the month this happens in, the month the page says it is (`thisMonth`, checked to be one some time zone is in now); one seen for the first time had none before; one gone ends its rollover; one on a category or group that no longer exists is dropped. So changing this month's amount never rewrites an earlier month, and a change made elsewhere (by the release before, after a rollback) is pinned to the month it is first seen. A save of budgets notes the record before writing the budget set, then records what it replaced. A record that can't be noted (it can't be read, say) never stops a save: the save writes only the budget set, the record stays exactly as it is, and the first read that can read it again notes the change as of the month it is read in, as it notes a change made by the release before; rollover changes, which need the record, are refused (409) meanwhile. The record begins with the first budget: a read with no budgets at all keeps none, since a budget set later had none before, which a record begun then says too. The month the record began bounds what is known: an amount for a month before it is the earliest recorded one, and said to be assumed.

**The carry is derived, never stored.** `lib/rollover.ts` is the math, pure and safe in the browser: a budget's amount in a month (following a merge to where it went, adding up the records under it), its carry into a month (zero at the month it counts from, then each month's amount less its spending added on), the reconcile rule over what is available (`availableMeters`, which is `budgetMeters` from `lib/budget-set.ts` over amounts with their carries), and the income pool (`incomePool`). `lib/budget-month.ts` reads what it needs, one way, for the Budgets tab (`app/api/budgets/month`), the read-only API and MCP (`readBudgets` in `lib/api-read.ts`) and the data download (`lib/user-export.ts`): the budget set, the record, the income setting, and the stored transactions as the Activity tab assembles them (`lib/activity.ts`, never calling Plaid), back to the first month any carry or pool counts (`neededFrom`), however long before the year the dashboard loads. Each month's spending by category is `spendingByCategory` and its money in and out `summarize` (`lib/totals.ts`), so through `countsInTotals`: one currency (the one most of the last year's transactions are in), what was excluded left out, transfers, cash and loan payments neither spending nor income. A recategorization, a merge, an exclusion, a rename, a rule (applied on read by the same assembly, `lib/txn-layers.ts`: a rule's hide marks a row excluded) or an account's end (whose rows the assembly leaves out from its end day, `lib/lifecycle.ts`) changes every carry at once, since nothing about them is stored. An end is never a gap in the months counted; a connection whose every account (not hidden) has ended leaves none from the last of their ends (`until` on its coverage facts), as a report counts it. Decoding every institution's stored rows is most of a read's cost, so the app's view of this month skips it when nothing in the month counts spending (no budget rolls over in it, and income carryover is off: `budgetsWithoutHistory`): its budgets are then the budget set's, with no carry, and the page counts the month's own spending as it always has. The Budgets tab asks for the history all the same (`history=1`), for its month picker and the months a rollover can start from. The page loads the month once its transactions have loaded, and again after each change has settled, never while a save is under way. Nothing is counted past this month: a month still to come has its budgets and no carry, no pool and no incomplete months, and the month ranges count months as numbers, so none runs past the month asked for.

**Honest gaps.** The same read says which months may be incomplete (`monthGapsOf`): an institution missing from the read or still importing, a connection in a broken state that last synced before the month ended (its notice's state and its last sync, as the read-only API reads them), a linked institution whose stored history begins after the month began, a bank account or card whose transactions don't come in, what the read couldn't read (a manual account's rows, the person's own categories or carried exclusions, connection health), and rows whose exclusion couldn't be read. A carry or pool counting such a month lists it. Files imported into a linked connection's bank accounts and cards (#52) stand for the bank's own where it has none, by the rule a report counts them by (`lib/history-import/coverage.ts`): the coverage facts of a linked institution's first stored day, of one whose transactions don't come in, and of one that hasn't synced yet carry each account with what its files cover and its end (`files`, `lib/rollover.ts` Filed, from `coveredAccountsOf` and `importedCoverage` in `lib/history-import/read.ts`, read leniently as a report reads them), and a month they cover for every one is no gap; a connection that stopped after it synced has none. Carries and pools begin no earlier than the first month with any stored transaction (a linked institution's first stored day, the earliest row on a manual or SimpleFIN account, or the earliest row imported into a linked account that counts: `imported_first` from `assembleBankRows`).

**Groups.** A group's own budget rolls over what is left of it after everything spent in the group. The reconcile rule works on what is available, a carry included, and the month's total adds each group's limit once, so a carry is never counted twice.

**Suggestions.** This month's answer, with the history, carries budget suggestions (`suggestions`, `lib/budget-suggestions.ts`, pure): each month's `spendingByCategory` over the three months before, from the same assembled rows, filed by `filedId` and rolled up to the spending groups, averaged in the currency's minor units over the months the stored history reaches whole (none while `earliest` is null, not one before it, nor the month the rows begin in from a later day, nor one with a `begins` gap), the others' gaps (`monthGapsOf`) named, and what another currency left out counted by the category and group it would have counted for (`left_out`). It needs no read of its own: the Budgets tab asks for the history anyway, and a month gone by, or an answer without the history, carries none.

**Merges and deletes.** The categories route moves a merged category's record onto the one it went into (`monthsAfterMerge`: amounts added month by month, the rollover of the one it went into, else its own) after it moves the budget, and drops a deleted category's or group's. Both are best effort: reads follow a merge and add the records up all the same, and the next note drops a deleted one's.

## Cash flow

The Activity tab's cash flow chart (#41) and `/api/v1/cash-flow` are one computation over the rows every total reads, with nothing stored:

- **Where the flows come from.** `lib/cash-flow.ts` (pure, safe in the browser) takes the rows `finishActivity` assembles (`lib/activity.ts`: the app's from `/api/transactions`, the API's from `readActivity` in `lib/api-read.ts`, read by `lib/api-cash-flow.ts`) and a range of days. Money in, money out, net and the counts are `summarize`'s own (`lib/totals.ts`). Each row that counts (`countsInTotals` in `lib/spending.ts`, so by its category group's kind) goes to a payer when it is money in, else to the category it is filed under (`filedId` in `lib/categories.ts`, as the Budgets tab files it) in that category's group. So the chart's money in is the Activity tab's for the same months, and its spending by category is `spendingByCategory`'s, to the cent: `test/cash-flow.test.ts` holds them equal over rows with transfers, a refund, an exclusion, a rule's hide, another currency, SimpleFIN and imported rows, and `test/api-cash-flow.test.ts` holds the API's answer to `/api/v1/spending`'s. Rows imported into linked accounts (#52) come in through the same assembly, each only where no bank row stands for it; a bank row that does carries what was said of the imported one (its `stands_for`, which `lib/txn-layers.ts` lays on and never sends), so none counts twice: `test/cash-flow-imports.test.ts` holds the chart and the API to the totals over an import with a row the person said is the bank's and one the bank sent later. Split and grouped transactions (#39) come in as `lib/split-rows.ts` answers them, a split one as its parts and a group as its net under its own category (its transactions inside it, never payers or spending on their own), and every count is `transactionCounter`'s (`lib/spending.ts`), as the totals' are: payers and categories keep their rows, so a fold and each side of the table count a transaction once however its parts are spread. `test/cash-flow-splits.test.ts` holds the chart and `/api/v1/cash-flow` to the totals and to `/api/v1/spending`, counts included. A payer is the name on its rows, compared without case or spacing: Plaid's `transaction_code` has no payroll value, so pay is told apart by who paid it. A refund is money in, as the month's totals and the budgets count it (the Plan's spending, with rules of its own, takes refunds off spending).
- **The chart's graph** (`flowGraph`) is four columns: payers (with what came from savings or debt at their foot), everything counted, the groups (with what was left over), and their categories. Payers and categories under 3% of the larger of money in and out fold, into Other income and into Other within their group, but never one alone; a group under 3% ends at the group. More out than in is a node beside the payers, never a link back, and the layout refuses a link to an earlier column.
- **The layout** (`lib/sankey.ts`) is a pure function, with no chart library: columns across a 340-wide viewBox, nodes on one scale stacked with a fixed gap and each column centred, ribbons as two cubic Bezier curves leaving and reaching their nodes at the stacked offsets of the links before them, labels beside thin nodes spread so none overlap and cut to an estimate of their width. Whether a label is drawn, on how many lines, and where it can be tapped are worked out beside the room the widest amount could take in the currency and locale (`amountSamples` in `lib/format.ts`, `fitBeside`), never beside the amount's own width, so they are the same whatever the amounts and whether they are hidden. The name drawn beside its amount is cut beside the amount drawn, which while amounts are hidden is the mask, as wide whatever the figure, so a name's cut never says how long a hidden figure is. `test/sankey.test.ts` holds the geometry, and `test/hide-amounts.test.tsx` that it is drawn the same with amounts hidden. `components/CashFlowSankey.tsx` draws it as inline SVG with the app's color variables, and a table of every flow as its text alternative.
- **Periods** are whole months on the person's own calendar (`periodOf`, from `localDate`), so each month in one is the Activity tab's. The app loads the last 365 days by UTC day (`WINDOW_DAYS`, which a test holds equal to `LOOKBACK_DAYS` in `lib/transactions.ts`, a server module the browser never loads); a period reaching before them, or before the earliest row loaded, says so (`historyNote`). What may be missing from its months is said beside it (`cashFlowNotes`): first what the load couldn't read (the Activity list's notes, never its `aside_notes`, on what no figure reads), then `lib/month-coverage.ts`'s gaps, as the Activity tab says them of each month. What imported files cover reaches both only for a connection whose transactions don't come in (`refused`, `no_consent`): `/api/transactions` sends each with its bank accounts and cards and the days their files cover (`files` on `without_transactions`, `lib/history-import/without-files.ts`, read on every load and never cached), and a month every one of them is covered for, by `lib/history-import/coverage.ts` (the rule reports, rollover and a goal's pace follow), drops it from the month's notes and from the chart's months (`coveredOutOf` in `lib/no-transactions.ts`); any other connection is named whatever files cover, as on a report. The earliest row loaded, imported ones among them, is where the history begins. Beside what it leaves out, it says how many of the period's rows were imported, in the month summary's own words (`importedRowsNote` in `lib/history-import/view.ts`, of the period), and so do the API's notes, spending's and the cash flow's alike, last (`importedNote` in `lib/api-read.ts`).
- **A tap** keeps which node of which period was tapped (`FlowPick`), not its rows: the Activity list works the node's rows out again from the rows as they are now (`pickedRows`), so a row recategorized or excluded since leaves it, and passes them through its own search and tag filter (`components/txn-search.ts`). The Activity tab keeps the chart's period beside the pick (`components/MonthBreakdown.tsx`), since a reload of the transactions shows a spinner in the card's place: both come back together. A pick from the table the chart folds or leaves to its group marks the node that holds it (`drawnNodeOf`). The list puts the picked rows back whole (`bankRows`): a split transaction with only its parts in the node under it, labelled and edited from every part of it (`wholeSplits` in `components/SplitRows.tsx`), and a group's row with its transactions; the line above the list counts transactions (`countTransactions`).

## Runway and year over year

Two reports on the report page (`app/reports`, `components/ReportsPage.tsx`), each also an endpoint of the read-only API, built on the accountant's report's read and on the forecast, with nothing stored but the scenarios the person saves:

- **One read, several periods.** `readReportInput` (`lib/report/read.ts`) is what `readReport` builds from, read once: the report's `ReportInput` (the Activity tab's rows from the period's first day on, from storage, with the sources, gaps' facts and ends) and the rows before it that recurring detection needs (the assembly's `history`). `periodRows` (`lib/report/build.ts`) is the rows a report counts over any days of it (an ended account's from its end on left out), what `buildReport` itself counts. So a runway or a comparison builds as many periods as it needs from one read, each period's gaps and short months by `buildReport`'s own rule. Both read it with `marked: false`, which skips the categories marked for taxes (`report-settings`): they never show them, so they don't depend on that value being readable, and nothing of it reaches the API.
- **The runway** (`lib/report/runway.ts`, pure and safe in the browser). Cash is the forecast's start (`cashPosition` in `lib/forecast.ts`) over the accounts `/api/v1/accounts` lists (`readAccounts`, so each balance is the newest measured one; those that ended, and health savings accounts, are dropped), read by `lib/report/runway-read.ts`. Spending starts from `summarize` over the last 3, 6 or 12 full calendar months, and `windowSpending` then adjusts it for what a runway must see: refunds (money in under a spending category) come off it, a payment from cash with the card-payment detail (`CARD_PAYMENT` in `lib/recurring.ts`) that no card in Nya shows arriving within `CARD_PAYMENT_DAYS` at its amount is added (it pays a card Nya doesn't see), and the bills detected less often than monthly (`infrequentBills`) are taken out, to be added on their dates. Transfers out of cash whose other side no other cash account shows, and ATM withdrawals, are added up apart (`transfers_out`, `cash_out`) for the what-if to count. `movesOut` matches every payment and move out of cash to its other side over all the rows read (from `MOVE_DAYS` before the longest window, so the window's first day has its other side too), telling accounts apart by id as `cashPosition` now tells the pending charges' accounts (each row's account id is followed through the links to the one the accounts are listed under, in `runway-read.ts`; a row whose id isn't listed is told by its name): receipts pending or posted, never one filed under a spending or income category, each taken by one payment only, the nearest in days first, within `CARD_PAYMENT_DAYS` on a card and `TRANSFER_DAYS` (a week) on another account. A card payment with no receipt is still the card's when its series pays a card in Nya (`paysCardOf`) and has been seen landing, or when its group's payments have and its receipt may not be in yet. A move with no other side is split into one that arrived on an account of the person's that isn't cash (`transfers_out_own`: a health savings account, an investment account), one that may have arrived where Nya can't see (`transfers_out_unsure`: a manual cash account with no transactions, never cash on hand, a cash account at a bank short that month, or its other side not in yet), and the rest. Its one-offs are an outflow of half an average month or more at a merchant with nothing of a similar size in the window and not in a detected series (`inSeries`), and money in of that size from a payer with nothing like it and not detected pay. The bills detection holds on a cash account whose latest row is a transfer to every total (a loan's payment, `paymentsOutsideSpending`, through `seriesGroupOf` in `lib/recurring.ts`), the bills less often than monthly, and the planned items become events through `forecastEvents`, so they fall on the forecast's dates. `projectRunway` carries the cash forward day by day for ten years in whole minor units: a day's spending (and income, through the day it stops) taken as a rate times the days, rounded once, plus the events through that day; it runs out on the first day below zero. With no cash account (`has_cash`) or no transactions in the window it gives no figure (`no_cash`, `no_spending`). Its words, for the page and the API's `notes`, are `lib/report/runway-words.ts`, with each window's own gaps. The server sends these inputs (`GET /api/reports/runway?tz=`, which takes nothing else) and the page projects every what-if itself, so a what-if is never sent. `test/runway.test.ts` holds it to a case worked by hand to the day, `test/runway-routes.test.ts` the same case from stored data through the routes and the API.
- **Saved scenarios** are a map store on the seam (`lib/report/runway-scenario-store.ts`, shapes and checks in `lib/report/runway-scenarios.ts`), one entry per scenario under a random id, holding its settings and the currency its lower spending is in, never a figure. A save counts the entries again after its write and takes itself back when saves sent together went past `MAX_SCENARIOS`, as `createToken` does. A delete reads the entry first: a damaged one is removed only with `unreadable: true` (the person confirmed), one a newer version saved never. Exportable; to a restore they are `data`, written back as they were, with room for twice the limit (`lib/user-restore/parts.ts`).
- **Year over year** (`lib/report/year-over-year.ts`, pure) compares January 1 through today with the same days a year before, each month with the same month (this one through the same day), and money in and out by group and category (`filedId`, as the Activity tab files a row, in the group the category is in now), all by `summarize`, so a month is the Activity tab's to the cent (`test/year-over-year.test.ts` holds it to `MonthBreakdown`, and the route's to the accountant's report and `/api/v1/spending`). `lib/report/year-over-year-read.ts` reads both years in one report read and builds the two years' reports for their gaps and months, which mark each month that may be short.
- **A home currency** (`lib/fx/`). The report read's rates (`readFlowFx`, with the accounts' currencies for the runway: `fxAccounts`) go to both. The runway keeps its currency, its cash's, and `buildRunwayInputs` converts the rows into it with `totalsIn` (each at its day's rate), and the cash, pending charges and expected amounts at the newest rates (`cashPosition`, `forecastEvents` and `forecastConverter` in `lib/forecast.ts`); a row is matched to its series, and a move to its other side, by what it was (`asWritten`), never by its converted amount. Year over year is in the home currency (or the one asked for), its rows through `totalsIn`. Each read can give a twin as before a home currency (`plain`), from the same read, for the API.
- **The API** answers both through `lib/api-reports.ts`, on UTC days, with the what-if as arguments of `/api/v1/runway` that change only that answer, and gaps said as sentences in `notes`. Version 1's fields are the `plain` twin's; `base_currency` and `base` are what the page shows.

## Plan scenarios

What-ifs beside the Plan (`lib/fire/scenarios.ts`, `lib/fire/events.ts`, `lib/fire/plan-figures.ts`, `components/PlanScenarios.tsx`), with nothing stored but what each changes:

- **Differences, never a copy.** A scenario is the Plan's settings it sets (absolute values, pinned even when equal to the Plan's), the ids of the Plan's other income and one-offs it leaves out, items it adds (one with a Plan item's id replaces it), and its life events. `resolveScenario` applies them to the Plan as the tab shows it and runs the Plan's own `parsePlan` on the result: a scenario the Plan's rules refuse today is shown with the reason and not run. Your age, `includeCash`, `planFunding`, the method and the part-time income are the Plan's alone, so every plan is measured from one dataset and run one way.
- **One function for a plan's figures**, the Plan's or a scenario's: `planFigures`, which is `fiView` and `enginePlan` exactly with no life events, so compare mode's column for the Plan is the tab's own figures and its job the tab's own job. Life events count in two models of the same years: the FI walk (`walkToFi`), which keeps saving until the FI number is reached, as `fiView` does, so an event counts in every year it covers from today, and stops with no date where a cost is more than the balance then; and the simulation, from the start age, as one-offs, income with an end (`OtherIncome.toYear`) and lower costs (`SimPlan.lowerSpending`, which takes off a year's spending and one-offs and never goes below zero). A lasting change in effect at the start age is retirement spending, in the FI number. `startsWith` says what each plan starts with and what the walk projects then, and whether it starts with more.
- **In the browser.** Measured inputs come from the tab's one hook; the walk is arithmetic on the page; each plan's simulation is one `simulate` job in the tab's worker (`lib/fire/jobs.ts`, with no options, so one seed, run count and block length), its answer kept for the visit by job (the tab's own key) and never stored. Four Monte Carlo plans are three jobs past the Plan's own, 20 to 40 ms each on the development machine.
- **Every save through one router** (`components/plan-savers.ts`): with a scenario open, the forms and Use my allocation save to it (recordSave turns a form's whole plan into the scenario's changes, at the forms' own precision, and refuses a change to what a scenario can't hold), and the repair, the method switch and the allocation settings have no saver. A scenario doesn't open while a repair of the Plan waits, and nothing is compared until the saved Plan has loaded. Every drawer (the tab's, the allocation card's, the life events card's) is bound to the plan it was opened for, a scenario at its `rev` or the Plan: it saves only to that one and closes when the plan shown changes, so a form left open as a scenario closes, or is changed on another device, can't save into another plan. `test/plan-tab-scenarios.test.tsx` renders the tab (react-dom over the small document in `test/mini-dom.ts`) and drives that lifecycle.
- **The store** is a map store on the seam, `plan-scenarios` (`lib/plan-scenarios.ts`), one entry per scenario under a random id. `isPlanScenario` checks the shape, its types and its choices, closed, so a later release's choice reads as unrecognised and is never changed or deleted. A save counts the entries again after its write and takes itself back past `MAX_PLAN_SCENARIOS` (10), as the runway's scenarios do. An edit (`PUT`) is a compare-and-set (`update`) against the `rev` the page loaded: a stale one gets the entry as it is now (409), and one that was deleted is never made again (404). A delete reads first: a damaged entry goes only with `unreadable: true`, one a newer version saved never. Exportable; to a restore they are `data`, with room for twice the limit. Not in the API or the MCP server: the figures exist only in the browser, and tokens have no scopes.
- **Currency.** A scenario's amounts are in the Plan's currency and carry it (`currency`, recorded with its first amount); one whose currency isn't the Plan's isn't run until the person says its amounts are in the Plan's. Once the Plan's own currency is recorded ([above](#storage-seam)) that is offered at once, since nothing can move it; while the Plan has nothing typed, and follows its accounts' currency, only once `shownReliably` holds; and while it isn't known, not until the person has said. Nothing is converted either way, as the Plan's typed figures never are.

## Splits and groups

A split transaction (#39) counts as its parts, each with a category of the person's own, and a group of transactions counts once, at its net, in its own category. Both are applied on read, last, in the one place every reader shares, and never written into a stored row: unsplitting or ungrouping shows the rows exactly as before, and the app, the read-only API and its MCP server, reports, the Plan and the download all count the same parts and nets.

**Where they are kept.** Two map stores on the storage seam, encrypted, exportable, each with a closed shape (a field this release doesn't know makes a record unrecognised, never half applied, since a part a later release leaves out of a total would otherwise count here):

- `transaction-splits` (`lib/splits.ts`), one record per split transaction, by its id (a bank's, a manual, imported or SimpleFIN row's, or a row's imported into a linked account from its bank's files): its parts, each a random id, an amount in Plaid's sign, a category by id and optionally a note and `excluded`, and the amount and currency the transaction had when it was split. The route saves one only when the parts add up to the transaction exactly in its currency's minor units (`checkParts`: cents, whole yen, eight places for a currency without an ISO code, with a float tolerance relative to the amount), each of the transaction's own sign; a pending transaction is refused (409: the posted one gets a new id), and so is one in a group. Each part row carries its record's `updated_at` (`split_updated_at`), which an edit sends back, so one made from a split another device changed since is refused (409) instead of saved over it.
- `transaction-groups` (`lib/groups.ts`), one record per group, under a random id: its name, its category by id, its transactions by id, its day (its earliest transaction's when it was saved), their one currency, and how many of them went since (`removed`). The route refuses a pending transaction, a split one or a part, one in another group, a mix of currencies and a span over a year (`checkMembers`), and looks every transaction up in the stores first (`lib/txn-lookup.ts`: the banks' stores, the manual and SimpleFIN books, and the rows imported into linked accounts, found whether they count now or a bank row stands for them), refusing with a 409 rather than guess when a store that could hold one can't be read.

**The read path.** After step 6 of [the rules' read path](#tags-notes-and-rules), once every row is filed, `finishActivity` reads both stores (display reads: what can't be read is a note, never a stop) and hands the rows to `expandSplitsAndGroups` (`lib/split-rows.ts`, pure, shared by the browser). Groups first: a group's transactions that are here are replaced by one row (`group:<id>`) at their net, filed under the group's category, on the group's day and its first transaction's account, carrying their tags, with them inside it (`group_members`) for the Activity tab; one that isn't here (removed, on a hidden account, not read this time) is left out and counted (`group_missing`), with why where the read knows it (`group_away`: counted in another group, by name, or a row imported from a file that a bank row still pending stands in for). A group dated before the read's first day (`from`, finishActivity's cutoff) counts on a day outside the read, so it has no row and is never answered at part of its net: its transactions that are here are listed on their own, each marked with the group (`group_outside`), and `countsInTotals` counts none of them (nor the day figures, the calendar and the Plan, which leave them out as they leave out what was excluded); the API gives their `transaction_group` with a `net` of `null`, and a report's appendix says they count in a group before the period. A group whose transactions are in more than one currency now leaves them on their own, each marked with the group (`group_unapplied`), so the Activity tab offers to ungroup it. An ended account's rows from its end (lib/lifecycle.ts) are never read by the app, so a group nets only its transactions still counting; a reader that keeps them and leaves them out itself (`keepEnded`, a report) passes the ends (`endedFrom`, `ended`), so those rows stay whole, never split nor in a group, and are left out, and counted, once each. Then splits: a split transaction is replaced by its parts (`split:<part id>`) in its place, each with its date, merchant as shown, account, currency, source, tags and rule ids, its own amount, category (merges followed) and note, and `split_of`, `split_index`, `split_count` and `split_parent` (what differs from the whole). The transaction's exclusion or a rule's hide reaches every part; a rule's category never reaches a part, only the remainder; its note stays on the transaction. When the bank changed the amount since the split, the difference is one more part (`split-rest:<id>`, `split_remainder`), filed as the transaction would be, so every total stays the bank's. A split that can't be read, or whose transaction is in another currency now, leaves the transaction whole and marked (`split_unread`, `split_unapplied`); groups that can't be read leave their transactions on their own; both with a note. A transaction in a group and split as well (only two devices at once can make one) counts whole in the group. A posted bank row standing for rows imported from files (#52: `stands_for`, which finishActivity reads before the layers take it off, passed as `stands`) takes the first of their splits, earlier imports first, and their places in groups, as it takes what was said about them; its own split or place in a group comes first. Its parts, and its row in the group, name the imported row the split or the place is kept under (`split_carried_from`, `group_carried_from`), which the Activity tab's edits send. The routes refuse a split or a group of the bank row's own while it shows them (409, `importedStoodFor` in `lib/txn-lookup.ts`, which works out what each bank row stands for as the read does, strictly about the accounts the request touches: a connection whose accounts can't be read refuses only a request on an account of its own or one a link touches, whose earlier id may be live there again), so a crafted request can't hide them; one it has already (two devices at once) comes first. The imported row doesn't count while the bank row stands for it, so the transaction is counted once, and when the bank row goes the imported row is split and grouped again as it was; a split edited meanwhile adds up to the bank's amount, so the imported row's remainder then holds the difference from the file's, which the Activity tab words as the bank's transaction that stood for it having gone (`splitAtBanksAmount`, `components/SplitRows.tsx`), not as an amount that changed.

Every total then counts what it is given, by `lib/spending.ts` as before, and no consumer changed for it, except the few that must read each transaction once, as the bank has it, which call `bankRows` to put a split one back whole (with its parts beside it, `split_parts`) and a group's transactions back on their own: recurring detection (a bill is looked for in the bank's transactions, never a part or a net), Home's biggest purchase, the Budgets calendar's list of what posted, the quick-add form's payees, the API's list of transactions (each once, with `splits` and `transaction_group`), counts of a tag's or a rule's transactions, a rule's preview, and a category's use. Goals (`lib/goal-flows.ts`) count what moved on each account: a group's transactions each on its own account at its own amount, never the group's net on one of them, and a split transaction's parts, which add up to it. Budget rollover reads the same rows (`lib/budget-month.ts`), so carries and the income pool count parts by their categories and a group's net in its category, and a split or a group made in a past month changes them on the next read. Counts of transactions beside the totals (`summarize`, `categoryTotals`, `spendingByTag`, the API's categories, groups and budgets, the Plan's, a report's and the Activity tab's) count with `transactionCounter` (`lib/spending.ts`): a split transaction's parts are one transaction, and a group's row is as many as it holds, so each count means what it meant before splits. Recurring detection's older rows (`OlderTxn`) are the bank's, never expanded.

**Where they go.** As what was said about a transaction goes (`lib/txn-annotations.ts`), by the same rules, at the same moments, one line at each (`lib/split-gone.ts`): a sync that saved the bank's removal, a disconnect and a forget prune the splits and group members no stored Item holds (both stores' records read first and the transactions' stores after, once; nothing while a store of transactions can't be read or is behind, never a record this release doesn't recognise); deleting a manual row or account, undoing an import (into a manual account, or into a linked one: `lib/history-import/commit.ts`), forgetting an earlier account's imported rows and letting a SimpleFIN account go forget theirs. A row imported into a linked account is never pruned with the bank's: no Item holds it, and it is kept past a disconnect, its split and its places in groups with it. A group left with no transaction goes. Neither carries across a re-link ([features.md](features.md#removing-an-institution-and-adding-it-back) says why), so the disconnect confirmation first asks how many of the connection's transactions are split or grouped (`GET /api/transaction-splits?item_id=`, `lib/txn-lookup.ts` splitsAndGroupsOn) and says so.

**The download** applies the same `expandSplitsAndGroups` to the file's own rows (`lib/export-splits.ts`): the transactions CSV keeps each transaction's row and `amount`, and adds a row for each part and each group's net, with `nya_amount` what the app counts (empty on a split transaction, a grouped one, and a pending one its posted one replaced), so neither column counts twice. An OFX statement lists each transaction once, whole, with its parts or its group in the memo when they fit, as they apply over every row of the file, the imported rows that count among them (`appliedSplitsOf`, worked out once per statement). Both pass the file's imported rows' `represents` as `stands`, so a bank's row standing for one is split and grouped as the app does it. Reports read the same rows as the app, and their appendix says which part of which transaction a row is. Sharing reads stored rows directly and applies neither.

**Cost.** Two more `HGETALL`s per read, of records people make by hand (at most 5,000 splits and 2,000 groups), and one pass over the rows.

## Sharing

`lib/sharing.ts` is the only code that reads another person's container: it builds the owner's `Ctx` from the owners map, passes it read-only to what builds the other person's view of the share (`projectShare`), and makes its only two writes there in the records of showings (`recordShowing`, `forgetShowings`). Its header has the model, and [authentication.md](authentication.md#sharing-between-people) has it as people see it. Nothing it returns carries the `Ctx` or anyone's user id, and every read on this path asks not to tidy as it goes (`readOnly`), so a share is never a write to the owner's data. Nothing on it calls Plaid.

**Accounts** are projected in `lib/sharing.ts` itself (`sharedAccounts`): each account at its level, from the stored balances and transactions. **The other kinds** (#45 step 3, `lib/share-kinds.ts`) are projected in `lib/share-views.ts`, one function each, built up field by field on the reads the owner's own screens and the read-only API use, never arithmetic of their own, so a share can't say what the owner's app contradicts:

| Kind | Built from | Never in it |
| --- | --- | --- |
| Net worth | `readNetWorthAndHistory` (`lib/api-read.ts`): each counted account's newest measured balance added up per currency, the total in the one most accounts are in shown and the others named; the history the chart draws (`getHistory`, hidden accounts subtracted, ended ones from their end day), one point a week (`sampleSeries`); at "total", `readNetWorth`, the same total without drawing the chart. With its accounts, `readAccounts`, listing only those whose balances the share of accounts shows (`balancesShown`, from `sharedAccounts` as it is read beside it) | an account's name or balance unless its own share shows its balance and the accounts are chosen, any account id |
| Spending | The Activity tab's assembly (`assembleBankRows` and `finishActivity` in `lib/activity.ts`, never syncing) and `summarize` (`lib/totals.ts`) for each of the last six months, rolled up by the owner's category groups; what another currency left out from money out alone (`leftOutByCurrency`, as the budgets count it), named by currency; a month counting a transaction whose exclusion couldn't be read (`exclusion_unknown`) says so, as the Activity tab does, and so do spending and budgets when how the owner files rows couldn't be (`filing_unread`: their own categories, their merchants' defaults, `defaults_unread` from `finishActivity`, or their approvals in the review queue) | money in, a transaction or its id, merchant, note or tags, a split's parts, a group of transactions, how many there were |
| Holdings | `allocate` (`lib/allocation/allocation.ts`), the Plan tab's allocation, over `readAccounts` and `readHoldings` (the positions last recorded), with the owner's allocation settings | an account's name, number or id, a security's id, a quantity, a price, a cost basis |
| Budgets | `readBudgetMonths` (`lib/budget-month.ts`, `readBudgetMonth`'s read for several months from one read of the transactions, the income setting left unread with `pool: false`) and `budgetsAnswer` (`lib/api-read.ts`, `readBudgets`' own answer from the month read) for this month and last | the income pool, a transaction, how many in another currency |
| Goals | `readGoals` (`lib/api-goals.ts`, which runs the Goals card's `lib/goal-view.ts`), the chosen goals only | a goal not chosen, archived, or on a hidden account; its monthly rate, what each month needs or is short by, its allocation |

Each kind is caught on its own (`projectViews`): an error that says the data can't be used (`StoredDataUnreadableError`, a transaction store that can't be decoded) makes that kind `{ unreadable: true }`, and the rest is shown; anything else (storage out of reach) throws, and the share isn't shown. A total that would be short of transactions that couldn't be read (a bank's stored ones, a manual account's book, rows imported from files, which `transactionsDamaged` finds from the banks' notes for spending and budgets alike) is unreadable too, never a short figure; one short of transactions not yet in (a bank still bringing in its history, a bank account or card whose transactions don't come in) is shown, and says so. "This month" is the owner's: the month in the time zone their weekly summary keeps (`weeklySettingStore`, read leniently), else by the UTC day as the read-only API counts it. Every percentage is sent with its words (`label`, `shareLabel` in `lib/allocation/allocation.ts`), worked out where the amount is known, so none says 0% of money that is there. What more than one kind reads (the accounts, for a net worth with its accounts and for holdings) is read once per projection.

**Settings** are kept in the share record, under `views`, beside `accounts` (the `lib/sharing.ts` header), and read closed (`parseViews` in `lib/share-kinds.ts`): a kind, a level or a field this release doesn't know is shared as nothing. The drawer's change is checked as a shape by the route and in full by `saveConnection` before anything is written.

**What the viewer could work out** is `lib/share-inference.ts`: pure rules over everything shared on a connection together, run on the owner's device by the drawer over what is being chosen, and by `previewShare` over what is shown (the preview's `inferences`, never part of what the viewer is sent).

**Records of showings** count, beside each account's level, each kind as it was shown (`views` on a quarter hour, `lib/access-log.ts`): its setting's level and options, and of goals the ids shown, merged widest within a quarter hour (`mergeViewsRead`) and given to the drawer by day with goals counted (`DayViews`); a kind that couldn't be read never.

**A limit on reads.** `/api/shared` and `/api/connections/preview` each count one read in the asker's own container (`sharing-reads`, a counter store in `lib/share-limit.ts`): `SHARED_READS_PER_WINDOW` in `SHARED_READS_WINDOW_SECONDS` (`lib/share-rules.ts`), then 429 with `Retry-After`; a count that can't be taken answers 503, never an open door.

## Review queue and merchant defaults

The review queue (master plan M3, from YNAB's approve step and its Card Mode, with ZeroSum's rule that an approved entry is never silently overwritten) and a merchant's default category (YNAB's payee default: it changes only when two of the last three categorizations agree) are applied on read, in the one place every reader shares, and never written into a stored row.

**Where they are kept.** Three stores on the storage seam, encrypted, exportable, each with a closed shape:

- `transaction-approvals` (`lib/review-store.ts`), a map store, one record per approved transaction under its id (a bank's, a manual, imported or SimpleFIN row's, or one imported into a linked account), never under anything taken from what it says: the amount and currency, the category by id, the name as shown and whether it was pending, as the page showed them when the person approved it (`approvalInputOf`). The page sends that snapshot, so what is approved is what was seen; a row the bank changed meanwhile reads as changed on the next read. Writes read what they replace strictly first (`getMany`) and are refused whole over a record that can't be read; an undo puts back what an approve replaced, only while the record is still the one it wrote (`approved_at`). At most 50,000 (`MAX_APPROVALS`), 500 a request; past that, approving is refused, saying how to make room: `make-room` forgets the 10,000 oldest by `approved_at` (`makeRoom`, `ROOM`), once the person confirms on the Review queue card, which `GET /api/review` tells how many are kept (`approvals: { kept, max, room }`). An edit of a manual row's amount or currency (`app/api/manual-transactions`) carries its approval to the new figures (`followEdit`): the person's own word, never taken for the bank's.
- `review-settings` (`lib/review-store.ts`), a value store: whether the queue is on and its first day (`since`). Turned on from today as the page has it (checked to be a day some time zone is in now), or at most 31 days before.
- `vendor-defaults` (`lib/vendor-default-store.ts`, the rule in `lib/vendor-defaults.ts`), one compressed value store: each merchant's last three categorizations and its default (`{ category_id, since, set_at, previous? }`: the categories it had before it moved, each with its days, `{ category_id, since, until }`, at most `MAX_PERIODS` of them), under a random id. A vendor key holds a merchant's name (`nm:<institution>::<name>`), so it is kept inside the ciphertext, never as a field name; one value changed by compare-and-set (`ValueStore.update`), so two categorizations at once never lose either, rather than a map whose racing first votes could make two entries for one merchant. At most 1,000 merchants: past that the one without a default categorized longest ago makes room.

**The read path.** `finishActivity` reads the settings and the defaults beside everything else, and the approvals of the rows it reads once it has them (`lib/review-read.ts`: by id, `getMany`, after one count that saves the read when nothing was ever approved), each a display read: what can't be read is set aside and named, never taken for "none". `lib/txn-layers.ts` calls `applyReview` (`lib/review-layer.ts`, pure, shared by the browser) for each row after the rules, with the person's own category as it was before them:

1. A merchant's default files a row with no category of its own and none from a rule, dated on or after the default's day, in the category it had on the row's day (`defaultOn`: a default that moved files what came before the move under its earlier category, so a move never re-files the past), never one side of a pair between SimpleFIN accounts (`filed_by_default`, with the entry's id, how many of the last three agree now, and `earlier` for an earlier category). Only clearing the default, the person's own act, takes back what it filed.
2. The approval under the row's id, else, for a posted row, under the pending one it replaced (`pending_from`, Plaid's `pending_transaction_id`, kept on display rows and never sent) or under a row imported from a file it stands for (`stands_for`): `review_via` names where it is kept. While there is one, a row with no category of its own that the layers would file elsewhere now is filed where it was approved instead (the layers' slot, `rule_category`, and its words, as a rule's are), with what would file it now offered (`review_suggestion`: the category and whose, a rule's with its id, a default's or the bank's), whether or not the approval holds, so a category the person chose never goes with an amount the bank changed; an approval under the uncategorized category pins nothing, so a rule or a default fills it. It holds while the amount and currency are the approved ones in the currency's minor units (`sameAmount`): then the row is `reviewed_at`, and a name that differs shows, with `approved_name`.
3. An approval that doesn't hold (the bank changed the amount) is `review_changed`, with what it was approved at. A bank row standing for an imported row keeps standing for it once the bank changes its amount (#52, `lib/history-import/twins.ts`), so the imported row's approval still applies, and no longer holds, and the row also carries `imported_amount`; when that is the amount approved, the views say the change once (`changedSinceWords` in `components/review-text.ts`: beside the row's own note on the Activity tab, only the approval; in Card Mode, the two in one). Then, with the queue on, a reviewable row (the bank's, a connector's, a file's: `reviewable`) dated on or after `since` with no approval that holds `needs_review`. An approval that can't be read, or settings that can't be, leave `review_unknown`, never `needs_review`.

The rows before the year, which only recurring detection reads, are filed by the same defaults and approvals and carry no marks. Every row is then filed by `resolveCategory`, whose layers' slot holds what step 1 or 2 put there. Splits and groups come after, as always: a split transaction's parts carry its marks (they copy the transaction's own fields), a group's row its transactions' (`group_members`), and `countToReview` counts transactions as `transactionCounter` does. `finishActivity` returns the queue's state (`review`, sent by `/api/transactions`), notes for defaults and approvals that can't be read (they change totals, so reports carry them, among their caveats: they leave no transaction out, so they are never a report's gaps), and a note for the settings apart (`review_note`, for the app only).

**Everywhere.** The read-only API gives every transaction `needs_review` (`null` when not known) and `reviewed_at` (`lib/api-read.ts`), additive, as version 1 allows; the MCP server's search says the same. The download files rows with the same layer from its own parts (`lib/export-layers.ts`: `transaction-approvals`, `vendor-defaults`), so a CSV's `nya_category` is the app's. A rule's preview counts the matches that stay where they were approved under another category than the rule's (`keep_approved`, from the approvals read by id). Sharing applies neither, as it applies no rule.

**Writes and their undo.** `app/api/review` turns the queue on and off, approves, undoes and repairs (only damaged records, once confirmed: `MapStore.replaceUnreadable` with a placeholder, then removed while it is still that placeholder). `app/api/recategorize` records each categorization by id with its vendor key (`recordCategorization`, best effort: the category saves either way), keeps an approved transaction's approval holding the category chosen (`noteRecategorized`, under the row's id or the one it names, `review_via`, which the page sends), and answers what the category was before (the override, or a manual row's own) and the merchant's entry before and after; `restore` puts the category back exactly, and `app/api/vendor-defaults` (`restore`) the entry, only while it is still exactly what the vote left (compared whole, since two votes can share a millisecond): Card Mode's undo. A category used by a default (now, or in an earlier category's days), or by an approval of any date, can't be deleted (`lib/category-usage.ts`); a merge is followed by id.

**Where they go.** As splits go (`lib/split-gone.ts`, the same moments and rules): a sync that saved the bank's removal of a transaction, a disconnect and a forget prune approvals no stored Item holds (the removed ones read by id; damaged ones go too, one this release doesn't recognise never), and deleting a manual row or account, undoing an import or letting a SimpleFIN account go forget theirs. Before that prune, the sync moves a removed pending transaction's approval to the posted row that names it (`carryApprovalsToPosted`, from the rows it just saved), unless that has its own. Approvals don't carry across a re-link.

**Cost.** One count, and when anything was approved one read by id of the rows read (a few thousand fields in batches of 1,000), plus two small values, per read; one pass over the rows.

## Containers

Every record belongs to a container, stored under `<prefix>:c:<container id>:`. A container is the unit of one person's data: with Clerk each account owns its own, and with the shared password the deployment uses a single one. Every function that reads or writes stored data takes the container, so a key cannot be built for a container nobody resolved. See [operations.md](operations.md#containers) and [authentication.md](authentication.md).

## On-device snapshot and offline use

The dashboard keeps its last-known snapshot in the browser's `localStorage` so the PWA opens instantly and still shows balances offline. The service worker never caches `/api/*` responses, so refreshing, linking, transactions and the Plan tab's saved assumptions need a network connection. The Plan tab's code is fetched the first time the tab opens (the service worker keeps a copy once it has been fetched); if that fails, the tab says it couldn't be loaded and offers to try again, and the other tabs work as before (`components/PlanTabLoader.tsx`). The snapshot is readable on the device without the app password; see [authentication.md](authentication.md#what-is-not-covered).

## Hiding amounts

Hiding amounts ([features.md](features.md#hiding-amounts)) is applied where amounts are written, not where they are drawn, so no screen can miss it. `lib/format.ts` holds the one flag, and while it is on its formatters (`formatMoney`, `signedMoney`, `compactMoney`) write an amount as its sign and currency, placed by the locale (`Intl.NumberFormat.formatToParts`), around one mask for the figures (`hiddenMoney`). Every amount on screen goes through them: the components' own helpers (`fmt` in the dashboard, `money` in the cards, the Plan's `wholeMoney`, the calendar's cell figure, the payoff plan's and investment activity's) delegate to them or check the flag first, and the sentences built from amounts (goal outlooks, insights, forecast notes, carries, the report's figures) are written by them, so they are hidden too. A figure written some other way (a holding's quantity, a rule's amount) goes through `hiddenFigure`, text the server wrote with an amount in it (a balance that changed since a form opened, a card a connector reports as money held) through `hideAmountsIn` where it is shown, and a file's own figures, which carry no currency to tell an amount by (a CSV file's lines in the mapping step), through `hideFiguresIn`. The two memos that keep sentences with amounts (Home's insights, the forecast's notes) list the flag (`useAmountsHidden()`) among their dependencies, so they are worked out again when it changes.

Four rules keep it so for code still to come, and `test/hide-amounts.test.tsx` holds every module a page can load to them (`test/amount-sources.ts`: every component and every `'use client'` module, and all they import, read as source, its JSX included; `test/amount-sources.test.ts` holds the scan itself to each shape below). An amount is written by the formatters, or by code that writes the mask in its place while the flag is on: through `hiddenFigure` or `hiddenMoney`, in a statement choosing by `amountsHidden()`, or after its function has returned when it is on (`if (amountsHidden()) return ...`); never with `Intl.NumberFormat` (with `new` or without) or `toLocaleString` given a currency, fraction digits or compact notation, nor with `toFixed`, `toPrecision` or a `toLocaleString` given no options, nor a "$" written by hand. A number written those last ways is taken for an amount unless the code beside it says what else it is: a "%" or a fraction made one by a hundred, a size or a time after it, a drawn shape's coordinate or a color's channel, a number rounded as a number (`Number(...)`, but not one drawn as it is), or a count, followed by the word for what it counts or going on with its sentence (never one an amount is followed by: "spent", "a month"), its noun chosen by it, or a length. Any other number that is nobody's amount (a count said some other way, a bound the app sets on a field) goes through `plainNumber`, and an amount put into a form's field to be edited, its figures alone, through `fieldAmount`, which the CSS hook below covers, and which is never drawn as text. Nothing keeps a written amount where the flag can't change it: a `useMemo` whose callback writes one (itself, or through any function of its module or one it imports that does, called or handed to a call) lists the flag in its dependencies, a component in `memo()` that writes one reads the flag, and no `useState` starts from one. A label a screen reader reads alone (`aria-label`, `aria-valuetext`, `aria-description`, `title`, `alt`, a field's `placeholder`) built from an amount goes through `spoken`, and an amount drawn as text goes through `Masked` (text that can't hold markup is let be only where it is said some other way: SVG text in a chart drawn as an image, `role="img"` with its own label, or hidden from a screen reader, and an option with an `aria-label` of its own): one written anywhere a child expression draws (alone, in a template literal, a ternary's branch, a list, or a call given a formatter as a callback; not in what a ternary or `&&` only tests), a variable given one (a `let` given one later, a list or a map one is put in, a callback's parameter given their items, what is destructured from a function's return, each by the members that hold one), a formatter handed to a component as a prop and called there, or kept in a variable or an object handed to a call, or a parameter's default, a prop given an amount, and text the server wrote through `hideAmountsIn`. `test/amount-sources.test.ts` also holds the scan to the app itself: drawn bare, each amount the app draws through `Masked`, and said as it is, each label it says through `spoken`, must be reported, but for a short list of text that never holds one. A number drawn as it is (`{account.balance}`) is no shape the source can tell from a count, so `test/hide-amounts.test.tsx` backs the scan up: it runs the view suites with each render made again with amounts hidden (`test/hidden-renders.ts`), and no figure may show in their text, the labels read alone or an option.

Only the browser sets the flag: `components/hide-amounts.ts`, which keeps the choice in `localStorage` (`nya:hide-amounts`, read leniently: what can't be read is shown), reads it when the page loads the module, before the dashboard or the report page draws its first amount (the server renders their loading state, with no amount in it), and follows a change made in another tab (the storage event). Components draw again when it changes (`useAmountsHidden`, a `useSyncExternalStore` whose server snapshot is "shown"); the dashboard and the report page subscribe at their root, so everything under them is drawn again. Where there is no browser, `setAmountsHidden` refuses to turn the flag on (there it would be the whole server process's), so routes, the read-only API and MCP server (whose goal sentences are written by the same `lib/goal-text.ts`), reports' CSV, emails and the downloads always carry the figures, whatever is rendered there; `test/hide-amounts.test.tsx` holds that, and, scanning the source, that only the switch calls it. The report page shows the figures while the browser prints (`showFigures`, from `beforeprint`, drawn at once with `flushSync`, to `afterprint`).

While the flag is on, the root element carries `data-amounts="hidden"` (marked once the page has hydrated, never under React), the CSS hook (`app/globals.css`, "Hide amounts") for what no formatter writes: a field holding an amount (`inputmode="decimal"`, the budget fields, but not one marked `data-percent`: a rate or a share) has its own text drawn transparent and one fixed mask drawn instead (a background image at the text's start, sized to its font), the same whatever its length, until it has focus; an empty one shows its placeholder, which every such field has (an example, or `NO_EXAMPLE`, one space, where it has none to give: `:placeholder-shown` never matches a field without one, which would draw the mask in it empty; `test/amount-sources.test.ts` holds every field to it). For a screen reader, `spoken` says each hidden amount as "hidden": every label built from an amount goes through it, and every amount drawn as text (a figure alone, a table's cell, or a sentence with amounts in it) is drawn by `Masked` (`components/HideAmounts.tsx`), which hides the bullets from it and gives it the spoken words instead. A select's option can't hold markup, so one with a hidden amount is given its spoken words as its `aria-label` (`spokenLabel`), which browsers give screen readers, though a phone's native list may read its own text. Each screen the test renders is checked for text given to a screen reader with the mask still in it.

## Security headers and the public pages

The headers that are the same on every response (HSTS, nosniff, the referrer policy, the permissions policy, `X-Frame-Options` and the opener policy) are set in `next.config.js`, so they also reach static files and the routes the proxy skips. Each page's Content-Security-Policy is built per request in `proxy.ts` (`lib/security-headers.ts`) with a fresh nonce, which Next.js puts on its scripts and Clerk on its own (`ClerkProvider`'s `dynamic`, `app/layout.tsx`); `CSP_MODE` sends it report-only (the default), enforced, or not at all. It is the only Content-Security-Policy: a browser enforces every one it is sent, and how Vercel combines a `next.config.js` header with a proxy header of the same name is not documented. The app writes no inline script of its own: the service worker registers from a client component. How to check the policy against a live Plaid Link and Clerk session and then enforce it is in [deployment.md](deployment.md#security-headers-and-the-content-security-policy).

`/security` and `/privacy` say in plain language how the data is protected, who can read what, and how long things are kept. They are readable without signing in (`PUBLIC_PAGES` in `proxy.ts`, which still runs on them, for the policy), read no stored data (from the environment, only `CSP_MODE`, whether a usable `MASTER_KEY` is set, which decides whether `/security` describes envelope encryption or the single key, how backups are kept: `backupRetention()` in `lib/backup.ts`, the rule the deletion receipt dates by, so the pages and a receipt give the same number of days, and `DATABASE_BACKUP_DAYS`, what a data key per account does at a deletion, said conditionally and in the same words on both (`keyDeletionText` in `lib/deletion-receipt.ts`), and whether this copy sends email, `sendsEmail()` in `lib/notice-recipients.ts`: mail set up in `lib/mail.ts` and someone it may write to, Clerk's accounts or `NOTIFY_EMAIL`, which decides whether they name an email provider), and are held by `test/public-pages.test.tsx` to the code's figures and to a list of claims they must never make (that nobody but you can read the data, that it is encrypted end to end, that deletion is instant and complete).

## Your data, and storage across accounts

**Your data** (`/your-data`, `/api/data-inventory`, [features.md](features.md#your-data)) is the data map the privacy page promises, for one person's own container. `lib/inventory.ts` is its registry: one entry, in plain words, for every key family on the old lists (`lib/key-families.ts`) and every store declared on the seam (`lib/stores.ts`), with what one stored entry is, the privacy page's retention row it is kept by, who else can see it and the plain text it carries. `test/inventory.test.ts` fails while a family or store has no entry, while an entry names one that is gone, and while a retention row it names is not on the privacy page word for word. Whether a kind is encrypted is not written there but follows from how it is stored (its kind on the lists, or its store's), and whether it is in the download from the download's own lists (`STORED_KEYS`, and each store's `exportable`, with the parts that carry a store under another name), so the page can't say what the code doesn't do.

`lib/inventory-read.ts` measures the container through the seam with `measureContainer(ctx, { heads: true })`, adds up each key's entries, bytes and claimed keys by the kind it belongs to, compares the claims with the container's own key (`readContainerEntry`), and counts the few kinds kept for the whole environment from their plain-text records: the container's registry entry, the owners entry for the signed-in account, its sharing connections (`myConnections`) and its data key. Each look is counted first, thirty an hour (`inventory-reads`, `lib/inventory-limit.ts`), since it walks the keyspace, as the restore's look at whether an account is empty is. It is lenient, for display only: a step of the measure that fails makes the kinds it held unreadable, with null figures, never zero; a walk that fails makes every kind in the container so (`measured: false`); and a key no kind names is counted (`unknown`). Nothing is decrypted.

`measureContainer` (`lib/repo.ts`) is the seam's operation over a whole container, and `measureContainers` the same for several with one walk: a SCAN of the container's prefix, then `MEASURE_KEYS`, one Lua step per hundred keys, which answers each key's type, entries (a string is one, a hash its fields), bytes (field names and values together, as Redis stores them) and largest value, and with `heads`, how many of its values claim each key, from their first 64 bytes inside Redis: a versioned value's key id, `k0` for an unversioned value of base64 long enough to be ciphertext, `?` for a versioned value whose id can't be read, `-` for anything else. A string's head is read with `GETRANGE`; a hash value has no such read, so at most `HEADS_STEP_BYTES` (4 MiB) of them are read whole inside Redis a step, and the rest are `+`, not looked at, so a step never holds Redis for long. No value leaves Redis. A step that fails names its keys in `unmeasured`; a walk that fails throws. Its contract tests run on the double and on a real Redis.

**Storage across accounts** (`/admin/storage`, `/api/admin/storage`, `lib/admin-storage.ts`, [operations.md](operations.md#storage-across-accounts)) is the admin's, decided as `lib/admin-items.ts` decides. The page lives at `/admin-view/storage` (`app/admin-view`), and no route answers `/admin/storage` itself: `proxy.ts` rewrites the admin's request there (`lib/admin-gate.ts`, which reads, and never makes a container), and lets anyone else's go on to no route, so they get the 404 any missing path gets, header for header, where a page that calls `notFound()` would send its own segments, and a rewrite would say so in a header; asked for `/admin-view` directly, anyone else is rewritten to a path no route matches. The page checks again, in `generateMetadata` too, so its title is never made for anyone else; the route answers them with the JSON 404 of the admin's other route. A page of containers in id order after a cursor, at most 50, measured with one walk (`measureContainers`, without heads), beside three plain-text records, read four containers at a time: the Items' (`getItems`; the access token inside is never opened), the daily check's (`readUsage` in `lib/item-usage.ts`, a damaged record said as one) and the snapshot's newest run (`readNewestRun`, a damaged one said as one, never an older run in its place). The blobs per Item, the markers beside them and the connector counts are read off the measured key names and entries. Each part is read leniently and apart, so one that fails is null, said as such, never zero, and costs the others nothing.

## The read-only API and the MCP server

`/api/v1` and `/api/mcp` read one container's stored data for a program holding a personal API token (`lib/api-tokens.ts`; how tokens are made, kept and checked is in [authentication.md](authentication.md#api-tokens)). Each operation is declared once, in `lib/api-spec.ts`: its path, summary and arguments. That one declaration checks a REST query (`argsFromQuery`) and an MCP tool's arguments (`argsFromJson`), gives each tool its JSON Schema, and lists the parameters on the developer page, so the three cannot disagree. What an operation runs (`lib/api-ops.ts`) is a thin call into `lib/api-read.ts`, which reads only what is stored and never calls Plaid: each balance is the newest measured one in the recorded history (`latestMeasuredBalances` in `lib/history.ts`), transactions are what the last sync stored, assembled exactly as the Activity tab assembles them (`lib/activity.ts`, shared by both, with the connections that bring in none and why: a connection never synced is judged by the sync's own check, made from what is stored, in `storedItemTransactions`), and every total follows the Budgets tab's rules (`lib/totals.ts`). Rows imported into linked accounts come with them, through the same assembly; balance history names the stretch of estimated points walked back through them (`from_imports`). Budgets are read by the same read as the Budgets tab's month (`lib/budget-month.ts`), back to the first month a carry counts, with their rollover and the income pool. The cash flow is read by `lib/api-cash-flow.ts`, on the same assembled rows, through the flows the Activity tab's chart draws (`lib/cash-flow.ts`, [above](#cash-flow)). The runway and year over year are read by `lib/api-reports.ts`, through the report page's own reads ([above](#runway-and-year-over-year)). Savings goals are read by `lib/api-goals.ts`, beside it, on the same accounts and the same assembled transactions, through the view the Goals card runs (`lib/goal-view.ts`), so the two tell a goal alike. Recurring bills are detected as the dashboard detects them, from those rows and the older ones a yearly bill needs (the assembly's `history`), with the series the person marked not recurring left out (`lib/planned-store.ts`, matched by `dismissedSeries`) and the monthly total added as the Budgets tab adds it (`recurringMonthly`). `lib/api-http.ts` is how a REST route answers (the token, its limit, the query, one error shape), and `lib/mcp.ts` the JSON-RPC methods over plain JSON, one message per request (no batches), without sessions. Once the person has chosen a home currency, `/me` says it and their own rates, and accounts, net worth and balance history add `base_currency`, each balance's and each point's `to_base`, and net worth's `base`, converted as the app converts ([above](#exchange-rates), `lib/fx/api-base.ts`); every version 1 field keeps its meaning, and only the API's own answers ask for them, so goals and shares, built on the same reads, read no rates. `/developers` is a public page like `/security` (`PUBLIC_PAGES` in `proxy.ts`), and reads no stored data; its examples and field descriptions (`lib/api-examples.ts`) are held by `test/developers.test.tsx` to the API's real answers.

## Writing through the API

Where `API_WRITES_ENABLED=1` (`lib/api-writes-enabled.ts`; [operations.md](operations.md#letting-api-tokens-write-and-rolling-back)), a token made for it can change manual accounts and their transactions, categories, groups and tags ([features.md](features.md#writing-through-a-token)). The pieces:

- **Access, chosen once.** A token's record (`lib/api-token-store.ts`) has an optional `access`: absent for a read token, so one made before stays read for good; `balances` or `write`, which the release before reads as a record it doesn't know, so a rollback fails closed. Only `createToken` writes it. `write` names exactly `WRITE_V1` in `lib/api-spec.ts`, pinned by a test: a later kind of change gets a new access value.
- **One gate.** Every operation, a REST read (`serve`), a REST read of one resource or a write (`serveResource`, `lib/api-http.ts`) or an MCP tool (`lib/mcp.ts`), passes `lib/api-run.ts` before it reads its input: the operation's `allows` against the token's access (403 `insufficient_scope`), the switch for anything beyond reading, and for a write, 30 writes a minute per token (`api-write-requests`). The gate's answer (`Gated`, which only it makes) is what the resource runner (`runResource`) requires, so nothing runs an operation without it. So a tool the MCP server didn't list is refused when called by name, as its endpoint refuses the token. The day's limits (`api-write-days`: 500 changes and 100 creates per token, 2,000 changes per person) are all checked before a change, counting nothing (`checkDay`, the seam's `CounterMapStore.peek`), and counted once it is made (`countDay`), so a refused change, a balance that changes nothing and a create sent again count against no day, and one token past its own limit leaves the person's alone. Writes at the same moment can each pass the check, so a day can end a few past its limit. The same store counts, per manual account, a balance set through the API that day, so the estimated history is rebuilt at most once a day for it, and marks a push that skipped its rebuild (`rebuild.<account id>`, its window started again by each skip, so it lasts a day past the last), which the nightly snapshot clears the backfill flag for (`lib/api-rebuilds.ts`): the estimate is never more than a day behind.
- **Declared once.** `RESOURCE_SPECS` in `lib/api-spec.ts` declares each resource operation (its path, method, fields with their limits and nullability, which fields it needs or may not mix, whether it takes a version or a key) and `WRITE_TOOL_SPECS` the MCP tools built on them. The same declaration reads a REST body strictly (`readBody`: JSON only, 8 KB, every key once, none it doesn't take) and an MCP call's arguments, gives each tool its JSON Schema, and documents the endpoint on the developer page, whose examples (`RESOURCE_DOCS`, `lib/api-examples.ts`) are held to real answers.
- **The app's own write paths.** `lib/api-writes.ts` runs each through the function the app's own route calls, moved into `lib/` for it: `lib/manual-account-writes.ts`, `lib/manual-txn-writes.ts` and `lib/annotate.ts`, `lib/category-actions.ts`, `lib/tag-actions.ts`. A test makes each change the app's way and the API's way on the same data and compares every stored value. What no write reaches is checked before anything is written: a bank's row, one a connector or a file brought, a linked or connector-fed account (403), a change of type across money held and owed (409), a split or grouped row deleted (409), and room kept for the app (creates stop at 90% of each of its limits).
- **Versions.** `lib/api-versions.ts` digests the stored fields a write depends on (never `created_at` and the like) into a version, keyed with a key only the server holds (derived from `PLAID_ENCRYPTION_KEY`), so a token can't confirm a guess at a field it isn't served; a transaction's has two parts, its row and what is said about it, written apart. `If-Match` is required for a change to something that exists (428 without, 412 for a stale or weak one) and checked inside the compare-and-set that writes, so two changes from one read never both land.
- **Idempotency keys.** A create's key is claimed in the token's entry of `api-change-keys` (SHA-256s of the key and of the request, and the change it makes), in one compare-and-set, for 24 hours. The same request again answers what was made, as it is now; one still in progress, 409 `in_progress`; one that stopped part way is taken over once every route that could still be running it has stopped (`PENDING_MS`, 150 seconds, past the MCP route's 120): its target looked for wherever it could be (found: answered; made and removed since, as its claim's `made` or a trace says: 409, never made again; begun, its change written, and nowhere now: 409 as well, settled `failed`, since a function can stop between the write and the claim's `made` mark, so it may have been made and deleted). Only a claim with no change ever begun under it (the first stopped before it wrote one) is made, under a fresh id, by one takeover alone, the claim pointed at it in a compare-and-set that the other loses.
- **The record of changes.** `lib/api-changes.ts`: one entry per change in `api-changes`, id `<YYYYMMDD>.<token ref or app>.<random>`, so the ids alone (`MapStore.ids`) say what to read for a day or a token and what is past 30 days. A token is named by a ref, a SHA-256 of its id, never the id. Written pending before the change, settled done with the stored states before and after, and taken back out when the app's rules refused the change before it wrote; anything else (storage failing after a write, say) is settled failed, never taken out. Forgetting a change forgets what its undo kept, and the change an undo undid. Pruned nightly by the snapshot job. A token lists its own (`GET /api/v1/changes`); the app's list (`app/api/api-changes`, `components/ApiChanges.tsx`) lists every token's, forgets, and removes a damaged entry.
- **Undo.** `lib/api-undo.ts`: the change made backwards through the same functions, only while its target is exactly as the change left it; a token undoes its own alone, the app any. A change written in one step (a row, an account's details, a balance, a category, a group, a tag) is checked inside the compare-and-set that writes it back; a deleted row added back is checked first, whole (the row nowhere, nothing said about it since), before its first write. An account a token made is checked whole under the links lock, just before the first write: it and every row on it as the token's standing changes left them (their versions), every row made by that token, nothing said about a row but what it said, no split or group, and nothing naming the account (hidden, an end, a goal, a link, a rule, a note, an allocation setting, a dismissed recurring series, or a share of the owner's on a connection, `ownerSharesAccount` in `lib/sharing.ts`, read strictly). Then, under the same lock, its rows and the account go (the app's own delete), and its balance on every recorded day is folded out of each total point by point as the app's forget of a hidden account does (`foldHiddenAccount`, `forgetAccountBalances` in `lib/history.ts`). Each step's name is written on the undo before it is taken (`progress`), and the change names the undo under way (`undoing`, set and cleared in a compare-and-set only while it names what was read, so a refused undo never takes another's name off), so the next undo asked takes one cut off part way up where it stopped; one still pending within `PENDING_MS` is never run beside. An undo refused before it wrote is taken back out; once a step is named it counts as written (the delete takes the rows before the account), so a resume refused under the lock is settled failed and kept, never dropped, and one that stopped after a write is settled failed. One cut off inside its delete never folds a total it can't be sure it took the account out of: a resume that finds the account still named by something else (the person kept it) ends it, recorded failed (`standing`), and one that finds it gone ends it too (`removed`, since the person may have deleted it, and the app's delete keeps past totals); either way `undoing` comes off, so the change can be forgotten, or undone afresh. A refusal after a write is recorded with a code of its own (`RefusedAs`): a row moved back into an account deleted meanwhile is `account-gone`, as the write's is. Forget is refused while a change names an undo under way, which needs its copies to finish.
- **The proxy.** Each new path is exempt from the session gate in `proxy.ts`, at exactly its spelling, an id being one path segment (with `:` or `%3A`), as Next compiles the matcher (tested). While the switch is off, every one of them answers as before writing existed: 405 where the path reads, else 404.

## The weekly summary

The weekly summary email ([features.md](features.md#the-weekly-summary)) is built in `lib/weekly-summary/`, in parts that can each be tested alone:

- **`settings.ts`** is the setting's closed shape and the check a save goes through, safe in the browser; **`store.ts`** declares its stores ([above](#storage-seam)); **`week.ts`** says which week a summary covers and when one is due, on the person's calendar; **`when.ts`** says at what hour it comes there, from the daily run's (`DAILY_RUN_UTC_HOUR`, held to `vercel.json` by a test), for the card and the sheet. Pure.
- **`gather.ts`** reads what a summary says with the readers the app and the read-only API answer with: `readActivity` (`lib/api-read.ts`), `readBudgetMonth` (`lib/budget-month.ts`), `readGoals` (`lib/api-goals.ts`), the planned items and the connection records. A reader that finds stored data it can't use makes that part unread; anything else (storage out of reach) stops the summary.
- **`content.ts`** turns that into facts with the functions the app shows the same things with (`countsInTotals` and `leftOutByCurrency` in `lib/spending.ts`, `availableMeters` and `monthGapsOf` in `lib/rollover.ts`, `upcomingBills` in `lib/recurring.ts`, `plannedDates`, the goals' projection, the notices' states), and **`compose.ts`** puts them into the subject and plain text. Both pure. `compose.ts` is the one place that decides what may leave Nya. A name of the person's (a budget, category, goal, planned expense, or a bill's merchant) is counted instead of named when it has a digit, a currency or percent sign, a number or currency written as an English word (`NUMBER_WORDS`, `MONEY_WORDS`, plurals and words run together too), a number written as a Spanish, Portuguese, French, Italian or German word (`OTHER_NUMBER_WORDS`, joined as those languages join them), or a letter outside the Latin alphabet (`safeName`); a bank's, which comes from Plaid or SimpleFIN, only for a digit or a sign (`safeBankName`). Control and format characters are taken out of every name first. `figuresIn` then checks the finished subject and text as an allowlist: it takes out the links, the dates as `dayText`, `weekText` and `monthName` write them (a weekday that is that date's, a year only near the send day's), the counts as `plural` writes them (a number before one of the summary's own nouns), the week in the subject, its one phrase with a number word, and the banks' names and currency codes it wrote, and anything left that is a digit, a sign, a number or currency word or a letter outside the Latin alphabet is a figure. Both senders refuse a summary it finds one in, and the log names the kind.
- **`job.ts`** sends them from the daily snapshot; **`send-now.ts`** answers the card (whether this copy can send, saving, the preview, Send me one now); **`unsubscribe.ts`** makes and checks the links that turn it off.

**When it runs.** From the daily snapshot (`lib/snapshot-job.ts`; 13:00 UTC, and the catch-up at 15:00), once every container has run and the connection notices have gone, as one pass over the registry (`sendWeeklySummaries`). It takes the active containers whose snapshot is done for the day (recorded then or earlier, unclean, or with nothing linked); one whose snapshot failed, was deferred or is still running elsewhere waits for the catch-up run, so the week is whole when it is summed. Their settings and records are read five at a time, then taken in the registry's order. A container is due on its send day on its person's calendar (`dueSendDay`), judged at the day's own run (`scheduledFor` at 13:00 UTC, or the run's own time if that is earlier), so the catch-up two hours later only catches up what its day's run should have sent: judged at its own hour, it would be the first run of the day from UTC+9 to UTC+11, and would send there from a run that brings in no SimpleFIN bank. It is also due on one of the two days after if that day was missed and the setting was chosen before it began, never for a week already sent, and never for one that would mostly repeat the last (at least four of its seven days must be new). Mail not set up: the pass does nothing, silently, as the notices already say so. No `APP_URL`: nothing goes, since every summary must carry its link to turn it off, and the log says why.

**Its budget.** 120 seconds in all (`WEEKLY_BUDGET_MS`), and never past the run's own mail deadline, 285 seconds into the run (`MAIL_DEADLINE_MS`), inside the route's 300-second limit, so the snapshots and the notices only ever shorten it. Each step has a timeout of its own, and a summary is started only if all of them can end in time: bringing its transactions up to date (20 seconds), reading it (15), finding whom to write to (3) and the send (4). A step that runs out of time says which, and how long it had, in the log (`StepTimeoutError`). A sync that ran out of time is still going, so the pass waits for those before it ends, as long as the deadline allows and 15 seconds at most (`STRAGGLERS_MS`): one left going after the function returned could write an older state when a later request wakes the function again. One that outlives that is put right by the next sync, as when two devices sync at once. They go one at a time, at most two a second (Resend's default limit), and a 429 is waited out once when Resend asks for 2 seconds or less. What doesn't fit, and everything after Resend itself fails (no answer, a 5xx, still rate limited), waits for the next run, unrecorded: the catch-up, then the day after, and the one after that. So a deployment with many summaries due on one day sends them over its runs, not at once; spreading the runs across a window, already deferred for the snapshots, is what would lift that.

**Brought up to date first.** The snapshot fetches balances, not transactions, which the app brings in when it is opened. So each due summary first syncs the container's bank transactions as opening the app does (`assembleBankRows` with `sync`, one `/transactions/sync` per connection, not billed per call) and drops the dashboard's caches (`clearCaches`), so the app then shows what the email says. A sync that fails or runs out of time only leaves the summary saying which connection's transactions aren't in since when.

**Once a week.** The week's send day is recorded in `weekly-summary-state` once Resend accepts the summary, and a week recorded is never sent again. Each summary carries an idempotency key built from the container and the send day, hashed so it names neither (`weekKey`), which Resend keeps for 24 hours: a retry after an answer that never arrived isn't delivered twice. Resend refuses the key for a different email (the week's facts moved between two tries) with a 409, `invalid_idempotent_request`, and its docs don't say whether a key is kept after a request it failed. So a send that got no answer at all marks its week in the record (`unanswered`), and the refusal counts as sent only after such a try; otherwise nothing is recorded, and the week goes once the key lapses, within the two days it may still go. One still being sent by another invocation (`concurrent_idempotent_requests`) is left to it. A summary that was accepted but couldn't be recorded is sent again by the catch-up under the same key, which Resend drops. The record also keeps which goals the last summary found at their target (`goals_told`), so each is told of once.

**The link that turns it off.** Its token is `<container>.<YYYYMMDD>.<mac>`: the container's opaque id (so a request with no session finds its container in the token, as an API token does), the UTC day it stops working, 90 days on, and HMAC-SHA256 of the link's one purpose, the container and the day, under 32 random bytes kept in that container's `weekly-summary-state` and made anew whenever the summary is turned on after being off, in base64url and in one spelling only (43 characters hold two bits of padding, so four spellings decode to the same mac; only the one with them clear is a token). Something not in a token's form is refused at once and not counted. One in form that doesn't work is refused the same way whatever the reason, after the same work: the registry entry and the key are read at once, and the mac is compared in constant time, under a key that is never right when there is none. Those are counted by address with the API's tokens that don't work (`lib/rate-limit.ts`), and an address past a flood of them is turned away before anything is read; one that works is counted against its container, ten an hour. `GET /api/weekly-summary/unsubscribe` never acts (mail apps and scanners open links on their own): it sends the browser on to `/unsubscribe`, which asks first. `POST` turns the summary off, from that page's button or from a mail app's one-click unsubscribe (the `List-Unsubscribe` and `List-Unsubscribe-Post` headers, RFC 8058, which `lib/mail.ts` now sends), and answers the same whatever the summary was. Both are open without a session (`proxy.ts`: the route is exempt from the matcher, and `/unsubscribe` is in `PUBLIC_PAGES`): the token is the only credential.

**The card's routes**, behind the session gate, for the signed-in person's own container, answering storage errors as every route on the seam does: `GET` and `PUT /api/weekly-summary` (the setting, checked field by field, and whether this copy can send one; a demo account can't turn it on), `GET /api/weekly-summary/preview?weekday=&time_zone=` (this week's summary, gathered and composed as the job would, for the day and zone the sheet shows), and `POST /api/weekly-summary/send` (that summary, sent now, at most three a day, counted in `weekly-summary-sends`; its footer says when the next comes from the setting as saved, and it stands for the week's only with the summary on, for its own day and zone, and when it could say how the week's spending went).

## Bringing back a download

A person's JSON download brought into an empty account ([data-export.md](data-export.md#bringing-it-back) says what the person sees). The first step: a bank connected through Plaid comes back held until its accounts are linked; counting its rows before a link is a later step. Everything is in `lib/user-restore/`, named `user-restore` throughout, never "restoring", which is the operator's restore and a container's status.

- **The page reads the file** (`file.ts`, pure, a few megabytes at a time through `stream.ts`, a strict incremental JSON reader that refuses a key written twice and `__proto__`): `collect` checks every record against this release's closed shapes (`shapes.ts`, with every part named in `parts.ts`, which a test holds equal to the stores `lib/stores.ts` declares) and holds what is small; `buildBatches` builds the batches in the plan's order (`plan.ts`: categories, then accounts, rows, what was said, budgets and goals, history), reading the large parts again from the file; `send.ts` takes each batch's SHA-256, sends the parts kept on the seam to the server's checks first, starts, sends from where the record stops, and finishes. The browser can't load the stores, so the page checks the core parts and the server checks the rest.
- **The server checks every batch** (`check.ts`): a record of a store on the seam by the store's own `check` (as its reads would take it, after a JSON round trip) and closed: a field is known when the store's check looks at it, so each field is replaced by a value of another kind and the check must refuse it (`unknownField`), with the outside world's own records (an import's raw lines) taken as stored and maps of ids or days probed once. A legacy writer's records by the shape its module reads. History days are real days, finite numbers, and no measured day after the download or today.
- **The writes** (`commit.ts`): each record by its own ids, so a batch written twice writes the same thing: a map entry set, a large entry's piece appended from where it says it starts (a gap or another head refused), a history day set by its day, a one-value store written whole, the legacy ones through named writers in their modules (`restoreHistoryDays`, `restoreDirectoryEntries`, `restoreLinks`, `restoreBudgets`, and so on), never the save a person's edit takes. A store's bound is checked against what is stored before anything is written. The finish derives what the download leaves out (`import-summaries` and `history-import-summaries`, with what an undone import handed on, and the holdings index).
- **The routes.** `app/api/user-restore` (state, the emptiness scan, start, empty, undo) and its `batch` route (a check, a batch, the finish), off unless `RESTORE_ENABLED=1` (`enabled.ts`). The record (`store.ts`, `user-restore`) is claimed with a compare-and-set before anything is written and keeps the plan by every batch's digest; a batch is taken only as the next one, only with the plan's digest, re-checking the record just before it writes, and only while no bank holds a credential here. A batch runs at most 60 seconds; the undo sweeps the container (`lib/account-deletion.ts` `sweepContainerExcept`, keeping only the machinery that is independent of the data, `keptWhenEmptied` in `classes.ts`: what is derived from it, such as the holdings index and the walk's record, goes with it) twice, the second after a 65-second pause, then removes the record.
- **Empty, defined** (`empty.ts`, `classes.ts`): every key family and declared store has one class (`data`, `setting`, `machinery`, `record`), a test fails when one has none, and a key nothing names counts as data. The two keys of budgets are read rather than judged by name, since the first read of budgets stores an empty set (`loadBudgets`) as soon as the dashboard opens: one that holds no budget counts as nothing. The scan runs at the preview, the start and before emptying, counted.
- **The read side** (`restored.ts`), live whether restores are on or not. A restored Plaid account is an earlier account with a directory entry, its rows in `restored-transactions` under `restoredId`, an imported row's prefix, so no pruner takes what was said about one. Until the account is linked its rows are held (`lib/history-import/read.ts` lists them, with a `held` coverage note wherever a total covers their days); once linked, they are read as an earlier import ranked first: paired with the old copy's file rows as the old copy paired them (`pairedWithRestored`), then claiming the new bank's rows by the bank's key before the amount rule (`heldOf`), all worked out on every read, never written. `bankRowDisplay` (`lib/transactions.ts`) shows one as the bank row it was. Forgetting the account forgets its books and what was said about them by id (`forget.ts`).
- **What waits.** `totalsHold`: no net worth total is recorded (`recordFetch`), and the backfill waits, while a restore is unfinished or undoing, a restored account the directory still lists is neither linked nor ended (once linked it stays answered, whatever its bank becomes since, as an earlier account stays linked after a disconnect), or any of that can't be read. `restoreUnfinished` keeps the read-only API and the MCP server (503), shares (nothing shown) and the weekly summary (deferred) from answering out of part of the data.
